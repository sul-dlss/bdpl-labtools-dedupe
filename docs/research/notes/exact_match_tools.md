# Exact-match (hash-based) duplicate-file detection and hashing tools for digital archives (outside BitCurator)

Research date: 2026-11-01. Version numbers were cross-checked against Homebrew (`brew info`, run locally 2026-11-01) and the GitHub/Codeberg release APIs (queried 2026-11-01). "Pushed" dates are the repository's last-commit date from the GitHub API.

## Key Question 1: Command-line duplicate finders — matching method, safety, output, speed, maintenance

### Takeaway
All mainstream CLI finders use the same funnel (size grouping -> partial hash of first/last block -> full hash -> optional byte-by-byte compare); they differ mainly in (a) whether they ever touch the filesystem by default (jdupes, fdupes, rdfind, rmlint, fclones `group`, yadf, czkawka_cli all default to report-only, but fdupes/jdupes/rdfind have in-process delete switches that an archivist must never pass), (b) hash algorithm (non-cryptographic xxHash/metro by default in jdupes/fclones/yadf vs. BLAKE2b/BLAKE3 in rmlint/czkawka vs. MD5 in fdupes/dupeGuru), and (c) machine-readable output (JSON in jdupes/rmlint/fclones/yadf/czkawka; CSV in rmlint/fclones/yadf; fdupes and rdfind have no JSON). The most actively maintained in 2026 are jdupes (1.31.3, Oct 2026), rmlint (2.11.0, Nov 1 2026), czkawka (12.0.2, Sep 2026), yadf (1.5.2, Oct 2026), rdfind (1.8.0, Feb 2026); fclones' last release was Mar 2025; dupeGuru's last release was 2022; duff (2012) and FSlint (Python 2) are effectively dead.

### Inferences
- For an appraisal tool that must never modify sources, the safest CLIs are those whose binary has no in-process delete path or where deletion is a separate step: rmlint (writes a script, never deletes), fclones (`group` vs `remove` subcommands), yadf (report-only), czkawka_cli (`-D NONE` default, `-Q` dry-run). jdupes/fdupes/rdfind are safe only as long as `-d/-N/-L/-B`, `-d/-N/-i`, or `-deleteduplicates/-makehardlinks/-makesymlinks` are never passed; wrapper code should hard-code the argument list.
- "Read-only" is not the same as "writes nothing": rmlint writes rmlint.sh/rmlint.json to CWD by default and `--xattr` writes into source files' xattrs; fdupes `-c` and jdupes `-y` write hash databases; fclones/czkawka caches go to the user cache dir. Run tools from a working directory outside the accession and avoid xattr/cache-in-tree options. Also mount sources read-only or work from a disk image where possible.
- Default minimum-size filters differ (czkawka_cli skips files < 8192 bytes by default; rdfind ignores empty files by default; jdupes/fdupes include empties). For completeness in archival inventories, set min size to 0 explicitly.
- Non-cryptographic 64/128-bit hashes are acceptable for *finding candidates* when followed by byte compare (jdupes default) but not as the persisted identifier in archival metadata; use the tool's JSON for grouping and a separate SHA-256/BLAKE3 manifest for the record.
- Published benchmarks are all author-run (fclones and yadf READMEs) on Linux SSDs; relative ordering (Rust tools fastest; jdupes/fdupes slowest due to byte compare and single-thread) is consistent across them, but absolute times are not transferable to macOS or network storage.

### Gaps
- fclones has had no commits since March 2025; whether it is still maintained is unknown (no archived notice, no statement found).
- No independent (non-author) 2026 benchmark comparing these tools on macOS was found.

## Key Question 2: Hashing/manifest tools (hashdeep/md5deep, b3sum, RHash) and cross-manifest comparison

### Takeaway
hashdeep (v4.4, 2014, effectively unmaintained but still packaged) remains the only common tool with a built-in *audit* mode comparing a directory against a stored manifest and classifying matched/moved/new/missing files, plus DFXML output and multi-algorithm (default md5+sha256) in one pass; b3sum and RHash are faster or more flexible hashers (RHash computes many digests in one pass; b3sum is multithreaded) but cross-accession comparison with them requires your own join on the hash column (trivial in Python/SQLite).

### Cited Findings
- hashdeep/md5deep: "The latest release is version 4.4." GitHub release v4.4 published 2014-01-29; repo pushed 2025-09-20 (small fixes), language C++. Homebrew `md5deep` 4.4, GPL-2.0-or-later. "This version supports MD5, SHA-1, SHA-256, Tiger, and Whirlpool hashes." — [jessek/hashdeep](https://github.com/jessek/hashdeep); [GitHub API]; [brew info, local]
- hashdeep options: `-c` "Legal values are md5, sha1, sha256, tiger, and whirlpool."; `-k` "Load a file of known hashes."; `-a` audit: "An audit is said to pass if each input file is matched against exactly one file in set of knowns." and "collisions, new files, or missing files will make the audit fail"; `-v` levels show per-category counts, then discrepancies, then every file; `-m` "Positive matching, requires at least one use of the -k flag."; `-x` "Negative matching." (shows only files not in the known set); `-d` "Output in Digital Forensics XML (DFXML) format."; `-j` "Controls multi-threading" with default "one producer thread to scan the file system and one hashing thread per CPU core"; `-p` "Piecewise mode. Breaks files into chunks before hashing."; `-r` recursive; `-l` relative paths; `-w` "displays the filename of the known hash that matched the input file." — [hashdeep.1 man page](https://raw.githubusercontent.com/jessek/hashdeep/master/man/hashdeep.1)
- hashdeep known-set semantics: "Audit mode. Each input file is compared against the set of knowns." — [jessek/hashdeep README](https://github.com/jessek/hashdeep)
- BLAKE3/b3sum: "Much faster than MD5, SHA-1, SHA-2, SHA-3, and BLAKE2."; "Highly parallelizable across any number of threads and SIMD lanes, because it's a Merkle tree on the inside."; "Secure, unlike MD5 and SHA-1."; default output 256 bits; "The b3sum command line utility prints the BLAKE3 hashes of files or of standard input. It uses multithreading by default, making it an order of magnitude faster than e.g. sha256sum"; license "CC0 1.0" or Apache-2.0 / Apache-2.0 with LLVM exception. — [BLAKE3 GitHub](https://github.com/BLAKE3-team/BLAKE3); release 1.8.7 on 2026-08-20; Homebrew b3sum 1.8.7. — [GitHub API]; [brew info, local]
- RHash: "console utility for calculation and verification of magnet links and various message digests"; algorithms listed: CRC32, CRC32C, MD4, MD5, SHA1, SHA256, SHA512, SHA3, AICH, ED2K, DC++ TTH, BitTorrent BTIH, Tiger, GOST R 34.11-94, GOST R 34.11-2012, RIPEMD-160, HAS-160, EDON-R, Whirlpool; "Calculates several message digests in one pass."; output "a predefined (SFV, BSD-like) or a user-defined format"; updating hash files by "adding message digests of files missing in the hash file"; LibRHash library; "BSD Zero Clause License". ### Inferences
- Cross-accession dedup with hashdeep: run `hashdeep -r -c sha256 -l accessionA > A.txt`, then `hashdeep -r -c sha256 -k A.txt -m -w accessionB` to list every file in B that already exists in A (with `-w` naming the A file matched), or `-x` to list only new files. Audit mode (`-a`) is for same-tree verification (expects 1:1 match) rather than cross-accession dedup. hashdeep never writes to the scanned tree.
- Because hashdeep manifests are flat CSV-like text (size, hashes, path), they can be loaded into SQLite/pandas and joined on sha256 across any number of accessions; the same is true for b3sum/sha256sum/RHash output and siegfried CSV/JSON, so a Python dedup tool can treat "manifest" as the interchange format regardless of hasher.
- hashdeep is the only tool in this set that emits DFXML natively, which matters if the dedup tool should consume the same format fiwalk produces for disk images.

## Key Question 3: Known-file filtering — NIST NSRL RDS (RDSv3, Modern/Legacy/Android/iOS, minimal, CAID) and how forensic tools consume them

### Takeaway
NSRL now publishes only RDSv3 SQLite databases (current release 2026.09.1, quarterly: Modern, Legacy, Android, iOS sets, plus a "minimal" Modern DB of distinct FILE rows), with SHA-256 added alongside SHA-1/MD5; CAID is a separate JSON multimedia-metadata product, not a general known-file set. Legacy forensic consumers (TSK hfind, Autopsy) still key on MD5/SHA-1 text indexes and need a conversion step from RDSv3; bulk_extractor dropped its hashdb scanner in 2.0.

### Cited Findings
- Current release: "RDS Version 2026.09.1 - September 1, 2026". "The NSRL has completed the transition away from the RDS 2.XX text file format, and will only be publishing the RDSv3 SQLite database format moving forward." Release labels 2025.03.1, 2025.06.1, 2025.09.1, 2025.12.1, 2026.03.1, 2026.06.1, 2026.09.1 (quarterly pattern). Minimal: "mirrors the FILE, MFG, OS, and PKG views of the full publication database" and "will only contain the set of FILE data that includes just distinct FILE rows"; minimal databases currently planned only for the Modern set. Page links "RDSv3_to_RDSv2_text_files" guides for producing RDS 2.xx-style text files; "files of the RDSv3 format can be very large". — [NIST Current RDS Hash Sets](https://www.nist.gov/itl/ssd/software-quality-group/national-software-reference-library-nsrl/nsrl-download/current-rds)
- RDSv3 design (from the RDSv3 documentation PDF as summarized in search): main changes are "publication as an SQLite3 database, the inclusion of SHA-256 hashes for published files, and incremental releases"; the full publication covers four sets, "Modern, Legacy, Android, and iOS", with separate delta publications for each; delta publications are SQL INSERT/UPDATE/DELETE statements applied to the previous full DB. — [RDSv3.pdf](https://s3.amazonaws.com/rds.nsrl.nist.gov/RDS/RDSv3_Docs/RDSv3.pdf) (binary could not be text-extracted locally; see Gaps)
- Non-RDS sets: CAID — "Child Abuse Image Database (CAID) sets"; NSRL publishes JSON files of metadata about multimedia files that "can be imported into CAID tools" (NSRL-CAID-JPG.json, NSRL-CAID-MP4.json, etc.); full release path RDS/CAID/20260227-full with later dated releases 20260601 and 20260901 listed; deltas contain "new files added since the previous NIST NSRL CAID JSON release". Also offered: a SHA-1 to SHA-256 mapping file (16,801,737 rows matched to RDS 2.41 SHA-1 values), MD5 hashes of the first 4096 and 8192 bytes of files, ssdeep/sdhash data sets, and a "Curated Kaspersky Hash Set - 2017". — [NIST Non-RDS Hash Sets](https://www.nist.gov/itl/csd/secure-systems-and-applications/national-software-reference-library-nsrl/nsrl-download/non)
- TSK hfind: "fast lookups using a binary search algorithm instead of a linear search such as 'grep'"; index types "nsrl-md5 or md5sum" plus nsrl-sha1; "If index files exist for both SHA-1 and MD5 hashes, then both types of hashes can be given at runtime."; `-f` file of hashes one per line; `-q` quick 0/1. — [hfind man page](https://sleuthkit.org/sleuthkit/man/hfind.html). Supported DB types in source: `TSK_HDB_DBTYPE_SUPPORT_STR "nsrl-md5, nsrl-sha1, md5sum, encase, hk"`; enum also has IDXONLY and SQLITE (kdb) types. — [tsk_hashdb.h](https://raw.githubusercontent.com/sleuthkit/sleuthkit/develop/tsk/hashdb/tsk_hashdb.h). TSK latest release sleuthkit-4.15.0 (2026-04-15). — [GitHub API]
- Autopsy hash lookup: import formats Text (\*.txt, "One hash starting each line", md5/md5sum/md5deep output), Index only (\*.idx), Autopsy (\*.kdb, "SQLite hash sets created by Autopsy", only editable type), EnCase (\*.hash), HashKeeper (\*.hsh). Types: Known ("Known good files are those that can be safely ignored"), Notable, No change. NSRL: download pre-made index "NSRL-XYZm-dt-autopsy.zip" (dt = Android/iOS/Computer) from SleuthKitLabs GitHub releases; NSRL treated as "known". "SHA-256 hashes are also calculated, though these will not be used in hash set lookups" — lookups are MD5. — [Autopsy Hash Lookup docs 4.23.0](http://sleuthkit.org/autopsy/docs/user-docs/4.23.0/hash_db_page.html)
- bulk_extractor: "BE1.6 shipped with 37 individual scanners; BE2 has 35 (hashdb and sceadan both having been removed)". — [Garfinkel & Stewart, "Sharpening Your Tools: Updating bulk_extractor for the 2020s" (arXiv)](https://arxiv.org/pdf/2208.01639); pre-2.0 usage documented in [hashdb quick reference 2.0.1](https://downloads.digitalcorpora.org/downloads/hashdb/hashdb_quick_reference_2.0.1.pdf)
- dfxml_python ships `nsrl_rds.py` among its bin tools. — [dfxml_python bin listing](https://github.com/dfxml-working-group/dfxml_python/tree/main/dfxml/bin)

### Inferences
- For a Python appraisal tool, the simplest NSRL integration is to open the RDSv3 Modern *minimal* SQLite DB directly (`sqlite3` stdlib) and query the FILE view by sha256 (or md5/sha1) — no conversion to hfind/Autopsy index formats needed, and SHA-256 keys avoid relying on MD5. This also sidesteps Autopsy's MD5-only lookup limitation.
- Because RDS Modern is still huge, a practical pattern is to extract only the hash column(s) into a local set/Bloom filter or a sorted file; the "minimal" distinct-FILE-rows variant exists precisely to make this cheaper.
- CAID is irrelevant for OS/application filtering in an archives context (it is child-abuse multimedia metadata for law-enforcement tooling); the relevant NSRL product is RDS Modern (and Legacy for old PC software).
- Known-file filtering removes *system/application* noise but is orthogonal to intra-accession dedup; a dedup tool should report NSRL hits as a separate category ("known software file") rather than as duplicates.

### Gaps
- The RDSv3 FILE view's exact column names (e.g. sha256, sha1, md5, crc32, file_name, file_size, package_id) could not be verified: the RDSv3.pdf downloaded but could not be text-extracted on this machine (no poppler), and the RDS hash-set description page returned 404. Confirm against the `.schema.sql` shipped in each RDS zip.
- Whether "Unique" is still a published RDS variant was not confirmed (not mentioned on the current page; only Modern/Legacy/Android/iOS and Modern-minimal are).
- Exact download sizes of the 2026.09.1 sets are not stated on the page (README.txt per set has them).
- No primary documentation found for how the SleuthKitLabs NSRL index for Autopsy is generated from RDSv3.

## Key Question 4: Python libraries and archival-specific tools for building a dedup tool (hashlib, blake3, DFXML, siegfried, fixity tools, Brunnhilde, digiarch)

### Takeaway
The standard library (`hashlib.file_digest`, GIL release for >2047-byte updates, `sqlite3`) plus the `blake3` wheel (multithreaded, mmap) is enough to build a fast hashing core; for archival integration, Brunnhilde already produces siegfried-derived duplicate reports (MD5 default, configurable), digiarch (Aarhus) uses BLAKE2 collisions to flag duplicates, and dfxml_python provides a parser for fiwalk/hashdeep DFXML with a simple one-file `dedup.py`.

### Cited Findings
- hashlib: constructors always present: "md5(), sha1(), sha224(), sha256(), sha384(), sha512(), sha3_224(), sha3_256(), sha3_384(), sha3_512(), shake_128(), shake_256(), blake2b(), and blake2s()"; `file_digest(fileobj, digest, /)` added in 3.11 — "Return a digest object that has been updated with contents of file object."; "To allow multithreading, the Python GIL is released while computing a hash supplied more than 2047 bytes of data at once in its constructor or .update method."; `usedforsecurity=False` flag "indicates that the hashing algorithm is not used in a security context". — [Python hashlib docs](https://docs.python.org/3/library/hashlib.html)
- blake3 (PyPI): 1.0.11 "Released: Oct 8, 2026"; license "CC0-1.0 OR Apache-2.0"; author Jack O'Connor; requires Python >=3.11; built on "official Rust implementation of BLAKE3" via PyO3; API `blake3(data).hexdigest()`, `update()`, `max_threads=blake3.AUTO`, `update_mmap("/big/file.txt")`, keyed/derive_key modes; "this can be slower for inputs shorter than ~1 MB". — [PyPI blake3](https://pypi.org/project/blake3/)
- xxHash (for in-memory candidate hashing): "extremely fast non-cryptographic hash algorithm, working at RAM speed limits"; "xxHash is not a cryptographic hash function"; benchmark (i7-9700K): XXH3 59.4 GB/s (AVX2), XXH64 19.4, XXH32 9.7, BLAKE2 1.1, SHA1 0.8, MD5 0.6; library BSD-2-Clause. — [xxHash GitHub](https://github.com/Cyan4973/xxHash)

### Inferences
- A Python tool can reuse siegfried's single pass for both identification and hashing (`sf -json -hash sha256 -multi N`), avoiding a second read of every file; Brunnhilde demonstrates exactly this pattern (siegfried CSV -> SQLite -> duplicates report), so extending Brunnhilde or mirroring its schema is the lowest-effort archival-specific path.
- `hashlib.file_digest` + a `concurrent.futures.ThreadPoolExecutor` gets real parallelism for SHA-256 because the GIL is released during large updates; for BLAKE3 the wheel's own `max_threads=AUTO` parallelizes inside a single large file (useful for multi-GB disk images), while the ~1 MB threshold means small files should be hashed single-threaded.
- Size-prefilter + partial hash (first/last 4 KiB) + full hash is cheap to reimplement in Python (os.scandir for sizes, read 4 KiB head/tail), and most of the wall time is I/O; a pure-Python tool can therefore be adequate for appraisal-scale accessions, with fclones/jdupes as optional backends via their JSON output.
- No university-library-specific "appraisal dedup" script was found; the closest published archival tools are Brunnhilde (Canada/CCA origin) and digiarch (Denmark).

## Key Question 5: Hash-algorithm trade-offs for archival use and multi-algorithm support

### Takeaway
MD5 and SHA-1 are cryptographically broken (NIST: phase out SHA-1 by 2030) but remain adequate for *accidental*-collision dedup; SHA-256 is the conservative archival default; BLAKE3 offers SHA-256-class security at roughly an order of magnitude more throughput with multithreading; xxHash/metro are non-cryptographic and only appropriate as a candidate filter followed by byte compare or a strong hash. Multi-algorithm single-pass is supported by hashdeep (`-c md5,sha256`), RHash, and several finders (rmlint any one of ~20; fclones 7; czkawka 3; rdfind 5), but most *finders* compute only one algorithm per run.

### Cited Findings
- NIST (Dec 15, 2022): SHA-1 "should be phased out by Dec. 31, 2030, in favor of the more secure SHA-2 and SHA-3 groups of algorithms."; "We recommend that anyone relying on SHA-1 for security migrate to SHA-2 or SHA-3 as soon as possible."; modern computers "can create fraudulent messages that result in the same hash as the original." — [NIST Retires SHA-1](https://www.nist.gov/news-events/news/2022/12/nist-retires-sha-1-cryptographic-algorithm)
- BLAKE3: "Secure, unlike MD5 and SHA-1."; "Much faster than MD5, SHA-1, SHA-2, SHA-3, and BLAKE2."; b3sum "an order of magnitude faster than e.g. sha256sum" due to multithreading. — [BLAKE3 GitHub](https://github.com/BLAKE3-team/BLAKE3)
- xxHash speeds vs cryptographic: XXH3 59.4 GB/s vs SHA1 0.8 GB/s, MD5 0.6 GB/s (same table marks SHA1/MD5 "cryptographic but broken"); "Do not use it for signatures, password storage, or any other purpose that requires resistance to attacks." — [xxHash GitHub](https://github.com/Cyan4973/xxHash)
- rmlint warns against 64-bit hashes: "The use of 64-bit hash length for detecting duplicate files is not recommended, due to the probability of a random hash collision." Default blake2b; `-p` byte-by-byte. — [rmlint man](https://rmlint.readthedocs.io/en/latest/rmlint.1.html)
- dupeGuru's rationale for MD5: acknowledges MD5 collisions can be forged but argues accidental collisions with equal size are "very, very small". — [dupeGuru scan docs](https://dupeguru.voltaicideas.net/help/en/scan.html)
- Autopsy computes SHA-256 but still looks up by MD5 ("SHA-256 hashes are also calculated, though these will not be used in hash set lookups"). — [Autopsy docs](http://sleuthkit.org/autopsy/docs/user-docs/4.23.0/hash_db_page.html)
- NSRL added SHA-256 in RDSv3 and publishes a SHA-1 to SHA-256 mapping (16,801,737 rows). — [NIST Non-RDS](https://www.nist.gov/itl/csd/secure-systems-and-applications/national-software-reference-library-nsrl/nsrl-download/non)
- Multi-algorithm support per tool: hashdeep `-c` "Legal values are md5, sha1, sha256, tiger, and whirlpool" (comma list, one pass) — [hashdeep.1](https://raw.githubusercontent.com/jessek/hashdeep/master/man/hashdeep.1); RHash "Calculates several message digests in one pass." — [RHash](https://github.com/rhash/RHash); siegfried `-hash` one of md5/sha1/sha256/sha512/crc — [siegfried](https://www.itforarchivists.com/siegfried); fclones `--hash-fn` one of metro/xxhash3/blake3/sha256/sha512/sha3-256/sha3-512 — [fclones](https://github.com/pkolaczk/fclones); rdfind `-checksum` one of md5/sha1/sha256/sha512/xxh128 (default sha1) — [rdfind.1](https://raw.githubusercontent.com/pauldreik/rdfind/main/rdfind.1); czkawka_cli `-t` BLAKE3/CRC32/XXH3 (default BLAKE3) — [commands.rs](https://raw.githubusercontent.com/qarmin/czkawka/master/czkawka_cli/src/commands.rs); jdupes xxHash64 only (plus byte compare) — [jdupes](https://codeberg.org/jbruchon/jdupes); fdupes MD5 + byte compare — [fdupes.1](https://raw.githubusercontent.com/adrianlopezroche/fdupes/master/fdupes.1); bagit-python any of md5/sha1/sha256/sha512 (multiple manifests) — [PyPI bagit](https://pypi.org/project/bagit/)

### Inferences
- For appraisal dedup the threat model is accidental collision, not adversarial forgery, so even MD5 is functionally sufficient for grouping; the reason to prefer SHA-256 or BLAKE3 is interoperability of the stored hash with preservation systems (BagIt default sha256/sha512 in many implementations, NSRL SHA-256, fixity policies) and avoiding future re-hashing as MD5/SHA-1 are deprecated institutionally.
- BLAKE3 is the best speed/security choice for a new tool's internal hash, but SHA-256 (and MD5 for NSRL/legacy cross-walk) should be computable in the same pass — hashdeep's `-c md5,sha256` model, or hashing once in Python and feeding bytes to several hashlib/blake3 objects, costs one extra CPU pass with no extra I/O.
- Tools whose default hash is 64-bit (jdupes XXH64) or 128-bit non-cryptographic (fclones metro) are safe as *finders* only because jdupes byte-compares and fclones' 128-bit space makes accidental collision negligible, but their hashes should not be persisted as archival identifiers.

### Gaps
- No published measurement found of BLAKE3 vs SHA-256 throughput specifically on Apple Silicon macOS for file-hashing workloads (BLAKE3's own charts are Cascade Lake, 16 KiB inputs).

## Key Question 6: Deduplication across disk images / DFXML without extracting files

### Takeaway
Yes, in a limited way: fiwalk (Sleuth Kit) emits per-file MD5 and SHA-1 `<hashdigest>` elements in DFXML directly from a disk image without extracting files, and dfxml_python can parse those; but the only shipped dedup script (`dedup.py`) works on a single DFXML file with MD5 only, so cross-image or image-vs-directory dedup requires joining hashdigest values yourself (hashdeep `-d` produces compatible DFXML for directories). No general-purpose duplicate finder (jdupes, rmlint, fclones, czkawka) reads disk images or DFXML.

### Cited Findings
- fiwalk: "processes a disk image using the SleuthKit library"; outputs DFXML (`-X <file>`), ARFF (`-A`), text, body file (`-m`); `-M` (MD5) and `-1` (SHA1) both "(default on)"; `-z` "do not calculate MD5 or SHA1 values"; `-g` "just report the file objects - don't get the data"; `-O` "only walk allocated files". — [fiwalk(1) Debian man page](https://manpages.debian.org/unstable/sleuthkit/fiwalk.1.en.html)
- Example fiwalk DFXML fileobject contains `<hashdigest type='md5'>...</hashdigest>` and `<hashdigest type='sha1'>...</hashdigest>` plus inode, allocation status, timestamps and byte runs; SHA-256 not mentioned. — [forensics.wiki fiwalk](https://forensics.wiki/fiwalk/)
- hashdeep `-d` "Output in Digital Forensics XML (DFXML) format." (directory-side DFXML with md5/sha256). — [hashdeep.1](https://raw.githubusercontent.com/jessek/hashdeep/master/man/hashdeep.1)
- dfxml_python `dedup.py` groups fileobjects by MD5 within one DFXML file; no cross-file comparison; `idifference.py`/`idifference2.py`/`make_differential_dfxml.py` compare two DFXML files for changes; `hash_sectors.py` exists for sector hashing. — [dedup.py](https://raw.githubusercontent.com/dfxml-working-group/dfxml_python/main/dfxml/bin/dedup.py); [bin listing](https://github.com/dfxml-working-group/dfxml_python/tree/main/dfxml/bin)
- Brunnhilde instead extracts: "uses SleuthKit's tsk_recover to export files from a disk image" then runs siegfried; recommends DFXML for dates. — [brunnhilde](https://github.com/tw4l/brunnhilde)
- bulk_extractor's block-hash (hashdb) scanner was removed in 2.0. — [arXiv 2208.01639](https://arxiv.org/pdf/2208.01639)
- NSRL also publishes MD5 hashes of the first 4096 and 8192 bytes of files (useful for block/partial matching). — [NIST Non-RDS](https://www.nist.gov/itl/csd/secure-systems-and-applications/national-software-reference-library-nsrl/nsrl-download/non)

### Inferences
- A practical no-extract pipeline: `fiwalk -X image.xml image.E01` per image (MD5+SHA-1 only), parse with dfxml_python `objects.py`, and join on sha1 (or md5) across images and against hashdeep/siegfried manifests of loose-file accessions. Because fiwalk does not emit SHA-256, cross-walking to a SHA-256-keyed inventory requires either extracting matched candidates to compute SHA-256, or keying the whole inventory on SHA-1/MD5 as well (hashdeep `-c md5,sha1,sha256` can emit all three for directories).
- fiwalk hashes walk allocated and unallocated/orphan files alike unless `-O` is given; for appraisal dedup of *user content*, restrict to allocated files and report deleted-file matches separately.
- Known-file filtering fits naturally here: fiwalk's MD5/SHA-1 values match the keys hfind/Autopsy/NSRL have historically used, so NSRL filtering of disk-image contents can be done entirely from DFXML without extraction.

### Gaps
- Whether current Sleuth Kit fiwalk builds can emit SHA-256 was not confirmed (man page and wiki list only MD5/SHA-1); check `fiwalk -h` on TSK 4.15.
- No tool was found that natively deduplicates across multiple disk images in one step; the cross-image join appears to require custom code.
- fiwalk's supported image formats (raw, E01 via libewf, AFF) are not stated on the man page fetched; they depend on how TSK was built.
