# Archival practice and policy on deduplicating born-digital materials

Scope note: this file covers what archivists do and what the literature/institutional manuals say about duplicates in born-digital collections, plus the tool requirements that follow. Tool inventories are covered by other researchers; tools are named here only as practitioners report using them. Research conducted 2026-11-01. Every source is dated where the source gives a date. Several institutional pages could not be fetched (403/404/certificate errors); those are flagged under Gaps and, where only a search-engine snippet was available, the finding is marked "(snippet only)".

## KQ1. What do institutional born-digital processing manuals and frameworks say about duplicates, and at what tier/stage?

### Takeaway
The most widely cited community framework (Faulder et al., *Digital Processing Framework*, Aug 2018) places all duplicate-handling tasks at the **Moderate** processing tier (not Baseline), frames them as "assess contextual and information value... to determine if duplicates should be weeded," and requires that the decision be documented in collection documentation and the finding aid. Institutional manuals (UC/UCLA, Buffalo, GWU, LoC, Scholars Portal, NC State) are consistent on three points: duplicates are identified by hash comparison; identification is an appraisal-stage activity; removal is discretionary, should be done at media/folder rather than item level where possible, and must be recorded. No manual found mandates file-level deduplication, and several (UC Guidelines, LoC) explicitly caution against item-level weeding.

### Cited Findings
- The Digital Processing Framework (Faulder, Annand, DeBauche, Gengenbach, Irwin, Musson, Peltzman, Tasker, Uglean Jackson, Waugh; released August 2018) defines three tiers. Baseline = "the minimum recommended processing actions that should be taken for any born digital material... do not typically require specialized tools and skill sets"; Moderate = "may utilize forensic tools and require specialized skill sets... require additional investment"; Intensive = "most time consuming and resource intensive... cannot be accomplished without specialized tools and skill sets." — [Digital Processing Framework, Cornell eCommons (PDF)](https://ecommons.cornell.edu/handle/1813/57659)
- DPF has a dedicated activity "Address presence of duplicate content" with two tasks, both marked at the **Moderate** tier in the XLSX version: "Assess contextual and information value of duplicate content to determine if duplicates should be weeded" and "Document decision in collection documentation and in finding aid/catalog record." — [Digital Processing Framework XLSX, eCommons](https://ecommons.cornell.edu/handle/1813/57659) (verified by parsing the spreadsheet's tier columns)
- DPF activity "Identify deleted/temporary/system files" lists, also at **Moderate**: "Run tools to identify file formats indicating: (1) Temporary files; (2) Deleted files; (3) System files; (4) Hidden files; (5) Duplicate files"; "Appraise system-generated files"; "Appraise found files"; "Apply disposition of files as needed." — [Digital Processing Framework](https://ecommons.cornell.edu/handle/1813/57659)
- DPF's "Document disposition" task is at **Baseline**: "If files are deleted, restricted, or redacted note this in the Processing Information note and/or the Conditions Governing Access note in the finding aid, as well as in your collection management system and the collection file." Its "Determine and implement disposition" row distinguishes Baseline "Delete/deaccession at file/folder level", Moderate "Restrict (object/series/collection)" and Intensive "Redact". — [Digital Processing Framework XLSX](https://ecommons.cornell.edu/handle/1813/57659)
- DPF arrangement activity notes that identifying like content for intellectual arrangement is done only "if you were going to arrange files differently from original order"; the framework was drafted by ten archivists after a 2016 Born Digital Archiving eXchange unconference at Stanford. — [Digital Processing Framework](https://ecommons.cornell.edu/handle/1813/57659)
- *Guidelines for Efficient Archival Processing in the University of California Libraries*, Version 4 (May 2020; revision team incl. Shira Peltzman, UCLA, and Elvia Arroyo-Ramirez, UCI), born-digital appraisal recommendations: "Appraising digital content at a high level means surveying carriers, disk-images, and directories, not individual files"; "Do not rename or re-arrange digital files during appraisal"; "Commonly discarded digital content includes system files, software applications, user libraries, and duplicate files"; "Duplicate files can be identified by comparing hash values or using tools that automate the recognition and deletion of duplicate files, such as TreeSize Professional or FTK." — [UC Guidelines v4, eScholarship](https://escholarship.org/uc/item/4b81g01z)
- Same UC Guidelines, general appraisal: "Do not weed items from folders. 'Weeding is for gardeners, not archivists.'" and "Document major appraisal decisions... in the collection management system, the collection file, and in appraisal notes in finding aids... in accordance with DACS Principle 6." — [UC Guidelines v4](https://escholarship.org/uc/item/4b81g01z)
- Same UC Guidelines, photographs section: "Avoid item-level weeding. Retain duplicates, unless voluminous. Duplicates may have unseen value. For example, the presence of numerous copies indicates a preferred, heavily used image, and this can be significant evidential information for public figures." Also, donor surveys should "Identify the extent to which the content is duplicated in analog formats in hybrid collections." — [UC Guidelines v4](https://escholarship.org/uc/item/4b81g01z)
- UC Guidelines processing-plan questions include: "How much non-archival content is present (publications, photocopies, digital applications or software programs, duplicates)? Does it detract from the accessibility of unique materials? How easy is it to identify and separate during processing?" — [UC Guidelines v4](https://escholarship.org/uc/item/4b81g01z)
- University at Buffalo digital-materials processing guidance: in the collection-level Appraisal Information note, "Note any general information about actions relating to appraisal, deduplication, or weeding of digital files," link to policy, and "Do not include specific technical details about the process of de-duplication or weeding in Appraisal Information." Processing Information must record decisions that changed the material (migration, normalization, PII redaction, filename changes, deleted empty directories). Extent should count "the total number of files that have been preserved." A DROID file manifest exported pre-processing documents the original state and is "available on request." — [UB Libraries, Processing digital materials](https://research.lib.buffalo.edu/processing/digital-materials)
- GWU SCRC *Framework for Born-Digital Accessioning & Appraisal* (updated 2023-11-01): during media transfer, "identify media that does not need to be copied (duplicates, out-of-scope material, ect.)"; appraisal documentation lives in the ArchivesSpace accession record. — [GWU Framework](https://gwu-libraries.github.io/DigitalServicesDocs/borndigital/framework)
- GWU SCRC *Best Practices for Born-Digital Accessioning: Appraisal and Migration* (draft 2023-11-30): Level 1 (Full Migration) says "Review files for duplicate files." Worked examples: "Duplicate files were reviewed by the practitioner and removed from the SIP"; "A search for duplicate files was conducted and none were found"; and for personal papers, "Duplicate files were not retained once it was confirmed that they existed in another preferred file format (PDF/A)" (the .pages copy was dropped). The document states "Not every record has value worthy of inclusion" and that save-everything approaches "accrue significant environmental, labor, and resource costs overtime." — [GWU Best Practices](https://gwu-libraries.github.io/DigitalServicesDocs/borndigital/bestpractice)
- Library of Congress Manuscript Division born-digital processing-history note (2023): lists "Identify Duplicates and Empty Directories" as a processing stage; states duplicate files "take up space and in large numbers can encumber and confuse research efforts" and "may be appraised for potential removal"; LoC practice is to remove duplicates at the media or folder level rather than the file level (snippet only; PDF returned HTTP 403 on fetch). — [LoC MSS Processing History Note (PDF)](https://findingaids.loc.gov/exist_collections/ead3pdf/mss/2023/MSS-Processing-History-Note.pdf)
- Scholars Portal (OCUL) *Handling Digital Archives Before Ingest*, "Review and Appraisal": "identifying duplicate files is useful during the appraisal process" because it informs later weeding at arrangement; hybrid fonds "might be duplicates in multiple formats" (e.g., a PDF on a hard drive also printed and filed); "Institutions may wish to define policies or processes for determining when to keep or discard duplicates" and "how to document these decisions." Tools named: Brunnhilde, DROID, Duplicate File Finder, ExifTool scripts. — [Scholars Portal, Review and Appraisal](https://learn.scholarsportal.info/?p=4795)
- NC State Special Collections' standard born-digital workflow "already includes: Finding total size of package; Itemizing file types; Determining whether there are duplicates" (Kate Phillips, ARCHIVES*RECORDS 2025 poster). — [SAA 2025 poster PDF](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)
- Northwestern University Libraries born-digital workflow (DPC workflow webinar, 2025) lists deduplication as one step in "Intake and Assessment" alongside inventory, file review and filename normalization (snippet only; tokenized DPC link). — [DPC workflow webinars 2025](https://www.dpconline.org/)
- University of Idaho "Digital Processing Walkthrough" (updated 2026-03-24) generates MD5 checksums via DROID but contains no duplicate guidance at all. — [UIdaho spec-docs](https://uidaholib.github.io/spec-docs/content/processing/digital-ingest.html)
- Rockefeller Archive Center Processing Manual (docs.rockarch.org) contains no section on duplicates or deduplication; RAC digital processing "prioritizes minimal processing in the interest of preservation and access to at-risk digital storage media." — [RAC Processing Manual](https://docs.rockarch.org/processing-manual); [RAC blog, digital media processing](https://www.diglib.org/?p=17413)
- CCA (Canadian Centre for Architecture) Digital Archives Manual: Step 3 "Processing Archivist conducts weeding, arrangement, and preservation actions"; the arrangement guide contains no duplicate/deduplication procedure. — [CCA digital-archives-manual](https://github.com/CCA-Public/digital-archives-manual); [CCA arrangement guide](https://github.com/CCA-Public/digital-archives-manual/blob/master/guides/arrangement.md)
- Bentley Historical Library's 2011–2013 digital processing guidelines relied on batch micro-services and stated staff "would not work with content at the individual file level"; they are marked "no longer employed... provided for reference use only." No dedup step was found. Bentley's BitCurator intro course uses Brunnhilde's "number of unique vs. duplicate files" statistic and duplicate CSV to "aid in later appraisal and processing" but gives no guidance on acting on duplicates. — [Bentley 2011 draft guidelines](https://deepblue.lib.umich.edu/bitstream/handle/2027.42/96439/bhl_digitalprocessingguidelines_20111116-draft.pdf?sequence=1); [Bentley bitcurator-intro, Reporting](https://bentley-historical-library.github.io/bitcurator-intro/04-reporting.html)
- Beinecke (Yale) Manuscript Unit pursues "bit-level capture through disk imaging"; its processing manual page "Reporting Duplicates, Errors, or Metadata Enhancements" (posted 2021-02-10) concerns digitized images in the Digital Library ("if the exact same image appears twice, as a DL scan and as a photonegative"), not born-digital files. — [Beinecke MSU Processing Manual 9.10.1.1](https://msu-processing-manual.beinecke.library.yale.edu/91011-reporting-duplicates-errors-or-metadata-enhancements)
- Stanford (RBMS 2011, Glynn Edwards): forensic software (AccessData FTK) was used "including rendering files, identifying duplicates, full-text searching, and flagging restricted files" (snippet only). — [RBMS 2011 Edwards slides](https://www.slideshare.net/slideshow/rbms-2011-edwards-8463230/8463230)
- SAA Dictionary of Archives Terminology defines deduplication as "the process of identifying and removing redundant electronic files," and quotes Thompson 2022: "Deduplication of those files deemed to be unnecessary should be part of the appraisal process," and Skinner & Hulbert 2022: archivists "have been trained to ask donors to deduplicate files before transfer," which was not practical for some donors. — [SAA Dictionary, deduplication](https://dictionary.archivists.org/entry/deduplication.html)
- BitCurator documentation lists FSlint for "duplicate file identification and deletion," and Christopher Lee's 2014 iPRES paper lists "identifying duplicate files, generating PREMIS metadata" among BitCurator features; fiwalk exports DFXML with per-file hashes, which practitioners use in spreadsheets to "quickly search for duplicate files." — [BitCurator Walkthrough](https://bitcurator.github.io/documentation/BitCurator%20Walkthrough/BitCurator%20Walkthrough); [DFRWS 2014 BitCurator presentation](https://dfrws.org/sites/default/files/session-files/2014_USA_pres-enabling_digital_forensics_practices_in_libraries_archives_and_museums_-_the_bitcurator_experience.pdf); [UCL student BitCurator report](https://reflect.ucl.ac.uk/inst0045-1920-jess-conway/?p=477)

### Inferences
- The field's consensus structure is: *detect* duplicates early (appraisal/accessioning, cheap, hash-based, often Baseline-level tooling like Brunnhilde/DROID), but *decide and act* only at Moderate tier after assessing context, and *always document*. A tool aimed at the appraisal stage should therefore be a detection-and-reporting tool that defers deletion to a human and emits documentation-ready output.
- The UC Guidelines' "do not rename or re-arrange digital files during appraisal" and "survey carriers, disk images, and directories, not individual files" imply appraisal-stage dedup should report at carrier/directory granularity (e.g., "disk 7 is 94% contained in disk 3") in addition to file-level lists.
- Institutional manuals rarely spell out a dedup procedure; Scholars Portal explicitly tells institutions to write one. A tool that ships with a configurable, documented decision policy fills a real gap.

Statements from these rest on search snippets.
- No current (post-2013) Bentley, Stanford SUL, UNC Wilson, Emory Rose Library, NYPL (digarch page 404), UCLA-specific, NARA, or Library and Archives Canada document stating a born-digital deduplication rule was found. LAC's removals directive lists "duplicates" as grounds for removing private archives (snippet only; PDF page returned only an archived notice).

## KQ2. Definitions: exact duplicate, near duplicate, version, copy in different container

### Takeaway
Practice literature uses a narrow technical definition (identical bitstream = identical checksum) for "duplicate," while treating versions/drafts, format-shifted copies (e.g., .pages vs PDF/A), analog-digital pairs, and copies embedded in containers (disk images, email threads, zipped packages) as appraisal judgments rather than mechanical matches. No archival standard definition of "near duplicate" was found.

### Cited Findings
- SAA Dictionary: deduplication (n.) "the process of identifying and removing redundant electronic files"; quotes Wong 2006: "Deduplication is the process of identifying two files as being the same file," with duplicate email attachments as the common example. — [SAA Dictionary](https://dictionary.archivists.org/entry/deduplication.html)
- TNA digital-transfer guidance: "if two records are exactly identical, the checksums will be the same," generated by DROID along with format, size and last-modified date; "on average there is 40% duplication in the digital environment." — [TNA Steps 1 and 2: Appraisal and selection](https://www.nationalarchives.gov.uk/information-management/manage-information/digital-records-transfer/digital-transfer-steps/steps-1-and-2-appraisal-and-selection/)
- Princeton University Archives: a checksum lets an archivist "rapidly determine whether multiple copies of the same file are present even when those files have different names and locations on the file system"; MD5 and SHA-1/SHA-256 are the most widely used in archives (snippet). — [Princeton University Archives, fixity post (2014)](https://universityarchives.princeton.edu/2014/10/the-university-archives-and-its-focus-on-fixity)
- GWU treats a format-shifted copy as a duplicate only after confirming the preferred-format copy exists: "Duplicate files were not retained once it was confirmed that they existed in another preferred file format (PDF/A)." — [GWU Best Practices](https://gwu-libraries.github.io/DigitalServicesDocs/borndigital/bestpractice)
- Scholars Portal treats cross-format duplication (digital PDF vs printed paper copy) as a duplicate category to review in hybrid fonds. — [Scholars Portal](https://learn.scholarsportal.info/?p=4795)
- UC Guidelines ask donor surveys to "Identify the extent to which the content is duplicated in analog formats in hybrid collections." — [UC Guidelines v4](https://escholarship.org/uc/item/4b81g01z)
- Email: ePADD de-duplicates a message that "appeared in the MBOX file more than once because it was part of a chain"; a parser bug (body text "From " read as a new message) created false extra entries, showing how container parsing affects duplicate counts. — [Rylands Blog, Palladium project (2021-11-17)](https://rylandscollections.com/2021/11/17/palladium-project-development-work-on-epadd/)
- Web archives: WARC "revisit" records with the identical-payload-digest profile cover a payload whose strong digest (e.g., SHA-1) matches a previously recorded version; the spec "does not adequately address spatial duplicates" (same content at different URIs), because replay indexes are keyed by URI+timestamp. — [IIPC WARC deduplication proposal 1.0](https://iipc.github.io/warc-specifications/specifications/warc-deduplication/recording-arbitrary-duplicates-1.0)
- Drafts/versions: a UMD/Rushdie-related paper argues auto-saved drafts "provide a record of the author's intellectual process," cutting against discarding near-identical drafts (snippet). — [UMD eniss paper (2010)](https://archive.mith.umd.edu/forensics/wp-content/uploads/2010/05/4n6umd_eniss.pdf)
- Audio heritage: Six et al. report "around 38%" duplicate material in a Belgian shellac-disc collection found by acoustic fingerprinting (near-duplicate detection on content, not bits), suggesting linking duplicates so users can be sent to better-preserved copies. — [Six et al., 2022/2023 duplicates chapter](https://0110.be/files/publications/2022/2022.duplicates-author_version.pdf)

### Inferences
- A tool should distinguish at least four classes with different default actions: (1) bit-identical (same hash) — safe to report as exact; (2) same content, different container (file in disk image vs extracted file, message in MBOX vs EML, file inside ZIP) — exact at payload level but needs container-aware extraction; (3) format-shifted equivalents — never auto-matched, surfaced as candidates by name/size/date; (4) versions/drafts — never flagged as duplicates by default.
- Filename and timestamp differences do not negate duplication (hash match is authoritative), but differing timestamps/paths are themselves evidence worth preserving in the report.

### Gaps
- No archival standard or widely cited definition of "near-duplicate" for born-digital documents was found; near-duplicate work found is from audio archives (fingerprinting) and commercial email archiving.

## KQ3. When dedup happens: pre-accession, appraisal, processing, preservation

### Takeaway
Duplicates are *identified* as early as donor negotiation and accessioning (TNA requires a DROID CSV with checksums before transfer; archivists historically asked donors to dedupe), *decided on* during appraisal/processing at Moderate tier, and occasionally *re-addressed* in reappraisal of legacy servers. Preservation-system-level dedup (Archivematica AIPs) is essentially absent from archival practice; removing files from an AIP is manual and disruptive.

### Cited Findings
- Pre-accession: SAA Dictionary quoting Skinner & Hulbert 2022 — archivists "have been trained to ask donors to deduplicate files before transfer," though impractical for some donors. — [SAA Dictionary](https://dictionary.archivists.org/entry/deduplication.html)
- Pre-accession (UK government): TNA requires a DROID CSV export (with checksums) "at the end of steps 1 and 2 (appraisal and selection), before you can proceed" to transfer; checksums help find exact duplicates to reduce review volume. — [TNA Steps 1 and 2](https://www.nationalarchives.gov.uk/information-management/manage-information/digital-records-transfer/digital-transfer-steps/steps-1-and-2-appraisal-and-selection/)
- Pre-accession (donor-side email): ePADD's appraisal module lets creators mark messages "Do Not Transfer" ("The files exported from ePADD will NOT contain the messages flagged as 'Do Not Transfer'"), and message deduplication runs automatically at ingest. — [LoC The Signal, ePADD team (2014-10-20)](https://blogs.loc.gov/thesignal/2014/10/the-epadd-team-on-processing-and-accessing-email-archives/); [Rylands Blog (2021)](https://rylandscollections.com/2021/11/17/palladium-project-development-work-on-epadd/)
- Accessioning/media transfer: GWU — appraise carriers to "identify media that does not need to be copied (duplicates, out-of-scope material, ect.)" — [GWU Framework (2023)](https://gwu-libraries.github.io/DigitalServicesDocs/borndigital/framework)
- Appraisal: UC Guidelines place duplicate identification in appraisal but forbid renaming/re-arranging at that stage. — [UC Guidelines v4 (2020)](https://escholarship.org/uc/item/4b81g01z)
- Processing: DPF places assess/weed/document duplicate tasks at Moderate processing tier. — [DPF (2018)](https://ecommons.cornell.edu/handle/1813/57659)
- Processing (NC State): dedup was performed "after transferring and arranging files," using jdupes to create symbolic links and a report of where each link pointed. — [SAA 2025 poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)
- Reappraisal: University of Kentucky (McDonnell, SAA ERS blog, 2025-11-05) used TreeSize's duplicate search across servers during reappraisal of legacy migrated data, finding "terabytes of duplicate materials that were clearly remnants of earlier processing"; "duplicate files with different names are still found thanks to the software's checksum comparisons." — [SAA ERS blog, Looking for Trouble](https://saaers.wordpress.com/2025/11/05/looking-for-trouble-born-digital-reappraisal)
- Preservation system: an Archivematica user describes purging files from an existing AIP by exporting, removing files, and re-ingesting, which "will result in us needing to re-do some of the descriptions on the AtoM side." — [Archivematica Google Group, Deaccessioning/removing files from AIPs](https://groups.google.com/g/archivematica/c/K_Vw8IvkWII)
- Preservation system (Wellcome): accessions are ingested as a single bag, then re-ingested "so that there is one 'bag' for each item" after arrangement, with the original accession bag deleted; no duplicate rule stated. — [Wellcome Collection, Born-digital cataloguing](https://docs.wellcomecollection.org/archive-cataloguing/general-guidance/preparing-a-collection-for-cataloguing/born-digital-cataloguing)
- Web archiving: dedup happens at crawl time (warcprox hashes payloads against a dedup DB and writes a revisit record on a match) or post-crawl (warcrefs converts duplicates to revisit records). Browsertrix (Webrecorder, 2026-04-09) dedupes against a Collection-level index; removing content does not remove it from the index; admins can purge/rebuild the index. — [IIPC spec](https://iipc.github.io/warc-specifications/specifications/warc-deduplication/recording-arbitrary-duplicates-1.0); [Webrecorder blog 2026](https://webrecorder.net/blog/2026-04-09-deduplication)

### Inferences
- Because preservation-system removal is costly and descriptive records depend on AIP contents, the economically rational point to decide about duplicates is before SIP/AIP creation, i.e., exactly the appraisal stage the Stanford tool targets. Once in the repository, practice shifts to *linking* (NC State symlinks, WARC revisits) rather than deleting.
- Detection should be re-runnable across accessions and across time (reappraisal), so hash manifests must persist and be comparable to earlier accessions' manifests.

### Gaps
- No source quantifies how often institutions dedup at each lifecycle stage; the Northwestern and LoC step lists are the only explicit stage placements beyond DPF/UC.

## KQ4. Decision rules: which copy to keep, how to record removed duplicates, when never to dedup

### Takeaway
Explicit rules are scarce. Those found: keep the copy in the preferred/preservation format (GWU); keep the copy that preserves the creator's folder structure and link the rest (NC State); remove at media/folder level rather than file level (LoC, UC); retain duplicates unless voluminous because multiplicity itself can be evidence (UC photographs); never dedup silently (Galloway, DPF). Documentation goes in Appraisal Information/Processing Information notes, the collection management system, and processing reports packaged with the files.

### Cited Findings
- Which copy to keep — preferred format: "Duplicate files were not retained once it was confirmed that they existed in another preferred file format (PDF/A)." — [GWU Best Practices (2023)](https://gwu-libraries.github.io/DigitalServicesDocs/borndigital/bestpractice)
- Which copy to keep — preserve creator order, link the rest: NC State kept folders "nested within a folder representing each drive," then "used the tool Jdupes to create symbolic links for each duplicate and generate a report of where link pointed. This was placed with other processing reports to be packaged with the digital files." Goal: researchers can "recreate Hall's original folder structure." — [SAA 2025 poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)
- Granularity: LoC removes duplicates at media or folder level, not file level (snippet). — [LoC MSS note (2023)](https://findingaids.loc.gov/exist_collections/ead3pdf/mss/2023/MSS-Processing-History-Note.pdf); UC: appraise "carriers, disk-images, and directories, not individual files"; "Do not weed items from folders." — [UC Guidelines v4](https://escholarship.org/uc/item/4b81g01z)
- When not to dedup — evidential multiplicity: "Retain duplicates, unless voluminous. Duplicates may have unseen value... numerous copies indicates a preferred, heavily used image... Subtle differences in contrast or retouching may be apparent among numerous proof prints." — [UC Guidelines v4](https://escholarship.org/uc/item/4b81g01z)
- When not to dedup — forensic/bit-level capture: Galloway (AERI 2010) argues "order as received" on media is itself evidence (e.g., "the contrast between the dates listed for the individual items by the operating system as contrasted with the dates of those same items as made available in the internal metadata"), that archivists customarily "weed duplicates" yet "nor is any public statement usually made as to what exactly has been done," and urges abandoning "the too frequently silent emendation by archivists of 'order as received'." The disk image is "about as close to the archival concept of 'fixed to a medium' as one can get." — [Galloway, Order As Received (2010)](https://pages.ischool.utexas.edu/galloway/spring2018/INF392K2018/OrderAsReceivedAERI-1.pdf)
- When not to dedup — restricted content check: a Harvard guide suggests that for a file restricted for 50 years "it may be worth your time to check to see if it is in fact a duplicate," since keeping dark files is complex (snippet only; page returned empty). — [Harvard wiki](https://harvardwiki.atlassian.net/wiki/x/TgZZAg)
- Context over bits: Emory's Rushdie team asked whether "the context that holds this data, the paratextual elements" is of equal importance to the data, and built a partitioned architecture that "makes copies while preserving the originals." — [Farr, Rushdie's Computers (DH abstract)](https://dh-abstracts.library.virginia.edu/works/734)
- Recording removals — DPF Baseline: "If files are deleted, restricted, or redacted note this in the Processing Information note and/or the Conditions Governing Access note in the finding aid, as well as in your collection management system and the collection file." — [DPF XLSX](https://ecommons.cornell.edu/handle/1813/57659)
- Recording removals — Buffalo: general dedup/weeding statement in Appraisal Information (no technical detail), specific changes in Processing Information, Extent counts preserved files only, and a pre-processing DROID manifest documents the original state. — [UB Libraries](https://research.lib.buffalo.edu/processing/digital-materials)
- Recording removals — GWU: appraisal findings recorded in the ArchivesSpace accession record and the BagIt bag-info ("The 50 year restriction and lack of a PII search was noted in the BagIt info file"; "The accession record was updated to reflect the information learned about the digital files"). — [GWU Best Practices](https://gwu-libraries.github.io/DigitalServicesDocs/borndigital/bestpractice)
- Recording removals — NC State: "added extra metadata into the finding aid to record the arrangement and processing steps unique to this collection" plus a spreadsheet inventory tracking each folder's destination record. — [SAA 2025 poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)
- Preservation-event vocabulary: PREMIS defines deletion as permanently and willfully removing an object, often preceded by deaccession, and appraisal as evaluating whether an object should be included/retained; APTrust records file-level deletion events (when, at whose request) and keeps the object/file record after deletion. — [APTrust Registry events](https://docs.aptrust.org/user-guide/registry/events/); [PREMIS preservation events (Lyrasis wiki)](https://wiki.lyrasis.org/x/o5IOB)
- Email versions: the Mailbag Specification 1.0 says "If a user wishes to manage multiple versions of an email message, such as for managing redactions or restrictions, they should use multiple mailbags," and maps bag metadata fields to PREMIS (e.g., Bagging-Timestamp to PREMIS event eventDateTime). — [Mailbag Specification 1.0](https://archives.albany.edu/mailbag/spec/)

### Inferences
- A defensible default keep-rule hierarchy, synthesized from the sources: (1) prefer the copy on the earliest/primary carrier or in the creator's most structured directory (original-order argument); (2) prefer preservation-format over proprietary when content-equivalent; (3) never auto-select — present the rule and let the archivist override.
- "Removed" should normally mean "excluded from the processed SIP/DIP while retained in the disk image or accession bag," not destroyed; every source that records a dedup action keeps a pointer (symlink report, finding-aid note, manifest).
- No source found recommends a PREMIS event type specifically for deduplication; institutions that log would use `deletion`/`deaccession` events plus a processing note. A tool should therefore emit a generic event record (agent, date, algorithm, rule, affected files, pointer to retained copy) that can be mapped to PREMIS `deletion` or a local event type.

### Gaps
- No institutional policy stating a formal "which copy wins" algorithm was found; GWU and NC State are single-case examples.
- No published PREMIS profile or controlled-vocabulary event for deduplication was found.

## KQ5. Quantitative duplicate rates and tools used in real collections

### Takeaway
Reported rates are few and collection-specific: 10–50% per drive and a ~41% storage reduction (±15% error) in a photographer's 8 TB/7-drive collection (NC State, 2025, jdupes + Brunnhilde); TNA's generic claim of "on average 40% duplication in the digital environment"; ~38% in a shellac-disc audio collection (fingerprinting); "terabytes" of duplicates on legacy servers (Kentucky, TreeSize). No cross-institutional survey of duplicate rates exists.

### Cited Findings
- NC State, John M. Hall Photographs: 7 hard drives, ~8 TB, ~20 years of photographs; "~10-50% of each drive is comprised of duplicates of the photos on other drives"; result "an estimated 41% reduction of total storage size for images" — "2518996.112 MB or a 41.89% difference after processing"; "Our reduction estimate has an error of 15%, which keeps the low end... at the estimated reduction of 26%"; "known error rate of 8% for records that needed to be re-done"; ~200 resulting records; 100 GB soft limit per package; disk images were made of each drive to pull files from "instead of the physical media"; Brunnhilde "would count symbolic links as having the same size as the file they link to," so 9 records lack accurate storage data; `du -sh` added to size step to account for symlinks. — [SAA 2025 poster PDF](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG); [SAA 2025 session page](https://www.pathlms.com/saa/events/11920/event_sections/18596/slide_presentations/377394)
- NC State also reports the arrangement step "was time extensive, had a relatively significantly larger error rate, and reduced our ability to maintain original order," and challenges of "Inconsistent labelling across drives" and "Inconsistent organization across drives." — [SAA 2025 poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)
- TNA: "on average there is 40% duplication in the digital environment" (no source given on page). — [TNA Steps 1 and 2](https://www.nationalarchives.gov.uk/information-management/manage-information/digital-records-transfer/digital-transfer-steps/steps-1-and-2-appraisal-and-selection/)
- Belgian shellac discs: "a surprisingly high amount of duplicate material of around 38%." — [Six et al. 2022/2023](https://0110.be/files/publications/2022/2022.duplicates-author_version.pdf)
- University of Kentucky reappraisal: "terabytes of duplicate materials that were clearly remnants of earlier processing," found with TreeSize across multiple servers. — [SAA ERS blog 2025](https://saaers.wordpress.com/2025/11/05/looking-for-trouble-born-digital-reappraisal)
- UCI 2014 Commencement collection: 2.5 TB on one hard drive, "over two terabytes of raw video files"; the IJDC case study (Uglean Jackson & McKinley, 2017) discusses apparent duplicate images but no percentage was found. — [IJDC article record](https://libmast.utm.my/Record/doaj.art-fcebc22a552848eda5225e394970d0eb); [OAC finding aid](https://oac-stg.cdlib.org/findaid/static/ark:/13030/c80g3nf5)
- Manchester/Rylands ePADD (2021): ePADD reports contain "important information on duplicate email" but "We were getting different figures for this process on the summary report and the individual MBOX file reports" because "the figures were being calculated differently for different reports." — [Rylands Blog](https://rylandscollections.com/2021/11/17/palladium-project-development-work-on-epadd/)
- Optical media (De Gruyter, Preservation, Digital Technology & Culture 2024): cross-disc checksum comparison "was not in archivists' toolkits, so a large degree of manual labor was still required" (snippet only; article returned 405). — [PDT&C 2024 article](https://www.degruyterbrill.com/document/doi/10.1515/pdtc-2024-0042/html)
- A Wellcome Library source notes existing appraisal workflows "were designed around much smaller deposits" than modern hard drives (snippet). — [Archives and Records 2016 article](https://informahealthcare.com/doi/full/10.1080/23257962.2016.1144504)

### Inferences
- The NC State case is the best-documented practitioner dataset and shows two tool pitfalls a new tool must avoid: size reporting that mis-counts links, and inability to predict record counts before processing ("Unclear how many duplicates there were, or how many eventual records"). A pre-processing cross-media duplicate matrix would have answered that question up front.
- The 40% figure (TNA) and the 10–50% (NC State) suggest tools should be designed for high-duplication inputs where the duplicate set is larger than the unique set, so reports must aggregate (by directory, by carrier) rather than list file pairs.

### Gaps
- No peer-reviewed cross-collection survey of duplicate rates in personal digital archives was found; Emory Rushdie and Stanford case literature did not surface quantitative dedup figures.

## KQ6. Arguments for keeping vs removing duplicates

### Takeaway
Arguments for removal are storage cost, environmental cost, reading-room usability (packages too large to move; "encumber and confuse research"), and processing/review time. Arguments for keeping are evidential value of multiplicity and placement, original/"received" order, differing timestamps and paths, the risk that detection is wrong (parser bugs, false matches), and the labor/error cost of rearrangement itself. The literature's resolution is: keep bits (disk image/accession bag), reduce copies in the processed/access package, and document.

### Cited Findings
- Removal — storage/usability: NC State needed arrangement because "packages over 100 GB were hard to move from preservation storage to the reading room"; dedup "made such a large collection more manageable by reducing the size of archival packages available to researchers." — [SAA 2025 session](https://www.pathlms.com/saa/events/11920/event_sections/18596/slide_presentations/377394); [poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)
- Removal — research confusion: duplicate files "take up space and in large numbers can encumber and confuse research efforts" (LoC, snippet). — [LoC MSS note](https://findingaids.loc.gov/exist_collections/ead3pdf/mss/2023/MSS-Processing-History-Note.pdf)
- Removal — environmental: Pendergrass, Sampson, Walsh & Alagna, "Toward Environmentally Sustainable Digital Preservation," *American Archivist* 82(1), 2019 (SAA Posner Award 2020) propose folding sustainability into appraisal, permanence and availability decisions; SAA Dictionary's Thompson 2022 quote adds that "retaining one copy and using metadata pointers can reduce storage and environmental costs." — [Harvard DASH record](https://dash.harvard.edu/handle/1/40741399); [SAA Dictionary](https://dictionary.archivists.org/entry/deduplication.html); GWU: save-everything approaches "accrue significant environmental, labor, and resource costs overtime." — [GWU Best Practices](https://gwu-libraries.github.io/DigitalServicesDocs/borndigital/bestpractice)
- Removal — review volume: TNA — identifying exact duplicates reduces the volume for sensitivity review. — [TNA Steps 1 and 2](https://www.nationalarchives.gov.uk/information-management/manage-information/digital-records-transfer/digital-transfer-steps/steps-1-and-2-appraisal-and-selection/)
- Keep — evidential multiplicity: "numerous copies indicates a preferred, heavily used image... significant evidential information." — [UC Guidelines v4](https://escholarship.org/uc/item/4b81g01z)
- Keep — order as received and silent weeding: Galloway 2010 (quoted above). — [Galloway 2010](https://pages.ischool.utexas.edu/galloway/spring2018/INF392K2018/OrderAsReceivedAERI-1.pdf)
- Keep — conceptual order: Niu argues electronic records have a conceptual order based on creation context and archivists should "respect the original order by creating folder structures that mimic the physical order of storage media" (snippet). — [Niu, via search]((https://www.bing.com/search?q=Jinfang+Niu+original+order+electronic+records))
- Keep — cost of rearrangement: NC State's arrangement step "reduced our ability to maintain original order" and had an 8% redo rate. — [poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)
- Keep — detection error: ePADD's "From " parser bug created spurious message splits and inconsistent duplicate counts across reports. — [Rylands Blog 2021](https://rylandscollections.com/2021/11/17/palladium-project-development-work-on-epadd/)
- Keep — email threads: SAA Dictionary cites Kopin, Hutchinson & Truitt 2025: tools such as ePADD and DarcMail "can make it harder to read threads in context," and "technical issues like deduplication can add to that difficulty." — [SAA Dictionary](https://dictionary.archivists.org/entry/deduplication.html)
- Middle path — link rather than delete: NC State symlinks with a pointer report; WARC revisit records with WARC-Refers-To; Six et al. recommend linking audio duplicates "so listeners can be sent to better-preserved copies." — [poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG); [IIPC spec](https://iipc.github.io/warc-specifications/specifications/warc-deduplication/recording-arbitrary-duplicates-1.0); [Six et al.](https://0110.be/files/publications/2022/2022.duplicates-author_version.pdf)
- Middle path — Emory: "partitioned data architecture that makes copies while preserving the originals." — [Farr abstract](https://dh-abstracts.library.virginia.edu/works/734)

### Inferences
- The strongest practitioner compromise is "preserve the image, dedupe the DIP." An appraisal-stage tool should make this explicit by never proposing deletion from a disk image or accession bag, only exclusion from a derived package, and by always retaining a map from excluded copies to the kept copy.
- Because arguments for keeping hinge on *where* and *when* duplicates occur, the report must retain full path, carrier ID, filesystem timestamps and embedded metadata timestamps for every member of a duplicate group, not just the kept one.

### Gaps
- No single essay arguing directly against deduplicating born-digital materials was found; the "keep" position is assembled from original-order, forensics and photographic-appraisal literature.

## KQ7. Email- and web-archive analogies for design

### Takeaway
Email (ePADD, Mailbag) and web archiving (WARC revisits) offer three transferable patterns: dedup at ingest with a persistent digest index; record the duplicate as a lightweight pointer record (revisit + WARC-Refers-To / symlink + report) rather than silently dropping it; and keep variant representations (redacted, restricted) as separate packages rather than mutating the original.

### Cited Findings
- ePADD dedups messages automatically at ingest; reports include duplicate counts; counts differed between summary and per-MBOX reports due to different calculations and parser bugs; developer fix plus a workaround ("add a hash after the word" From). Duplicate attachments appear as a separate error category (a user reported "241 duplicate attachments"). — [Rylands Blog 2021](https://rylandscollections.com/2021/11/17/palladium-project-development-work-on-epadd/); [ePADD users group thread](https://groups.google.com/g/epaddusers/c/H-BMxiJBAnA); [Illinois EA workshop slides 2023](https://emailarchivesgrant.library.illinois.edu/wp/wp-content/uploads/2023/06/Workshop-Using-ePADD-to-Process-Email-Archives.pdf)
- ePADD appraisal module: donor flags "Do Not Transfer" or restricted; exports exclude flagged messages; archivists then process. — [The Signal 2014](https://blogs.loc.gov/thesignal/2014/10/the-epadd-team-on-processing-and-accessing-email-archives/)
- Mailbag 1.0 (Albany; funded by Illinois EA:BCC): extension of BagIt (RFC 8493); multiple versions of a message (redactions/restrictions) go in separate mailbags; bag-info fields map to PREMIS object/event fields. — [Mailbag Specification 1.0](https://archives.albany.edu/mailbag/spec/)
- WARC revisit, identical-payload-digest profile: requires WARC-Payload-Digest; recommends WARC-Refers-To (record ID), WARC-Refers-To-Target-URI and WARC-Refers-To-Date; discourages file-offset pointers as "potentially very brittle"; spatial duplicates unaddressed. — [IIPC spec 1.0](https://iipc.github.io/warc-specifications/specifications/warc-deduplication/recording-arbitrary-duplicates-1.0)
- warcprox computes a payload digest (typically SHA-1) during fetch, checks a dedup database, writes a revisit on a hit; warcrefs post-processes a hash manifest to convert copies (count > 1) into revisits. Archive-It dedups at seed level. — [warcprox summary](https://awesome.ecosyste.ms/projects/github.com%2Finternetarchive%2Fwarcprox); [Archive-It support](https://support.archive-it.org/hc/en-us/articles/208001016)
- Browsertrix (2026): Collection-scoped dedup index; org-wide default dedup source; "deduplicated crawls depend on other archived items"; bundling dependencies for self-contained export "may cancel the storage savings"; index can be purged and rebuilt. — [Webrecorder blog 2026-04-09](https://webrecorder.net/blog/2026-04-09-deduplication)

### Inferences
- The WARC-Refers-To pattern maps directly onto an archival dedup report: each excluded copy should reference the kept copy by stable identifier (hash + accession/carrier + path), not by filesystem offset or temporary mount path.
- The Browsertrix "dependency" warning translates to archives: once a DIP omits duplicates, the DIP depends on the retained copy's package; the report must make that dependency explicit.
- ePADD's inconsistent counts show that a dedup tool must define its counting units (files vs bytes vs groups vs groups-across-carriers) and report them identically everywhere.

### Gaps
- ePADD's exact matching criterion (Message-ID vs content hash) was not found in public documentation.

## KQ8. Requirements for an appraisal-stage dedup tool

### Takeaway
Synthesizing the sources: the tool must be read-only against source media and images, hash-based with strong algorithms and multiple-algorithm support, operate on both disk images and logical directories, compare across carriers and accessions, aggregate at carrier/directory level, never delete, propose a documented keep-rule with human override, and emit machine-readable (CSV/JSON) and narrative outputs that drop directly into DACS Appraisal/Processing Information notes, the accession record, and a PREMIS-style event log.

### Cited Findings (requirement -> grounding)
- Read-only / never modify source: UC Guidelines — "Do not rename or re-arrange digital files during appraisal"; DPF PII task notes opening "(write-blocked) files"; Galloway — disk image captured "without creating any metadata recording the fact of capture"; NC State imaged drives "instead of the physical media... protecting the integrity of the physical media." — [UC v4](https://escholarship.org/uc/item/4b81g01z); [DPF](https://ecommons.cornell.edu/handle/1813/57659); [Galloway](https://pages.ischool.utexas.edu/galloway/spring2018/INF392K2018/OrderAsReceivedAERI-1.pdf); [poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)
- Hash choice: DPF Baseline — "Create checksum of files using one or more algorithm (MD5, SHA-1, SHA-256)"; Princeton — MD5 and SHA-1/SHA-256 most used; Archivematica defaults sha256 (sha512 if unset); WARC uses SHA-1 payload digests; one email archiver notes SHA-256 makes false matches "very unlikely." — [DPF](https://ecommons.cornell.edu/handle/1813/57659); [Princeton](https://universityarchives.princeton.edu/2014/10/the-university-archives-and-its-focus-on-fixity); [Archivematica issue 918](https://github.com/artefactual/archivematica/issues/918); [IIPC](https://iipc.github.io/warc-specifications/specifications/warc-deduplication/recording-arbitrary-duplicates-1.0)
- Disk images and logical files: Brunnhilde runs "against a directory or disk image"; fiwalk/DFXML provides per-file hashes inside images; Beinecke and Galloway favour bit-level capture. — [Bentley bitcurator-intro](https://bentley-historical-library.github.io/bitcurator-intro/04-reporting.html); [BitCurator walkthrough](https://bitcurator.github.io/documentation/BitCurator%20Walkthrough/BitCurator%20Walkthrough)
- Cross-carrier / cross-accession comparison: NC State duplicates were "of the photos on other drives"; PDT&C 2024 found cross-disc comparison "not in archivists' toolkits"; Kentucky needed duplicates "across multiple servers at once"; Browsertrix dedups against a persistent collection index. — [poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG); [PDT&C](https://www.degruyterbrill.com/document/doi/10.1515/pdtc-2024-0042/html); [SAA ERS 2025](https://saaers.wordpress.com/2025/11/05/looking-for-trouble-born-digital-reappraisal); [Webrecorder](https://webrecorder.net/blog/2026-04-09-deduplication)
- Carrier/directory-level aggregation: UC — appraise "carriers, disk-images, and directories, not individual files"; LoC removes at media/folder level. — [UC v4](https://escholarship.org/uc/item/4b81g01z); [LoC](https://findingaids.loc.gov/exist_collections/ead3pdf/mss/2023/MSS-Processing-History-Note.pdf)
- Human-in-the-loop: DPF — "Assess contextual and information value... to determine if duplicates should be weeded" (Moderate); GWU — "Duplicate files were reviewed by the practitioner and removed"; Scholars Portal — institutions should define keep/discard policy. — [DPF](https://ecommons.cornell.edu/handle/1813/57659); [GWU](https://gwu-libraries.github.io/DigitalServicesDocs/borndigital/bestpractice); [Scholars Portal](https://learn.scholarsportal.info/?p=4795)
- Pointer records instead of deletion: jdupes symlinks + "report of where link pointed... packaged with the digital files"; WARC-Refers-To; Thompson 2022 "metadata pointers." — [poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG); [IIPC](https://iipc.github.io/warc-specifications/specifications/warc-deduplication/recording-arbitrary-duplicates-1.0); [SAA Dictionary](https://dictionary.archivists.org/entry/deduplication.html)
- Correct size accounting: Brunnhilde counted symlinks at target size; NC State added `du -sh`. — [poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)
- Consistent counts across report views: ePADD summary vs per-file report discrepancies. — [Rylands](https://rylandscollections.com/2021/11/17/palladium-project-development-work-on-epadd/)
- Reporting formats: Brunnhilde emits HTML report + `csv_reports/` incl. duplicates CSV + full siegfried.csv; TNA requires DROID CSV (checksum, format, size, modified) as the appraisal deliverable; Buffalo keeps a DROID manifest "available on request." — [Bentley bitcurator-intro](https://bentley-historical-library.github.io/bitcurator-intro/04-reporting.html); [TNA](https://www.nationalarchives.gov.uk/information-management/manage-information/digital-records-transfer/digital-transfer-steps/steps-1-and-2-appraisal-and-selection/); [UB](https://research.lib.buffalo.edu/processing/digital-materials)
- Finding-aid/ArchivesSpace integration: DPF Baseline — note deletions in Processing Information and/or Conditions Governing Access, collection management system, collection file; Buffalo splits general statement (Appraisal Information) from technical detail (Processing Information) and counts preserved files in Extent; GWU records in ArchivesSpace accession record and bag-info; UC cites DACS Principle 6 for transparency. — [DPF](https://ecommons.cornell.edu/handle/1813/57659); [UB](https://research.lib.buffalo.edu/processing/digital-materials); [GWU](https://gwu-libraries.github.io/DigitalServicesDocs/borndigital/bestpractice); [UC v4](https://escholarship.org/uc/item/4b81g01z)
- Event logging: PREMIS deletion/deaccession/appraisal concepts; APTrust logs who requested and when, retaining the record after deletion; Mailbag maps bag metadata to PREMIS event fields. — [Lyrasis PREMIS events](https://wiki.lyrasis.org/x/o5IOB); [APTrust](https://docs.aptrust.org/user-guide/registry/events/); [Mailbag](https://archives.albany.edu/mailbag/spec/)
- Container awareness (email/zip/disk image): ePADD parser bug; Mailbag multiple representations; WARC spatial-duplicate limitation. — [Rylands](https://rylandscollections.com/2021/11/17/palladium-project-development-work-on-epadd/); [Mailbag](https://archives.albany.edu/mailbag/spec/); [IIPC](https://iipc.github.io/warc-specifications/specifications/warc-deduplication/recording-arbitrary-duplicates-1.0)
- Hybrid (analog) duplication flagging: UC and Scholars Portal ask for analog duplication to be identified; not automatable but the report should have a field for it. — [UC v4](https://escholarship.org/uc/item/4b81g01z); [Scholars Portal](https://learn.scholarsportal.info/?p=4795)

### Inferences — consolidated requirement list
1. Operate only on write-blocked media, forensic images, or read-only mounts; produce no writes to source; verify by re-hashing the image/manifest before and after a run.
2. Compute SHA-256 (configurable; optionally also MD5/SHA-1 for reconciliation with legacy DROID/fiwalk manifests); import existing DFXML/Siegfried/DROID CSVs rather than re-hashing when available.
3. Accept inputs: raw/E01/ISO disk images (via fiwalk/DFXML or mounted), logical directories, bags, MBOX/EML/PST (message-level and attachment-level hashing), ZIP/TAR (member-level hashing); tag each object with carrier ID and container path.
4. Persist a per-collection hash index so later accessions and reappraisals can be compared (cross-accession, cross-carrier).
5. Report at three levels: group (hash -> all members with carrier, path, size, fs timestamps, embedded timestamps), directory/carrier containment matrix (e.g., % of carrier B's bytes/files present on carrier A), and summary (unique vs duplicate counts and bytes, consistent definitions used in every view; sizes exclude links).
6. Classify matches: exact; exact-in-different-container; candidate equivalents (same name/size/date, different hash) flagged but never auto-grouped; versions/drafts never flagged as duplicates.
7. Propose a kept copy via a transparent, configurable rule (default: earliest carrier / most-structured path / preferred format), show the rule, require archivist confirmation; allow "keep all" per group and a "never dedup" flag per series/carrier (e.g., forensic or evidential collections).
8. Never delete. Output an exclusion list for SIP/DIP builders and a pointer map (excluded copy -> retained copy by hash + carrier + path), analogous to WARC-Refers-To / jdupes link report.
9. Outputs: CSV + JSON (machine), HTML/PDF (human), plus prose snippets pre-formatted for DACS Appraisal Information (general statement), Processing Information (technical detail incl. algorithm, tool version, date, counts), and Extent (preserved-file count); optionally push notes to ArchivesSpace accession/resource records via API.
10. Emit an event log per run (agent, tool version, algorithm, date/time, inputs by hash, rule applied, groups affected, outcome) mappable to PREMIS `deletion`/`deaccession` or a local "deduplication decision" event, and include bag-info-ready key/values.
11. Provide a hybrid-collection field for archivist-entered analog duplication notes, and a free-text rationale per decision.

### Gaps
- No published institutional requirements document for a dedup tool was found; the list above is synthesized from manuals, case studies and analogous systems rather than quoted from a single source.
- No source documented ArchivesSpace API integration for writing appraisal/dedup notes; this is inferred from the DPF/Buffalo/GWU documentation targets.
