# BitCurator Environment and Consortium Ecosystem: Deduplication and Hashing Tools

Research date: 2026-11-01. Scope: what the BitCurator Environment (current release 5.1.0) and the wider BitCurator Consortium ecosystem offer for finding exact or near-duplicate files, how each tool is used for dedup in practice, and current maintenance status. Package-list facts were verified directly against the `bitcurator-salt` repository (the installer's Salt states) and GitHub API metadata, not just documentation pages. Where documentation and the actual package list disagree, that is called out.

## Q1. Which hashing and duplicate-detection tools ship in the current BitCurator Environment?

### Takeaway
BitCurator 5.1.0 (July 2025, Ubuntu 24.04/22.04) ships general hashing tools (hashdeep/md5deep, hashrat, GtkHash, ssdeep, Siegfried's `-hash`, fiwalk/TSK DFXML with MD5+SHA1) and exactly one tool that produces a duplicates *report* out of the box: Brunnhilde (via Siegfried hashes). No dedicated dedup utility (fdupes, jdupes, rdfind, FSlint) and no sdhash is installed by the 5.1.0 Salt states, despite the project's Tools documentation page still listing sdhash and the BitCurator Reporting Tool.

### Inferences
- For a university library building a dedup tool, the components in BitCurator that are both installed and scriptable are: Siegfried (`sf -csv -hash sha256 dir`), fiwalk (DFXML with MD5/SHA1 per file), hashdeep/md5deep (recursive hash lists in a stable text format), hashrat, ssdeep (fuzzy/near-duplicate), and Brunnhilde's SQLite-backed duplicates query. Everything else is GUI-oriented or absent.
- The `docs/Tools.md` page is stale relative to the 5.1.0 installer (it lists sdhash, Disk Image Access and the Reporting Tool, none of which have Salt states); treat it as a historical inventory.
- hashdeep is effectively frozen upstream (no release since 2014) but remains packaged in Ubuntu and therefore installs cleanly; ssdeep likewise has had no release since 2017 though the repo shows activity.

## Q2. How does BitCurator Reports / the BitCurator Reporting Tool surface duplicates?

### Takeaway
The BitCurator Reporting Tool (Python scripts `generate_report.py`, `identify_filenames.py`, `bc_genrep_premis.py`, historically in `bitcurator-distro-tools`/bctools) never had a dedicated "duplicates" or "identical files" report. Its contribution to dedup was indirect: converting fiwalk DFXML into `fiwalk-output.xml.xlsx`, which carries per-file MD5 and SHA1 columns that archivists sorted/filtered to find duplicates. The GUI tool appears to have been dropped from the 5.x environment; only `identify_filenames.py` survives in `bitcurator-python-tools`.

### Cited Findings
- Reporting Tool "Run All" inputs: Image File, Bulk Extractor Feature Directory, Output Directory, optional Config File. Outputs: `features/` (annotated features), `bc_format_bargraph.pdf`, `bulk_extractor_report.pdf`, `fiwalk_deleted_files.pdf`, `fiwalk-output.xml.xlsx` ("DFXML file system metadata converted to an Excel spreadsheet"), `fiwalk_report.pdf`, `format_table.pdf`, `premis.xml`. The page "does not mention MD5 or SHA1 hashes, duplicate files, or identical files" — [Creating Disk Image Reports using the BitCurator Reporting Tool](https://bitcurator.github.io/documentation/All%20Step-by-Step%20Guides/Forensics%20and%20Reporting%20Guides/Creating%20Disk%20Image%20Reports%20using%20the%20BitCurator%20Reporting%20Tool)
- The "Forensic Reports" guide lists the same eight outputs; it does not mention hashes, duplicates, or spreadsheet columns — [Forensic Reports.md](https://github.com/BitCurator/documentation/blob/main/docs/All%20Step-by-Step%20Guides/Forensics%20and%20Reporting%20Guides/Forensic%20Reports.md)
- Practitioner account (Jess Conway, UCL, April 27, 2020) of the xlsx output: "The spreadsheet also includes MD5 and SHA1 hash values for each individual file" and "if two hash values are the same, the files themselves are identical!" — the author describes this as the method for spotting duplicates, but did not report actually finding any — [A Little Bit Of Curation: 4. Running Reports](https://reflect.ucl.ac.uk/inst0045-1920-jess-conway/?p=477)
- Command-line path (Kam Woods, Dec 2016): annotate bulk_extractor output with `identify_filenames.py` (then in `/usr/share/dfxml/python`), run `generate_report.py` with "the fiwalk XML, the annotated feature directory, and a new output directory", then `python3 bc_genrep_premis.py` with `--dfxmlfile`, `--bulk_extractor`, `--Allreports`, `--premis_file`. Woods said these scripts "have not been updated in a very long time" and "could definitely use a rewrite" — [bitcurator-users thread: Generating PREMIS xml file via command line](https://groups.google.com/d/topic/bitcurator-users/Ku7e4WsdCys)
- The `bitcurator-distro-tools` repository referenced in that thread returns 404 on GitHub (2026-11-01); the BitCurator org has no repo named `bitcurator-reports` or `bitcurator-reporting` (`gh search repos` returned empty) — [BitCurator org](https://github.com/BitCurator)
- `bitcurator-python-tools` (MIT, last commit 2024-11-20) is "an installable pip package for specific Python 3 scripts used in the BitCurator Environment" and is "a dependency of bitcurator-salt". It contains only `build_stoplist.py`, `bulk_diff.py`, `bulk_extractor_reader.py`, `cda_tool.py`, `cda2_tool.py`, `identify_filenames.py`, `post_process_exif.py` — no `generate_report.py` or PREMIS generator — [BitCurator/bitcurator-python-tools](https://github.com/BitCurator/bitcurator-python-tools)
- `identify_filenames.py` (the surviving script) reads fiwalk DFXML, uses `fi.md5()` per fileobject, writes a `Filename\tMD5` header and offers a flag "Do not calculate MD5 or SHA1 when running fiwalk" — i.e. it maps bulk_extractor feature offsets to filenames plus MD5, not a dedup function — [identify_filenames.py](https://github.com/BitCurator/bitcurator-python-tools/blob/main/bitcurator_python_tools/identify_filenames.py)

- A 2014 iPRES demonstration described BitCurator features including "identification of duplicate files, generation of PREMIS metadata and initial steps toward redaction" (abstract-level only; mechanism not described) — [Phaidra (Univ. Vienna) iPRES 2014 record](https://phaidra.univie.ac.at/o:378717)
- CurateGEAR 2014 slides (Woods) are reported to note that BitCurator's GUI "generates MD5 and SHA1 hashes for per-partition file items" (search-snippet level; PDF not text-extractable in this session) — [woods-curategear2014.pdf](https://ils.unc.edu/digccurr/curategear2014-talks/woods-curategear2014.pdf)

### Inferences
- "BitCurator Reports" dedup capability = the DFXML-to-Excel conversion exposing MD5/SHA1 columns; the "identification of duplicate files" claimed in 2014 marketing most plausibly refers to this plus FSlint (both now gone from the default install).

## Q3. What do Brunnhilde's duplicate reports contain and how are they generated?

### Takeaway
Brunnhilde runs Siegfried with `-csv -hash <algo>` (MD5 by default; sha1/sha256/sha512 optional), loads the CSV into SQLite, and emits `duplicates.csv` using a `GROUP BY hash HAVING COUNT(hash) > 1 AND COUNT(DISTINCT filename) > 1` query that excludes zero-byte files; the HTML report shows a "Duplicates: N (of M distinct files)" summary. It is the only turnkey duplicates report in the current environment, but it has had no release since 1.9.6 (March 2023).

### Cited Findings
- Brunnhilde is a "Siegfried-based characterization tool for directories and disk images"; MIT license; created by Tessa Walsh / Canadian Centre for Architecture, "initially developed in 2016-2017"; "Brunnhilde uses the md5 hash algorithm by default. Other options are sha1, sha256, sha512, or none" (`--hash HASH`); with `--hash none` outputs lack "information about duplicate files in the source" — [tw4l/brunnhilde README](https://github.com/tw4l/brunnhilde)
- Siegfried invocation in source: `'sf -csv -hash %s "%s" > "%s"' % (hash_type, source_dir, sf_file)`; `_determine_hash_type` "Defaults to md5 if no or invalid user input"; accepted sha1, sha256, sha512 — [brunnhilde.py](https://raw.githubusercontent.com/tw4l/brunnhilde/main/brunnhilde.py)
- Duplicates SQL: `SELECT * FROM siegfried WHERE hash IN (SELECT hash FROM siegfried WHERE filesize<>'0' GROUP BY hash HAVING COUNT(hash) > 1 AND COUNT(DISTINCT filename) > 1) ORDER BY hash;` — zero-byte files excluded; a hash group counts only if it spans more than one filename — [brunnhilde.py](https://raw.githubusercontent.com/tw4l/brunnhilde/main/brunnhilde.py)
- HTML summary math: total files `SELECT COUNT(*) from siegfried`; distinct files `SELECT COUNT(DISTINCT hash) from siegfried WHERE filesize<>'0'`; `duplicate_copies = all_dupes - distinct_dupes`; report shows "Duplicates:" with duplicate_copies "(of {distinct_dupes} distinct files)" — [brunnhilde.py](https://raw.githubusercontent.com/tw4l/brunnhilde/main/brunnhilde.py)
- CSV outputs in `csv_reports/`: `formats.csv`, `formatVersions.csv`, `mimetypes.csv`, `years.csv`, `unidentified.csv`, `warnings.csv`, `errors.csv`, `duplicates.csv` (only when hashing enabled); plus `siegfried.csv` (full Siegfried output); `report.html` includes provenance, aggregate stats and detailed duplicates table — [tw4l/brunnhilde README](https://github.com/tw4l/brunnhilde) and [brunnhilde.py](https://raw.githubusercontent.com/tw4l/brunnhilde/main/brunnhilde.py)
- `duplicates.csv` rows are full Siegfried CSV rows (filename, filesize, modified, errors, hash, namespace, id, format, version, mime, basis, warning) because the query is `SELECT *` from the imported siegfried table — [brunnhilde.py](https://raw.githubusercontent.com/tw4l/brunnhilde/main/brunnhilde.py)
- Disk-image handling: "Brunnhilde uses SleuthKit's tsk_recover to export files from a disk image into a 'carved files' directory"; HFSExplorer for HFS images; ClamAV scan by default; bulk_extractor optional (`-b`); Siegfried must use PRONOM signatures only ("It does not support MIME-Info or FDD signatures") — [tw4l/brunnhilde README](https://github.com/tw4l/brunnhilde)
- Processing of a disk image also "generat[es] a DFXML report with fiwalk" alongside tsk_recover carving, virus scan and Siegfried; BitCurator launches it from Applications > Forensics and Reporting > Brunnhilde; example `brunnhilde.py -d --tsk_fstype fat --tsk_imgtype ewf SampleData.E01 TestAnalysis` — [Analyzing a Disk Image with Brunnhilde (BitCurator docs)](https://github.com/BitCurator/documentation/blob/main/docs/All%20Step-by-Step%20Guides/Forensics%20and%20Reporting%20Guides/Analyzing%20a%20Disk%20Image%20with%20Brunnhilde.md)
- Bentley Historical Library teaching material: Brunnhilde `report.html` includes "number of unique vs. duplicate files" and `csv_reports` includes a CSV of duplicate files; the lesson gives no recommendation on keeping or removing duplicates — [Bentley bitcurator-intro, 04 Reporting](https://bentley-historical-library.github.io/bitcurator-intro/04-reporting.html)
- Release/maintenance: v1.9.6 released 2023-03-31 (v1.9.5 2022-08-17); last code commits Oct 2023 ("Remove Python 2.7 from CI", "Fix sf csv import to work with sf 1.10"); repo pushed 2025-11-28; not archived; 14 open issues — [tw4l/brunnhilde](https://github.com/tw4l/brunnhilde) (GitHub API 2026-11-01)
- Added to BitCurator in 1.8.0 (Mar 17, 2017): "Launchers for Timothy Ryan Walsh's Brunnhilde and Richard Lehane's Siegfried" "now included by default" — [Release History](https://github.com/BitCurator/bitcurator-distro/wiki/Release-History)
- Practical caveat from NC State (Kate Phillips): "the Brunnhilde tool would count symbolic links as having the same size as the file they link to – rather than the much smaller size of the link itself", distorting post-dedup size estimates — [Phillips, NC State poster PDF](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)

### Inferences
- Because Brunnhilde stores everything in a SQLite table named `siegfried`, a dedup tool can reuse Brunnhilde's database (or simply Siegfried's CSV) and run its own queries; the duplicates logic is ~3 lines of SQL and trivially reproducible without Brunnhilde.
- MD5 default is adequate for exact-duplicate grouping but a library building a tool should prefer sha256 (`--hash sha256`) for interoperability with fixity records; Siegfried supports it natively.
- Brunnhilde's exclusion of zero-byte files and requirement for distinct filenames are sensible defaults but mean hardlinked/identically named copies in different directories are included while same-path re-scans are not.

### Gaps
- No CHANGELOG file exists in the repo (404), so the per-version changes beyond the commits list were not verified.
- Brunnhilde's handling of symlinks (whether Siegfried follows them) was not verified from source.

## Q4. How is DFXML used for cross-media duplicate detection?

### Takeaway
DFXML (produced by fiwalk/TSK and by `walk_to_dfxml.py` for directories) records per-file `hashdigest` values (MD5 and SHA1 from fiwalk), so duplicates within or across images can be found by grouping fileobjects on hash. The `dfxml_python` library ships `dedup.py`, `dfxinfo.py --files`, `idifference.py`/`make_differential_dfxml.py`, `cat_fileobjects.py` and `nsrl_rds.py` for this, but several of these scripts are broken or unmaintained in the current tree; the library itself is active (commits May 2026, NIST/NPS public domain + LGPL).

### Cited Findings
- fiwalk "is part of The Sleuth Kit's collection of digital forensics tools and is used to produce a DFXML (Digital Forensics XML) report on the contents of a disk image" — [BitCurator Tools.md](https://github.com/BitCurator/documentation/blob/main/docs/Tools.md); fiwalk's DFXML records "the offset of every file, and an md5 checksum, all stored in a standardized XML structure" — [Smithsonian TBMA: comparing fiwalk reports (search snippet; page returned 403)](https://www.si.edu/tbma/resource/comparing-fiwalk-reports)
- fiwalk output includes MD5 and SHA1 per file (as shown in the Reporting Tool's xlsx conversion) — [UCL blog](https://reflect.ucl.ac.uk/inst0045-1920-jess-conway/?p=477); `identify_filenames.py` has an option "Do not calculate MD5 or SHA1 when running fiwalk" confirming both are computed by default — [identify_filenames.py](https://github.com/BitCurator/bitcurator-python-tools/blob/main/bitcurator_python_tools/identify_filenames.py)
- BitCurator ships DFXML reference material in its Documentation and Help menu: `DFXML tag library v3.xlsx`, `dfxml.dtd`, `dfxml.xsd` (under "DFXML Guides/Legacy") — [bitcurator-salt theme/documentation](https://github.com/BitCurator/bitcurator-salt/tree/main/bitcurator/theme/documentation)
- `dfxml_python` ("Digital Forensics XML packages in Python"): standalone tools live in `dfxml/bin/` and are added to `$PATH` on install; license: "a work of the Naval Postgraduate School (NPS) and the National Institute of Standards and Technology (NIST)... not subject to copyright law", CC0 1.0 for US-government work, "Contributions by non-US government entities herein are covered under the LGPL"; repo pushed 2026-05-08 (commits "Add type annotations", "Run pre-commit autoupdate"); no GitHub releases; last dated release note 2018-07-22 signed by Simson Garfinkel May 6, 2021 — [dfxml-working-group/dfxml_python](https://github.com/dfxml-working-group/dfxml_python) and [LICENSE.md](https://raw.githubusercontent.com/dfxml-working-group/dfxml_python/main/LICENSE.md)
- `dfxml/bin` tools relevant to dedup: `walk_to_dfxml.py` ("Fully walks the current working directory and records all files encountered"), `make_differential_dfxml.py` ("Produces a DFXML file showing file system changes between two input DFXML files"), `idifference.py` ("Generates a report on differences between two disk images"), `cat_fileobjects.py` ("Prints a new DFXML of all fileobjects in an input DFXML file to stdout"), `dfxinfo.py` ("Prints a summary of a DFXML file, including all files, duplicates, and file types"), `hash_sectors.py` (sector hashes), `iverify.py`, `Extractor.py`; listed under "Work needed": `dfxml_tool.py`, `idifference2.py`, `nsrl_rds.py`, `validate_dfxml.py`; also present without description: `dedup.py`, `summarize_differential_dfxml.py` — [dfxml/bin](https://github.com/dfxml-working-group/dfxml_python/tree/main/dfxml/bin)
- `dedup.py`: reads one DFXML file, groups filenames by MD5 via `self.seen[fi.md5()].append(fi.filename())`; prints `Total files / total MD5s processed / Unique MD5s`; `--dups` prints `dups: <name> <count>`, `--distinct` prints unique files, `--prefix` filters paths; despite its header "optionally remove duplicates" it never deletes; malformed XML errors are silently swallowed — [dedup.py source](https://raw.githubusercontent.com/dfxml-working-group/dfxml_python/main/dfxml/bin/dedup.py)
- `dfxinfo.py` (v0.2.0) `--files` mode: MD5 only; skips virtual files, keeps regular files; groups via `fi_by_md5`; prints groups with >1 member sorted by size with "Total duplicate bytes"; but as written has a `TypeError` (`histogram()` called on a module) and a `NameError` (`fn` undefined) in `--files` mode, so it will not run without fixes — [dfxinfo.py source](https://raw.githubusercontent.com/dfxml-working-group/dfxml_python/main/dfxml/bin/dfxinfo.py)
- Smithsonian Time-Based Media workflow uses a DFXML comparison script that sorts differences into "New Files" and "Deleted Files" (idifference-style) — differencing between two images rather than within-image dedup — [Smithsonian TBMA (search snippet)](https://tbma.si.edu/resource/comparing-fiwalk-reports)
- DFXML schema: `dfxml-working-group/dfxml_schema` ("XML Schema for Digital Forensics XML"), tags v1.1.0, v1.1.1, v2.0.0-beta.0; pushed 2025-02-07 — [dfxml_schema](https://github.com/dfxml-working-group/dfxml_schema)
- Known-file filtering: `nsrllookup` is built from source in BitCurator ("Query tool to check for a matching MD5 hash in the National Software Reference Library Reference Data Set") — [Tools.md](https://github.com/BitCurator/documentation/blob/main/docs/Tools.md), [bitcurator-salt tools/nsrllookup.sls](https://github.com/BitCurator/bitcurator-salt/tree/main/bitcurator/tools)
- Creighton Barrett (Dalhousie), lightning talk at the 2017 BitCurator Users Forum, Northwestern University, April 28, 2017: "Tools for identifying duplicate files and known software files" — overview of FSlint, Forensic Toolkit (FTK), and the NSRL Reference Data Set (PDF and PPTX available) — [Dalhousie repository record](https://dal.scholaris.ca/items/b1daa03c-3fa5-4739-bc68-00b95c0e669c/full)

### Inferences
- Cross-media dedup via DFXML in practice means: run `fiwalk -X out.xml image.E01` (or `walk_to_dfxml.py` for loose files) on each carrier, then parse `<fileobject>/<hashdigest type="md5|sha1">` across all DFXML files with the `dfxml` Python library (`dfxml.objects` iterparse) and group by hash. None of the shipped scripts does multi-file cross-image dedup out of the box; `dedup.py` and `dfxinfo.py` are single-file and the latter is broken.
- Because the DFXML library is public domain/LGPL and actively maintained (2026 commits) while the dedup scripts are not, a new tool should import the library and write its own grouping logic rather than depend on `dedup.py`/`dfxinfo.py`.
- fiwalk DFXML + nsrllookup gives a BitCurator-native "known file" filter (removing OS/application files) that complements within-collection dedup.

### Gaps
- Exact fiwalk flags controlling hash calculation and the DFXML `hashdigest` element structure were not fetched from primary docs this session (the Smithsonian pages returned 403; fiwalk man page not fetched).
- Whether `idifference.py` currently runs under Python 3 in the main branch was not tested.

## Q5. Official documentation, forum threads, workshop materials describing deduplication workflows; recommendations and caveats

### Takeaway
BitCurator's own documentation on deduplication is thin: a legacy FSlint guide (delete-oriented), the Reporting Tool guides (hash columns, no dedup discussion), Brunnhilde guides (report only). The clearest practitioner workflow is NC State's (OSSArcFlow-era) approach: identify duplicates after arrangement with jdupes, replace copies with symbolic links, and package a link-target report with the processing documentation — a "flag and record, don't silently delete" pattern. No BitCurator Consortium webinar specifically on deduplication was found.

### Cited Findings
- FSlint guide (legacy): "The BitCurator environment incorporates FSlint to help you to rapidly scan file directory contents to identify duplicate files, and delete selected items from those duplicates"; steps: open from Forensics Tools, add directories, optional recursive, run, select duplicates (Ctrl-click) and delete — [FSlint guide](https://bitcurator.github.io/documentation/All%20Step-by-Step%20Guides/Forensics%20and%20Reporting%20Guides/FSlint)
- Historical project messaging listed "Locate and remove duplicate files: Know what files to keep and what can be discarded" as a BitCurator use case (Educopia Confluence BC wiki; host no longer resolves as of 2026-11-01) — [confluence.educopia.org/display/BC (search snippet; DNS failure on fetch)](https://confluence.educopia.org/display/BC)
- NC State Special Collections (Kate Phillips), John Mark Hall Photographs Collection (8 TB, 7 hard drives): standard born-digital workflow "already includes - Finding total size of package - Itemizing file types - Determining whether there are duplicates"; "After transferring and arranging files, we used the tool Jdupes to create symbolic links for each duplicate and generate a report of where link pointed. This was placed with other processing reports to be packaged with the digital files"; they added `du -sh` to size packages correctly with symlinks; disk-imaged each drive first; result "an estimated 41% reduction of total storage size for images" with a 15% error margin (low end 26%); recorded arrangement/processing steps as extra finding-aid metadata; caveat: Brunnhilde counted symlinks at target size — [Phillips poster PDF](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)
- OSSArcFlow (IMLS-funded, Educopia/UNC, 2017-2019) studied born-digital workflows across BitCurator, ArchivesSpace and Archivematica; the NC State dedup case is reported in that context, but no OSSArcFlow document describing a canonical dedup step was found — [OSSArcFlow at Kansas Historical Society (CoSA)](https://www.statearchivists.org/blogs/cosanews1/2018/07/10/ossarcflow-at-the-kansas-historical-society); [Pasig-discuss OSSArcFlow announcement](https://asist-archive.ischool.illinois.edu/pasig-discuss/2017-September/000606.html)
- Barrett 2017 BCUF lightning talk covers FSlint, FTK and NSRL RDS for "identifying duplicate files and known software files" (abstract only; PDF not text-extractable in this session) — [Dalhousie record](https://dal.scholaris.ca/items/b1daa03c-3fa5-4739-bc68-00b95c0e669c/full)
- Bentley Historical Library's BitCurator intro: DFXML "includes all filesystem data, checksums for integrity" and "could be good for checking fixity"; Brunnhilde reports aid "triage, arrangement, and description"; no recommendation on removing duplicates — [Bentley 04 Reporting](https://bentley-historical-library.github.io/bitcurator-intro/04-reporting.html)
- UCL student practitioner: hash columns in the Reporting Tool xlsx "allow you to quickly search for duplicates files" — [UCL blog](https://reflect.ucl.ac.uk/inst0045-1920-jess-conway/?p=477)
- jdupes documentation (not a BitCurator source) warns that metadata changes (ID3 tags, EXIF) make a file "no longer identical to the original" even if it looks/sounds the same, i.e. exact-hash dedup misses content-identical variants — [LinuxLinks jdupes summary](https://linuxlinks.com/jdupes-powerful-duplicate-file-finder-enhanced-fork-fdupes/)
- SAA Dictionary of Archives Terminology: "deduplication of those files deemed to be unnecessary should be part of the appraisal process" — [SAA Dictionary: deduplication](https://dictionary.archivists.org/entry/deduplication.html)
- BitCurator Users Forum mailing list: a `site:` search for duplicate-file threads returned nothing from the bitcurator-users group; the only relevant thread found concerned command-line PREMIS/report generation — [bitcurator-users PREMIS thread](https://groups.google.com/d/topic/bitcurator-users/Ku7e4WsdCys)

### Inferences
- The BitCurator community's de facto recommendation (from NC State, Bentley, Barrett) is: compute hashes at ingest, *report* duplicates (Brunnhilde/DFXML), make the appraisal decision explicitly, and if removing copies, replace them with symlinks or a link-target report so original order and provenance remain reconstructible. BitCurator's own docs stop at "report" and never prescribe deletion except in the retired FSlint guide.
- Storage-driven dedup (NC State) and appraisal-driven dedup (SAA definition) are both present in the literature; BitCurator tooling supports the detection step for either but not the decision/record-keeping step, which is where a new library tool could add value (link-target reports, PREMIS events for removed copies).

### Gaps
- "From Bitstreams to Heritage" (Lee, Woods, Kirschenbaum, Chassanoff 2013) could not be text-extracted (PDF binary only); its specific guidance on duplicates/hashes is not cited here.
- No BitCurator Consortium webinar or BCUF session dedicated to deduplication was located; the Barrett 2017 lightning talk is the closest.
- Google Groups search for bitcurator-users dedup threads returned no hits; the archive may simply not be indexed.

## Q7. Summary matrix for tool builders (inputs/outputs, hashes, scriptability)

### Inferences
- A pipeline that mirrors BitCurator practice: image -> fiwalk DFXML (MD5+SHA1) or `sf -csv -hash sha256` on exported files -> load into SQLite -> Brunnhilde-style `GROUP BY hash HAVING COUNT>1` -> optional ssdeep pass for near-duplicates -> nsrllookup to drop known software files -> emit a link-target/duplicate report packaged with the SIP (NC State pattern). All pieces are CLI tools with text outputs and are present on a stock BitCurator 5.1.0 install except jdupes/fdupes.
