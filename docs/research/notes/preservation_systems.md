# Deduplication in digital preservation / archival processing systems and in storage tooling

Researcher scope: preservation platforms (Archivematica, Preservica, Rosetta, LIBNOVA, Arkivum, Islandora/Fedora, DSpace, Hyrax), Stanford SDR / SUL DLSS tooling, archival processing tools (Brunnhilde, DROID, Siegfried, FTK, Autopsy, AVP Fixity/Exactly, BagIt, TreeSize/dupeGuru), storage-level dedup (restic, Borg, Kopia, ZFS, object storage), and community guidance. ePADD and BitCurator are covered by other researchers; only integration points noted. Research conducted 2026-11-01. Where a source is a vendor marketing document or a third-party blog rather than product documentation, that is stated.

## Key question 1: Archivematica — fixity at transfer/ingest, duplicate detection, Appraisal tab, AIP behavior (2026 status)

### Takeaway
Archivematica (current release 1.18.0 as of the "archivematica-latest" docs in 2026) generates and verifies checksums at transfer and re-verifies at ingest, but has no built-in duplicate detection at any stage. The Appraisal tab (introduced in 1.6, 2017) offers format reports, tagging, bulk_extractor PII review, and arrangement, but nothing about duplicates, checksums, or hashes.

### Cited Findings
- The Appraisal tab (docs for Archivematica 1.18.0, "stable-current", © 2026 Artefactual) provides: a Backlog pane for searching transfers in backlog; tagging ("The tag is not recorded in any way and does not persist beyond the Appraisal tab"); an Objects report view listing format, PUID, format group, file count and size; visualizations of file counts or size per format; an "Examine contents" tab showing Bulk Extractor results (US SSNs, credit card numbers); a file preview tab; a File list pane with filenames, sizes, last-modified dates and tags; an ArchivesSpace pane; and an Arrangement pane for drag-and-drop SIP creation. "The page does not mention duplicate detection, duplicate display, checksums, or hashes." Deletion of individual files in the Appraisal tab is not described; it refers to the Backlog tab's delete-transfers instructions. — [Archivematica docs: Appraisal](https://www.archivematica.org/en/docs/archivematica-latest/user-manual/appraisal/appraisal/)
- Transfer-stage fixity: "Archivematica can verify MD5, SHA1, SHA256, and SHA512 checksums that were created outside of the system." Checksums are checked in the "Verify transfer checksums" microservice; if verification fails "the transfer will fail." Checksum files live in the transfer's `metadata` directory, named `checksum.md5`, `checksum.sha1`, `checksum.sha256`, or `checksum.sha512`. The page does not mention duplicate or identical files. — [Archivematica docs: Transfer](https://www.archivematica.org/en/docs/archivematica-latest/user-manual/transfer/transfer/)
- Archivematica assigns each file a unique identifier and a SHA-256 checksum during transfer processing; the checksum algorithm is set in the DashboardSettings table and defaults to 'sha256'; checksums are re-calculated at ingest and compared, creating a fixity-check PREMIS event. — summarised from search results citing MIT and Rockefeller Archive Center documentation: [Rockefeller Archive Center Archivematica docs](https://docs.rockarch.org/archivematica-local/transferAndSetup); [MIT wiki](https://wikis.mit.edu/confluence/x/cwM2CQ)
- The Appraisal tab was introduced in Archivematica 1.6 and developed with the Bentley Historical Library as part of the ArchivesSpace–Archivematica–DSpace integration project. — [DPC blog, Grygiel 2017](https://dpconline.org/blog/appraising-appraisal-and-picking-the-right-tool-for-the-job); [code4lib 2016](https://2016.code4lib.org/ArchivesSpaceArchivematicaDSpace-Workflow-Integration)
- Chris Grygiel (Digital Archivist, University of Leeds, DPC blog, updated 4 Sept 2017) judged the Appraisal tab useful for some deposits but "not a one-stop solution," preferring BitCurator's approach where archivists pick tools per deposit; he notes whole hard drives "might need de-duplication" and that appraisal tools help with "arrangement and de-duplication," but names no dedup feature in Archivematica. — [DPC blog](https://dpconline.org/blog/appraising-appraisal-and-picking-the-right-tool-for-the-job)
- A GitHub issue search in artefactual/archivematica for `is:issue duplicate files appraisal` returned "No results matched your search." — [GitHub issues search](https://github.com/artefactual/archivematica/issues?q=is%3Aissue+duplicate+files+appraisal)

### Inferences
- Because Archivematica stores a per-file SHA-256 (or other configured algorithm) in its database and METS, a dedup tool could consume Archivematica's METS/premis output or query the transfer backlog via the Storage Service API to compare hashes across transfers; Archivematica itself offers no such comparison or UI.
- The only "appraisal-stage" removal path Archivematica provides is deleting an entire transfer from backlog or excluding files during arrangement; there is no per-file "exclude duplicate" action.

### Gaps
- Could not verify whether any Artefactual wiki / GitHub issue (under other wording such as "dedup" or "identical files") requests duplicate detection; broader issue-tracker searches were not run.
- AIP-level behavior: no public documentation found describing whether two AIPs containing identical files are related in any way (they are not, as far as the docs show, but this is absence of evidence).

## Key question 2: Preservica, Rosetta, LIBNOVA/LIBSAFE, Arkivum, Islandora/Fedora, DSpace, Samvera/Hyrax — duplicate detection and fixity

### Takeaway
All of these platforms do checksum-based fixity at ingest and/or at rest, but only Preservica (vendor claim) and LIBNOVA (marketing claim) mention duplicate detection at all, and neither publishes how it works. Rosetta, DSpace, Hyrax/Fedora, and Arkivum show no public evidence of content-duplicate detection; their fixity services compare each file to its own stored checksum.

### Cited Findings
**Preservica**
- Preservica Professional edition service description (UK G-Cloud 15, document dated 2026-01-15) lists under ingest: "Workflow steps to perform quality assurance including: Virus checking; Checksum verification; Checking permitted file formats..." and "Ability to detect the ingest of duplicate files." Under Archival Storage: "Checksums calculated on storage for each copy", "Checksum re-calculated on access or at regular timed intervals on files at rest", and "Confirmation by Preservica Professional that when a file is accessed, it is the same as the file loaded in ingest using its own checksum (choose from MD5, SHA-1, SHA-256, SHA-512)." It also advertises an "extensive API library." The document does not say which hash is used for duplicate detection or what happens to duplicates. — [Preservica G-Cloud service definition PDF](https://assets.applytosupply.digitalmarketplace.service.gov.uk/g-cloud-15/documents/583399/255400856602027-service-definition-document-2026-01-15-1401.pdf)
- A 2014 AVPreserve vendor profile (dated) says ingest "generate[s] or validate[s] existing checksums" and the customer defines a preferred algorithm. — [AVPreserve Preservica profile](https://www.weareavp.com/wp-content/uploads/2014/07/AVPreserve_Preservica_profile.pdf)
- Searches of public Preservica documentation for a duplicate-detection setting found only the v6.3 "Guide to OPEX Ingest and Monitoring" (April 2021), which does not mention duplicates. — [Erfgoed Leiden OPEX guide](https://www.erfgoedleiden.nl/images/e-depot/Bijlage_1_Guide_to_OPEX_Ingest_and_Monitoring.pdf)

**Rosetta (Ex Libris)**
- "When does Rosetta run fixity?" (Rosetta 5): fixity runs in the validation stack during SIP processing; "In case fixity is not provided, the system will generate new fixity values (SHA1, MD5 and CRC32)"; if the SIP METS supplies fixity values they are compared; a permanent-repository validation task chain runs a checksum task; NFS and Amazon storage plugins "perform data integrity check" completing chain of custody through to permanent storage. No mention of duplicates. — [Ex Libris Knowledge Center](https://knowledge.exlibrisgroup.com/Rosetta/Knowledge_Articles/When_does_Rosetta_run_fixity%3F)
- Custom Fixity plug-in: "allows customers to run a fixity check in addition to the three fixity algorithms used by Rosetta (MD5, CRC32 and SHA-256)"; custom types (e.g. SHA-512) mapped via the `fixityType` code table; plug-in name mandatory on deposit (Rosetta 5.2–5.4 article). — [Custom Fixity](https://knowledge.exlibrisgroup.com/Rosetta/Product_Documentation/Rosetta_Configuration_Guide/010Plug-in_Management/014Custom_Fixity); [Deposit with custom fixity](https://knowledge.exlibrisgroup.com/Rosetta/Knowledge_Articles/Deposit_with_custom_fixity_requires_the_Plug-In_Name)
- The Rosetta Glossary contains no entries on fixity, checksum, duplicate or deduplication. — [Rosetta Glossary](https://knowledge.exlibrisgroup.com/Rosetta/Product_Documentation/Rosetta_Overview_Guide/Glossary)
- The only Ex Libris duplicate-check feature found is in Esploro (a different product) and is title-based, for the deposit workflow. — [Ex Libris Ideas: Esploro](https://ideas.exlibrisgroup.com/forums/929326-esploro/suggestions/51301432-duplicate-check-process-for-etd-workflow)
- Community caution: an Ideas post about recalculating ~22 million files from SHA-1 to SHA-256 recommends the AIP-update functionality or a custom validation plug-in; a commenter reported a task chain bug that created a new IE version per object. — [Ex Libris Ideas: Recalculate fixity SHA2](https://ideas.exlibrisgroup.com/forums/308179-rosetta/suggestions/31730143-recalculate-fixity-sha2-and-insert-into-rosetta)

**LIBNOVA LIBSAFE**
- LIBSAFE GO marketing brochure lists "Duplicate content detection" among advanced preservation features, without describing the mechanism or stage. — [LIBSAFE GO brochure](https://libnova.com/LIBSAFE_GO_by_LIBNOVA.pdf)
- The documented "Main ingestion checks" are eight rule types (1004 specific folder inside object; 1006 maximum object size; 1007 file name starts with object name; 2001 file extension; 2003 sequential file names; 2006 minimum file size; 3003 invalid characters; 3004 max filename length). "None covers duplicates, duplicate content, already-ingested objects, checksum/fixity verification." "Ingestion checks are programmed processes that will block an object from ingestion if it does not comply with certain set conditions." — [LIBSAFE Main ingestion checks](https://docs.libnova.com/libsafe-advanced-preservation-administrator-manual/preservation-configuration-basic-sections/ingestion-checks/main-ingestion-checks); [Ingestion checks](https://docs.libnova.com/libsafe-advanced-preservation-administrator-manual/preservation-configuration-basic-sections/ingestion-checks)
- The LIBSAFE FAQ notes ingests can be rejected when OS-generated files (Thumbs.db, .DS_Store) are present and that duplicate *versions* of already-ingested objects can be flagged (per search summary; not read in full). — [LIBSAFE FAQ: About ingestion and retrieval](https://docs.libnova.com/libsafe-advanced-preservation-administrator-manual/frequently-asked-questions-and-additional-considerations/about-ingestion-and-retrieval)

**Arkivum**
- No Arkivum product documentation on duplicate detection was found. A DPC Workflows webinar (Feb 2024) slide deck by Adam Harwood, University of Sussex Library, shows a customer workflow around Arkivum: tools include "Checksum by Corz", "Teracopy", "DROID collections profiling", "dupeGuru for file deduplication", "WinSCP for FTP transfer to Arkivum". Pre-ingest steps: "Scan collection with DROID → Export results → ... Identify duplicate files → Record to appraisal spreadsheet"; "MD5 checksums & directory trees generated pre-transfer"; "Appraisal Actions: Deduplication; Weeding unwanted files; Renaming; Reorganising; Format Migrations; Access versioning"; archivists make appraisal decisions, "Agreed upon actions are completed and documented"; then "Update MD5 Checksums; Run DROID on finished collection" and "Copy to Arkivum ingest location via FTP". — [DPC Workflows webinar: Ingest, Feb 2024 (PDF)](https://www.dpconline.org/docs/events-1/2024-events/workflow-webinars-1/3099-dpc-workflows-webinar-ingest-feb-2024/file)

**DSpace**
- DSpace 8.x Checksum Checker "can run to verify the checksum of every item within DSpace", typically from cron; reports "only on bitstreams for which the newly calculated checksum does not match the stored checksum"; results logged to `[dspace]/log/checker.log` and stored in the `checksum_history` table; `checker-emailer` sends reports. "The page does not address duplicate detection." — [DSpace 8.x docs: Validating CheckSums of Bitstreams](https://wiki.lyrasis.org/display/DSDOC8x/Validating+CheckSums+of+Bitstreams)

**Hyrax / Fedora / Islandora**
- Hyrax `FixityCheckJob` uses `Hyrax.config.fixity_service`, contacts Fedora, requests a check and stores results in a `ChecksumAuditLog` row. — [Hyrax FixityCheckJob (rubydoc)](https://www.rubydoc.info/gems/hyrax/FixityCheckJob)
- Emory's Hyrax-based code queries Fedora's `fcr:fixity` endpoint and compares to a SHA-1 digest. — [emory-libraries dlp-selfdeposit fixity job](https://codeclimate.com/github/emory-libraries/dlp-selfdeposit/app/jobs/fixity_check_job.rb/source)
- Fedora: if the repository retains multiple copies of binary content, a fixity check runs against each stored copy. — [LYRASIS wiki (Fedora)](https://wiki.lyrasis.org/x/sdAQAg)
- No source found on Islandora duplicate detection.

### Inferences
- Across commercial platforms, "duplicate detection" where claimed is an ingest-time, exact-hash feature of unknown behavior; none of the documentation found exposes an appraisal UI for reviewing duplicates across accessions. Pre-ingest dedup is being done by customers with desktop tools (Sussex: dupeGuru + DROID + spreadsheet) before content reaches the preservation system.

### Gaps
- Preservica's actual duplicate-detection mechanism (hash algorithm, scope: within ingest vs. against whole repository, action taken) is not in any public document found; requires vendor documentation/support portal (login).
- LIBNOVA's "Duplicate content detection" mechanism is undocumented in the public admin manual pages read.
- No Islandora-specific information found; no Arkivum product-level information found.

## Key question 3: Stanford Digital Repository (SDR) / SUL DLSS tools — fixity, duplicate content across deposits, Preservation Catalog, relevance to BDPL

### Takeaway
SDR's Moab design identifies files by their fixity values (at least two of MD5/SHA-1/SHA-256) and deduplicates **within a single object's version history** (later versions store only new or changed files), but by design keeps each object's file storage separate and does not deduplicate across objects. preservation_catalog audits Moabs against `manifestInventory.xml` and `signatureCatalog.xml` and replicates to three cloud endpoints; nothing in its public docs detects duplicate content across druids.

### Cited Findings
- Richard Anderson, "The Moab Design for Digital Object Versioning," Code4Lib Journal issue 21 (2013-07-15): "At least two of MD5, SHA1, or SHA256 hash values are generated for each file ingested"; these plus file size identify duplicate files; "the fixity information of a file manifestation is used as its primary identifier and the filename is treated as metadata." The signature catalog "is derived from a filtered aggregation of all the version inventories of a digital object" and "has a file signature entry for every file manifestation ever ingested for the object." Later version data folders "will contain only those new files that were added in that version" (plus modified files). On cross-object dedup, the design is the opposite: "Because each digital object has its own separate file storage structure (rather than a common file pool), the risk of checksum collisions is very low." — [Code4Lib Journal 8482](https://journal.code4lib.org/articles/8482)
- moab-versioning gem: default checksum set is MD5, SHA-1 and SHA-256; `FileInventory` records information about a collection of related files; `StorageObjectVersion#generate_manifest_inventory` builds manifest inventories serialized to XML. — [rubydoc moab-versioning](https://rubydoc.info/gems/moab-versioning/Moab); [StorageObjectVersion](https://rubydoc.info/gems/moab-versioning/Moab/StorageObjectVersion)
- preservation_catalog "tracks, audits and replicates archival artifacts associated with SDR objects"; works with preservation_robots to store SDR object versions in Moab, zips them and replicates to Amazon S3, Google Cloud Storage and an on-premises Ceph cluster; cron audits "compare the Moabs that are on disk, with what is in the database (and vice-versa)" and "ensure that files are present with the expected content (fixity)"; failed audits trigger Honeybadger alerts and audit results generate DOR Services API events; versioned REST API documented in openapi.yml at sul-dlss.github.io/preservation_catalog/; "Authentication/authorization is handled by JWT"; "all tokens grant the same (full) access to the read/update API." The README does not name hash algorithms, does not mention cross-object duplicate detection, and the license type was not stated in the page text (a LICENSE file exists). — [sul-dlss/preservation_catalog](https://github.com/sul-dlss/preservation_catalog)
- Audits (wiki "Audits (basic info)"): M2C (Moab to Catalog), C2M (Catalog to Moab), CV (Checksum Validation: "fixity checking of the Moab", comparing stored checksums in `manifestInventory.xml` and the most recent `signatureCatalog.xml` against recomputed values), and Replication audit (C2A). CV re-runs on Moabs with expired `last_checksum_validation`. No algorithm named; no mention of duplicates across objects. — [preservation_catalog wiki: Audits (basic info)](https://github.com/sul-dlss/preservation_catalog/wiki/Audits-(basic-info))
- A Dec 2022 mirror of the "Audits (how to run as needed)" wiki page describes checksum validation covering every MoabRecord for a storage root, with a "90-day fixity TTL" (mirror; may be outdated). — [preservation_catalog wiki mirror](https://github.imc.re/sul-dlss/preservation_catalog/wiki/Audits-(how-to-run-as-needed)/82ee6c230227188d87f3577262c59b2fb781f384)

### Inferences
- For a BDPL (born-digital) workflow, SDR will not warn that a file in a new accession is byte-identical to one already preserved under a different druid; any cross-accession duplicate review must happen before accessioning (appraisal stage) or via an external index of Moab `signatureCatalog.xml` / `versionInventory.xml` hashes.
- Because Moab inventories already carry MD5/SHA-1/SHA-256 per file, a Stanford dedup tool could reuse those algorithms to make its pre-accession hashes directly comparable with SDR preservation metadata (useful for "has this already been deposited?" checks against exported inventories).

### Gaps
- preservation_catalog license type not confirmed from the page text (LICENSE file exists; other sul-dlss repos use Apache 2.0, unverified here).
- No SUL DLSS blog post or documentation found addressing duplicate content across deposits; absence noted rather than confirmed.
- Current Checksum Validation interval (TTL) not confirmed from the live wiki.

## Key question 4: Archival processing tools with dedup — Brunnhilde, DROID, Siegfried, AVP Fixity/Exactly, Bagger/BagIt, FTK, Autopsy, TreeSize-style tools (ePADD/BitCurator: integration points only)

### Takeaway
Only a few archivist-facing tools actually report duplicates: Brunnhilde (via Siegfried hashes, md5 default, report-only), FTK ("Flag Duplicate Files" + filter, flag/exclude only), and general-purpose desktop tools (TreeSize, dupeGuru, WinDirStat) that can also delete. DROID computes hashes (off by default, MD5 default) but leaves duplicate finding to Excel/Access; Siegfried, BagIt tools, AVP Fixity and Exactly produce or verify checksums but do not identify duplicates; Autopsy's hash module does known-file lookup, not duplicate detection.

### Cited Findings
**Brunnhilde**
- Version 1.9.6; MIT license; "Brunnhilde uses the md5 hash algorithm by default"; options sha1, sha256, sha512, or none; default Siegfried invocation `sf -csv -hash md5 DIR`; with `--hash none` "the CSV outputs and HTML report lose the duplicate-file information"; CSV reports in `csv_reports` folder "queried from database" include a duplicate-files report; writes `siegfried.sqlite` to the output directory (deleted at end unless `-k`; `--in-memory-db` option); flags include `-d` disk image input, `-b` bulk_extractor, `-z` scan archives, `--csv`/`--stdin` to read existing Siegfried CSV; "Brunnhilde and its dependencies are already installed in BitCurator 1.7.106+" and from 1.8.0 a launcher is in BitCurator's "Forensics and Reporting" folder. No Archivematica integration. — [tw4l/brunnhilde](https://github.com/tw4l/brunnhilde)
- A later release "reworked the duplicates query and report processing to be significantly faster for large quantities of files" (release notes, per search summary). — [brunnhilde releases](https://www.github.com/tw4l/brunnhilde/releases)
- BitCurator step-by-step guide: Brunnhilde's HTML report "displays information provided by Siegfried, such as file formats, versions, dates, errors, duplicates, etc." — [BitCurator docs: Analyzing a Disk Image with Brunnhilde](https://bitcurator.github.io/documentation/All%20Step-by-Step%20Guides/Forensics%20and%20Reporting%20Guides/Analyzing%20a%20Disk%20Image%20with%20Brunnhilde)
- Integration point (BitCurator covered elsewhere): Brunnhilde is the BitCurator environment's packaged duplicate reporter; bulk_extractor results are exposed in both Brunnhilde and Archivematica's Appraisal tab ("Examine contents"), but neither uses bulk_extractor for duplicates.

**DROID**
- DROID User Guide, July 2024, © Crown copyright 2024, "based on the current version of DROID (v.6.6)": "3.11 Hash (checksum): DROID can optionally generate a content hash or checksum of the contents of each file and container file, using either the SHA 1, SHA 2 (256) or MD5 algorithms... Content hashes can be used to detect files with duplicate content, or can be linked to forensic hash databases to find or exclude files which are widely used..." "Detecting duplicates: An easy way to see if you have duplicate files using Excel is to highlight the HASH column and select the Home section - Conditional Formatting - Highlight Cells Rules - Duplicate Values." "Tick box 3: Generate hash for each file: ... By default this option is off, as generating hashes slows down profiling significantly. The hash type defaults to MD5, but SHA256 and SHA1 can be selected as alternatives." CSV column 13: "HASH (Fixed size string of character generated by running the contents of the file through one of the hashing algorithms. Droid supports MD5, SHA1, SHA256 and SHA512)". DROID can look inside zip, tar, gzip, rar, 7zip, iso, bzip2, arc containers. — [DROID User Guide PDF (TNA, July 2024)](https://cdn.nationalarchives.gov.uk/documents/information-management/droid-user-guide.pdf)
- A UW-Milwaukee workflow exports DROID CSV to MS Access and runs the duplicate wizard on MD5_HASH; "Duplicates identified may not share a file name." — [UWM Preservation File Inventory Workflow](https://uwm.edu/libraries/wp-content/uploads/sites/572/2022/05/Preservation_FileInventoryWorkflow.pdf)
- TNA states "DROID is a mandatory software required for the digital transfer process" for UK government transfers. — [TNA appraisal and selection](https://www.nationalarchives.gov.uk/information-management/manage-information/digital-records-transfer/digital-transfer-steps/steps-1-and-2-appraisal-and-selection/)

**Siegfried**
- Version 1.11.9 (changelog "v1.11.9 (2026-09-27)"); Apache-2.0; `-hash` "Calculate md5, sha1, sha256, sha512, or crc hash"; outputs YAML (default), `-csv`, `-json`, `-droid`; `-z` "Decompress and scan zip, tar, gzip, warc, arc". "Nothing in the README, options list, or changelog mentions duplicate detection." — [richardlehane/siegfried](https://github.com/richardlehane/siegfried)

**AVP Fixity, Exactly, BagIt/Bagger**
- Fixity (AVP) "creates a manifest of files stored in directories identified by the user, documenting file names, locations, and checksums" and schedules reviews to monitor changes; "ideal for monitoring of files in long term storage, complimenting tools such as BagIt that check fixity at points of transition." — [AVP Fixity v0.3 release](https://www.weareavp.com/fixity-v0-3-released/)
- Exactly (AVP) is a desktop utility to create and transfer Bags; the 2018 user guide (v0.1.6) describes checksum creation and validation while copying files before preparing a BagIt bag. — [Exactly User Guide 2018](https://www.weareavp.com/wp-content/uploads/2018/05/Exactly_UserGuide.pdf)
- Library of Congress Bagger "is no longer maintained or supported"; BagIt can be used via bagit-python or other tools. — [Orbis Cascade: File Fixity & Data Integrity](https://orbiscascadeccd.github.io/digprezsteps/fixity-deep.html)
- None of these tools is documented as identifying duplicates; BagIt manifests (`manifest-<alg>.txt`) list per-file hashes that a dedup tool could parse.

**FTK (Exterro, formerly AccessData)**
- NYPL Digital Archives (de-duplicating collections guide): de-duplication via filter is "an optional method of managing the amount of files surveyed"; run Additional Analysis (Evidence menu) → "Flag Duplicate Files" under File Hashes; "This will start a comparison of the checksums of all files in the collection"; a blank Duplicate File field means the file was never analyzed for duplication; a Duplicate File column set can be added. — [NYPL digarch: De-duplicating Collections](https://nypl.github.io/digarch/staging/De-duplicating-collections.html) (page returned 404 on direct fetch in Nov 2026; content from search index)
- Forensic Focus training: pair MD5 hashing with "flag duplicate" options, especially for email review; FTK has a built-in Duplicate Files filter to include/exclude. — [Forensic Focus: Optimizing FTK Processing Options Part 1](https://www.forensicfocus.com/articles/ftk-feature-focus-optimizing-ftk-processing-options-part-1/); [Part 2](https://www.forensicfocus.com/articles/ftk-feature-focus-optimizing-processing-options-part-2/); [forum thread](https://www.forensicfocus.com/forums/general/ftk-filter-file-duplication/)
- Harvard wiki describes a "No Duplicates" filter that removes items FTK has flagged as duplicates from view. — [Harvard wiki: Filters](https://harvardwiki.atlassian.net/wiki/spaces/Proceed/pages/39398539)
- KFF (Known File Filter) flags or ignores files whose hashes match known databases (NIST NSRL, Hashkeeper). — [forensics.wiki: Forensic Toolkit](https://forensics.wiki/forensic_toolkit/)
- Third-party (Cyberly, 14 June 2025, not Exterro): FTK "calculates cryptographic hash values (using algorithms like MD5, SHA-1, and SHA-256)"; users can "Select and exclude duplicate files from the investigation"; framing is exclusion from analysis, not deletion. — [Cyberly](https://www.cyberly.org/en/can-ftk-perform-data-deduplication/index.html)

**Autopsy**
- Hash Lookup ingest module computes hashes and checks them against configured hash sets, flagging files in "notable" sets (Autopsy 4.19.1/4.22.0 docs); no dedicated duplicate-files module found in docs. — [Autopsy 4.22.0 Hash Lookup](https://sleuthkit.org/autopsy/docs/user-docs/4.22.0/hash_db_page.html); [Autopsy 4.19.1](https://sleuthkit.org/autopsy/docs/user-docs/4.19.1/hash_db_page.html)

**TreeSize, WinDirStat, dupeGuru, Auslogics**
- TreeSize (JAM Software) duplicate search "uses a combination of file name, file size, and last change date or compares MD5 or SHA256 checksums"; can replace duplicates with NTFS hardlinks/symlinks or move/delete. — [JAM Software blog](https://www.jam-software.com/blog/find-remove-duplicate-files.shtml); [data sheet](https://www.jam-software.com/sites/default/files/2019-04/TreeSizeProfessional_Data_Sheet_EN.pdf)
- Andrew McDonnell (University of Kentucky SCRC), "What's Gobbling this Hard Drive? Deduplication, Advanced File Search, and File Characterization ... with TreeSize For Windows," UK Libraries R&I Day, 14 Feb 2024: uses TreeSize in born-digital appraisal and processing to "determine what sorts of file duplication we might have across multiple folders or network drives"; it "is able to determine where duplicate files exist in multiple locations", remove duplicates and keep a log. — [UKnowledge](https://uknowledge.uky.edu/ri_day_2024/6)
- dupeGuru: free, open source, cross-platform; scans filenames (fuzzy) or contents; Standard/Music/Picture modes. — [LinuxLinks dupeGuru](https://www.linuxlinks.com/dupeguru-find-duplicate-files/)
- Wisconsin Historical Society "File Management Tools" (reviewed Jan 2018, not maintained) lists Auslogics Duplicate File Finder for Windows for records managers. — [WHS FileMgmtTools PDF](https://www.wisconsinhistory.org/pdfs/la/FileMgmtTools-Final.pdf)

### Inferences
- Among free tools used by archivists, Brunnhilde is the only one that produces a ready-made duplicates report, and only within one run (one directory or disk image); none of the surveyed free tools maintains a persistent cross-accession hash index. FTK provides flag+filter across a case but is proprietary and forensic-oriented; TreeSize/dupeGuru can delete, which archivists generally avoid before appraisal decisions are documented.
- A Stanford tool consuming Siegfried/DROID CSV (both carry per-file hash columns) and BagIt manifests would interoperate with the formats archivists already generate.

### Gaps
- Brunnhilde's exact duplicates CSV filename/columns not confirmed from the README (source code would show it).
- No official Exterro documentation of current FTK "Flag Duplicate Files" semantics (which hash, email dedup behavior) found; relied on NYPL, Forensic Focus and a third-party article.
- Autopsy: absence of a duplicate module is inferred from docs; not confirmed with the full module list.

## Key question 5: Storage-level deduplication — content-defined chunking (restic, Borg, Kopia), ZFS/btrfs, object storage; why archivists keep appraisal dedup separate

### Takeaway
Storage-level dedup works transparently on chunks or blocks identified by cryptographic hashes, saves bytes across everything in a repository or pool, and never surfaces "this file duplicates that file" to a curator; it also carries operational costs (dedup tables, verify options) and is absent from S3-style object stores. Preservation platforms and community guidance treat it as a storage-efficiency concern, distinct from appraisal.

### Cited Findings
- restic: "All content within a restic repository is referenced according to its SHA-256 hash"; CDC "uses Rabin Fingerprints"; "An irreducible polynomial is selected at random and saved in the file `config`" (makes watermark attacks harder); 64-byte sliding window; "Files smaller than 512 KiB are not split, Blobs are of 512 KiB to 8 MiB in size"; "aims for 1 MiB Blob size on average"; "only modified Blobs have to be saved in a subsequent backup... even works if bytes are inserted or removed at arbitrary positions"; trees encoded deterministically "so that trees can be properly deduplicated"; AES-256-CTR + Poly1305-AES. — [restic design references](https://restic.readthedocs.io/en/stable/100_references.html)
- Borg: buzhash chunker "triggers (chunks) when the last HASH_MASK_BITS bits of the hash are zero"; "Buzhash is **only** used for cutting the chunks"; defaults CHUNK_MIN_EXP=19 (512 KiB), CHUNK_MAX_EXP=23 (8 MiB), HASH_MASK_BITS=21 (~2 MiB target), HASH_WINDOW_SIZE=4095; buzhash table XORed with a per-repository seed "stored encrypted in the keyfile"; chunk id is "a cryptographically strong hash/MAC over the chunk contents" (`id_key` HMACs plaintext chunk data); "Chunks already present in repo won't be transferred to repo again"; also a `fixed,BLOCK_SIZE[,HEADER_SIZE]` chunker. — [Borg internals: data structures](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html)
- Kopia: "Block ID is generated by applying cryptographic hash function... such as SHA2 or BLAKE2S"; "two identical blocks of data will produce exactly the same identifiers"; blocks "typically <=20MB", packs "20-40MB each"; encryption after hashing (AES256-GCM-HMAC-SHA256, CHACHA20-POLY1305-HMAC-SHA256). — [Kopia architecture](https://kopia.io/docs/advanced/architecture/)
- ZFS `dedup` property: values `on`, `verify`, `sha256[,verify]`, `sha512[,verify]`, `skein[,verify]`, `edonr,verify`, `blake3[,verify]`; default checksum "sha256 (this may change in the future)"; "If set to **verify**, ZFS will do a byte-to-byte comparison in case of two blocks having the same signature"; "Specifying **verify** is mandatory for the **edonr** algorithm"; "Unless necessary, deduplication should _not_ be enabled on a system"; "Deduplication and Direct I/O writes are currently incompatible." — [OpenZFS zfsprops(7)](https://openzfs.github.io/openzfs-docs/man/master/7/zfsprops.7.html)
- Object storage: Wasabi documentation states S3-style cloud storage services like Wasabi do not perform data compression or deduplication; such capabilities are "a function of the storage application or gateway." — [Wasabi: Does Wasabi perform deduplication or compression](https://docs.wasabi.com/docs/does-wasabi-perform-data-deduplication-or-compression)
- An open-source S3 gateway (rs3gw) implements SHA256 content addressing with reference counting and lists "no cross-bucket dedup: deduplication is per-storage-root" as a limitation. — [rs3gw DEDUP.md](https://docs.rs/crate/rs3gw/0.2.2/source/src/storage/DEDUP.md)
- Preservation platforms describe storage copies as *redundancy*, not dedup: Preservica "For integrity multiple copies of files are saved across multiple cloud storage locations" with checksums per copy ([Preservica G-Cloud](https://assets.applytosupply.digitalmarketplace.service.gov.uk/g-cloud-15/documents/583399/255400856602027-service-definition-document-2026-01-15-1401.pdf)); SDR replicates zipped Moabs to three "geographically distributed, architecturally heterogeneous" platforms ([preservation_catalog](https://github.com/sul-dlss/preservation_catalog)); Moab deliberately avoids a common file pool ([Code4Lib 8482](https://journal.code4lib.org/articles/8482)).
- Richardson 2012 (quoted in SAA Dictionary): "Deduplication works by comparing chunks of data and looking for duplication" — the storage sense; vs. Wong 2006: "Deduplication is the process of identifying two files as being the same file" — the file/appraisal sense. — [SAA Dictionary: deduplication](https://dictionary.archivists.org/entry/deduplication.html)
- 2015 iPRES paper on deduplicating a ~1 PB web archive after the fact using WARCrefs and ISO 28500 (WARC `revisit` records) — a domain where dedup is recorded explicitly in the preservation format rather than hidden in storage. — [phaidra.univie.ac.at o:429548](https://phaidra.univie.ac.at/o:429548)

### Inferences
- Storage dedup operates below the level of archival description: it identifies common byte ranges (often sub-file) and cannot tell an archivist that two *files* are duplicates, which copy is in original order, or whether removing one changes evidential context. It also changes nothing about what is described, delivered to researchers, or counted in extent statements. Hence appraisal dedup (a documented curatorial decision) and storage dedup (an invisible efficiency) are complementary, not substitutes.
- The preservation community's preference for *multiple independent copies* (NDSA Levels, Preservica, SDR) runs counter to pool-wide dedup: a single corrupted shared chunk/block would affect every object referencing it, and Moab's "separate file storage structure" is an explicit design choice against a common pool.

### Gaps
- No formal preservation-community position statement (e.g. DPC, NDSA) specifically about storage-level dedup was found; the "position" is inferred from platform designs and redundancy requirements. btrfs dedup documentation was not consulted.

## Key question 6: Community guidance — NDSA Levels, DPC Handbook, SAA, OSSArcFlow; "keep everything, flag duplicates" vs. "weed at appraisal"; legal/evidentiary considerations

### Takeaway
Community guidance strongly frames deduplication as an *appraisal* decision made and documented by archivists (TNA, SAA Dictionary citations, DPC webinar workflows), with practitioner workflows typically identifying duplicates pre-ingest via hash reports and recording decisions in a spreadsheet. The NDSA Levels and DPC Handbook address fixity and multiple copies but do not prescribe dedup; evidentiary arguments (original order, email thread context) favour flagging over silent deletion, though no authoritative statement resolving this was found.

### Cited Findings
- SAA Dictionary of Archives Terminology, "deduplication (n.): the process of identifying and removing redundant electronic files" (Toney 1992). Citations include Huth 2016 / Pendergrass et al. 2019: "Deduplication tools enable a user to find and remove duplicate files and temporary files"; Thompson 2022: "Deduplication of those files deemed to be unnecessary should be part of the appraisal process"; Skinner and Hulbert 2022: "request precustodial interventions from the donor such as deduplication"; Decker et al. 2022: "some method of deduplication will be necessary." The entry also notes metadata or descriptive pointers can stand in for duplicate files, and that removing unneeded duplicates during appraisal lowers storage and environmental costs; a Friends Historical Library case found asking donors to dedupe before transfer impractical. — [SAA Dictionary: deduplication](https://dictionary.archivists.org/entry/deduplication.html)
- UK National Archives (digital transfer steps 1-2) lists removing "exact duplicates (this will reduce the amount of information you will have to review on average there is 40% duplication in the digital environment)" and explains "if two records are exactly identical, the checksums will be the same"; recommends macro-appraisal and DROID. — [TNA: Appraisal and selection](https://www.nationalarchives.gov.uk/information-management/manage-information/digital-records-transfer/digital-transfer-steps/steps-1-and-2-appraisal-and-selection/)
- DPC Handbook "Acquisition and appraisal": does not address deduplication; says "digital resources can proliferate and appraisal can be a daunting task", "decisions about selection and preservation may need to be taken simultaneously for digital collections", selection may need "greater rigour" than for analogue; cost options range from "Accept and store as received (least cost-effective option long-term, despite lower initial costs)" to "Limit range of media received (most cost-effective long-term option)"; cites a Wellcome article on "Duplication and Abundance" as a barrier to transfers. — [DPC Handbook: Acquisition and appraisal](https://www.dpconline.org/handbook/organisational-activities/acquisition-and-appraisal)
- State Library of New South Wales (DPC appraisal watch party, 25 Sept 2024) recommends excluding duplicate folders during pre-custodial technical appraisal of born-digital archives, alongside excluding program/system files. — [DPC SLNSW appraisal slides](https://www.dpconline.org/docs/events-1/2024-events/appraisal-watch-party/3359-2024-09-25-slnswappraisal-dpc/file)
- University of Sussex (DPC Workflows webinar Feb 2024): duplicates identified from DROID output, recorded to an appraisal spreadsheet, archivists decide, "Agreed upon actions are completed and documented", then checksums regenerated before Arkivum ingest. — [DPC ingest webinar PDF](https://www.dpconline.org/docs/events-1/2024-events/workflow-webinars-1/3099-dpc-workflows-webinar-ingest-feb-2024/file)
- NYPL treats FTK duplicate flagging as "an optional method of managing the amount of files surveyed" (hiding duplicates via filter), not deletion. — [NYPL digarch](https://nypl.github.io/digarch/staging/De-duplicating-collections.html)
- GW Libraries born-digital framework: carriers should be appraised so media that "does not need to be copied (duplicates, out-of-scope material, etc.)" is identified. — [GW Libraries framework](https://gwu-libraries.github.io/DigitalServicesDocs/borndigital/framework)
- NDSA Levels of Digital Preservation V2.0 (Oct 2019, Levels of Preservation Revisions Working Group) organized into five functional areas including Storage, Integrity (fixity), Control, Metadata, Content; materials at OSF DOI 10.17605/OSF.IO/QGZ98; V2.1 adds a "Digital Curation Decision Guide" for "decision points around collections." The matrix text itself was not retrievable in this session; no mention of deduplication found on the NDSA page. — [NDSA Levels](https://ndsa.org/publications/levels-of-digital-preservation/); [OSF project](https://doi.org/10.17605/OSF.IO/QGZ98)
- NDSA 2014 fixity guidance defines fixity as "the property of a digital file or object being fixed or unchanged... synonymous with bit-level integrity." — [NDSA Fixity Guidance Report 2014](https://www.digitalpreservation.gov/ndsa/working_groups/documents/NDSA-Fixity-Guidance-Report-final100214.pdf)
- OSSArcFlow Guide to Documenting Born-Digital Archival Workflows (Chassanoff & Post, Educopia, 2020; SAA Preservation Publication Award 2021) describes 13 common steps and tools; search results did not surface any dedup-specific guidance. — [Educopia OSSArcFlow](https://educopia.org/research/ossarcflow); [SAA award](https://www.archivists.org/2021-Preservation-Publication-Award-Alexandra-Chassanoff-and-Colin-Post)
- Evidentiary/context considerations: for organisations "e-mail is generally organized within the system by the individual who is sending and receiving the e-mail. This organization ensures that duplicates will appear through out the system" ([Archives & Museum Informatics, item-level control](https://archimuse.com/papers/nhprc/item-lvl.html)); a critique that treating each message as a single artifact (ePADD, DarcMail) "tend[s] to decontextualise the email corpus" ([AERI Evidence Studies](https://aeri.website/conference-schedule/evidence-studies/)); an NC State case reports tension between "Preserve original order where possible" and "Reduce storage size on servers" with drives full of duplicate images ([pathlms PDF](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)); "Digital records are more likely to have multiple versions over the course of their lifetime than physical records" ([Galloway, Order As Received](https://ischool.utexas.edu/galloway/spring2018/INF392K2018/OrderAsReceivedAERI-1.pdf)).
- Integration points for ePADD/BitCurator (covered by other researchers): BitCurator ships Brunnhilde as its duplicates reporter ([tw4l/brunnhilde](https://github.com/tw4l/brunnhilde)); email dedup is a distinct problem (quoted/forwarded content, same message in multiple mailboxes) as noted in the sources above.

### Inferences
- The dominant practitioner pattern (TNA, Sussex, NYPL, SLNSW, UK) is: hash → report → archivist decides → document → act, with the hash report generated pre-ingest by DROID/Siegfried/Brunnhilde/FTK. This matches an appraisal-stage tool design where duplicates are flagged and decisions logged, rather than auto-deleted.
- Because email and shared-drive duplicates carry contextual meaning (who held a copy, where it sat in original order), a "flag and record, exclude from transfer by decision" approach preserves evidentiary value better than silent removal; the sources support this inference but do not state it as a rule.

### Gaps
- No single authoritative SAA/DPC/NDSA statement on whether to weed duplicates at appraisal versus keep-and-flag was found; guidance is diffuse (dictionary citations, national-archives transfer guidance, practitioner workflows).
- NDSA V2.0 matrix row text could not be retrieved (OSF-hosted PDF not fetched); the Harvard conformance page returned empty.
- Legal/evidentiary literature specific to deduplication of born-digital archival records (as opposed to e-discovery) was not found; e-discovery dedup practice (not surveyed here) is the closest analogue.
