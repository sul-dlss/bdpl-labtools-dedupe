# BitCurator Finds Duplicates but Never Decides Them

*Research report for the Stanford Libraries Born-Digital Preservation Lab (BDPL). Research conducted 2026-11-01; all version and date claims are as of that date unless stated. Where the underlying notes could only confirm a fact from a search-engine snippet, or could not fetch the primary source, that is marked "(snippet only)" or "(unverified)".*

**Bottom line.** BitCurator 5.1.0 (released July 2025) ships general-purpose hashers (hashdeep/md5deep, Hashrat, GtkHash, ssdeep, Siegfried's `-hash`, fiwalk's DFXML with MD5 and SHA-1) and exactly one tool that produces a duplicates *report* out of the box: Brunnhilde, which groups Siegfried hashes in SQLite with a three-line SQL query. It ships no dedicated duplicate finder (FSlint was dropped in February 2020; fdupes, jdupes, rdfind and rmlint are absent), no sdhash despite the documentation still listing it, and its own Reporting Tool has no installer state in the 5.x line and should be treated as retired ([bitcurator-salt](https://github.com/BitCurator/bitcurator-salt/tree/main/bitcurator); [Release History](https://github.com/BitCurator/bitcurator-distro/wiki/Release-History)). Outside BitCurator, a mature field of exact-match finders exists (jdupes, rmlint, fclones, czkawka, rdfind, all with 2025–2026 releases), but every one of them works on one filesystem tree per run and none reads disk images, DFXML, or a persistent cross-accession index. Near-duplicate tooling is usable from Python (TLSH, imagehash, datasketch, Chromaprint) but has no production archival deployment; the one archival prototype, Eltrovo (2024), stalled on output volume. Preservation systems, including Stanford's SDR, verify fixity per object and do not detect duplicate content across deposits; Moab deduplicates only within a single object's version history, by design. Archival guidance is consistent: identify duplicates early by hash, decide at the Moderate processing tier after assessing context, remove at media or folder level if at all, link rather than delete, and document in the finding aid. The gap a BDPL tool fills is therefore specific and real: a read-only, hash-based tool that reports duplicates within and across accessions and carriers, aggregates at carrier and directory level, proposes a transparent keep-rule for a human to confirm, and emits pointer maps, exclusion lists, and DACS- and PREMIS-ready documentation, without ever touching the source.

## BitCurator 5.1.0 hashes everything and reports duplicates once

The BitCurator Environment is a volunteer-maintained set of Salt states that converts a clean Ubuntu 24.04 LTS or 22.04 LTS install (x86/amd64 only) into a forensics workstation; the current release is **5.1.0, announced 17 July 2025** with Installer 3.0.0, and the `bitcurator-salt` repository was last pushed on 2026-06-17 ([bitcurator-distro wiki: Releases](https://github.com/BitCurator/bitcurator-distro/wiki/Releases); [bitcurator-users announcement](https://groups.google.com/g/bitcurator-users/c/gpZSHxZ6DFc); [bitcurator-salt](https://github.com/BitCurator/bitcurator-salt)). The 5.1.0 release added JHOVE, dvdisaster and lightgrep 1.5.0 and swapped OpenJDK 8 for Temurin JDK 21; it added or removed no hashing or deduplication tools. Because the GitHub Releases tab is empty and releases are announced on the wiki and mailing list, the Salt tree itself is the authoritative inventory of what is installed, and the research for this report read it directly rather than relying on documentation pages ([bitcurator-distro releases](https://github.com/BitCurator/bitcurator-distro/releases)).

That distinction matters because the project's `docs/Tools.md` (last commit 2025-05-01) still lists the BitCurator Reporting Tool, BitCurator Disk Image Access, and sdhash under forensic analysis tools, and none of the three has a Salt state in 5.1.0 ([BitCurator documentation Tools.md](https://github.com/BitCurator/documentation/blob/main/docs/Tools.md)). The BitCurator Walkthrough likewise still says the environment "includes Vassil Roussev's sdhash" and lists FSlint under "Deduplicate Files", and a 2024 PDT&C article repeats that BitCurator includes both ssdeep and sdhash ([BitCurator Walkthrough](https://bitcurator.github.io/documentation/BitCurator%20Walkthrough/BitCurator%20Walkthrough); [Karp, PDT&C 2024](https://www.degruyterbrill.com/document/doi/10.1515/pdtc-2024-0042/html), snippet only). A recursive grep of the 5.1.0 Salt tree found no `fslint`, `fdupes`, `jdupes`, `rdfind`, `sdhash`, or any state or launcher matching "report" or "premis" ([bitcurator-salt tree](https://github.com/BitCurator/bitcurator-salt/tree/main/bitcurator)). Treat the Tools.md and Walkthrough pages as historical inventories.

### Brunnhilde's duplicates report is three lines of SQL

Brunnhilde, created by Tessa Walsh at the Canadian Centre for Architecture in 2016–2017 and bundled in BitCurator since 1.8.0 (17 March 2017), runs `sf -csv -hash <algo>` over a directory or over files that `tsk_recover` has exported from a disk image, loads the CSV into a SQLite table named `siegfried`, and derives its duplicates report from this query: `SELECT * FROM siegfried WHERE hash IN (SELECT hash FROM siegfried WHERE filesize<>'0' GROUP BY hash HAVING COUNT(hash) > 1 AND COUNT(DISTINCT filename) > 1) ORDER BY hash;` ([brunnhilde.py](https://raw.githubusercontent.com/tw4l/brunnhilde/main/brunnhilde.py); [Release History](https://github.com/BitCurator/bitcurator-distro/wiki/Release-History)). Three design choices follow from that query and are worth copying or consciously rejecting: zero-byte files are excluded, a hash group counts only if it spans more than one filename, and `duplicates.csv` rows carry the full Siegfried record (filename, size, modified date, hash, PUID, format, version, MIME, basis, warning) because the query is `SELECT *`. The HTML report's headline figure is computed as all duplicate rows minus distinct duplicate hashes and displayed as "Duplicates: N (of M distinct files)". **MD5 is the default** and `--hash none` removes duplicate information entirely ([tw4l/brunnhilde README](https://github.com/tw4l/brunnhilde)). Two practical caveats come from practitioners: Brunnhilde counts symbolic links at the size of their target, which distorted post-dedup storage estimates at NC State, and `tsk_recover` does not retain filesystem dates, so Brunnhilde itself recommends fiwalk DFXML for timestamps ([Phillips, NC State poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG); [tw4l/brunnhilde README](https://github.com/tw4l/brunnhilde)). Because everything sits in one SQLite table, a new tool can reuse Brunnhilde's database or Siegfried's CSV directly and write its own grouping; the duplicates logic is trivially reproducible without Brunnhilde, and the project has had no release since 1.9.6 (31 March 2023) and has not tracked Siegfried CSV changes past `sf` 1.10 ([tw4l/brunnhilde](https://github.com/tw4l/brunnhilde)).

### The Reporting Tool never had a duplicates report, and is gone

The BitCurator Reporting Tool's documented outputs were annotated bulk_extractor features, `bc_format_bargraph.pdf`, `bulk_extractor_report.pdf`, `fiwalk_deleted_files.pdf`, `fiwalk-output.xml.xlsx`, `fiwalk_report.pdf`, `format_table.pdf`, and `premis.xml`; the guide never mentions hashes or duplicates ([Creating Disk Image Reports](https://bitcurator.github.io/documentation/All%20Step-by-Step%20Guides/Forensics%20and%20Reporting%20Guides/Creating%20Disk%20Image%20Reports%20using%20the%20BitCurator%20Reporting%20Tool); [Forensic Reports.md](https://github.com/BitCurator/documentation/blob/main/docs/All%20Step-by-Step%20Guides/Forensics%20and%20Reporting%20Guides/Forensic%20Reports.md)). Its contribution to deduplication was indirect: the xlsx conversion of fiwalk DFXML carries per-file MD5 and SHA-1 columns, which a UCL practitioner in April 2020 described as the way to spot identical files, without reporting having found any ([Conway, UCL blog](https://reflect.ucl.ac.uk/inst0045-1920-jess-conway/?p=477)). Kam Woods said in December 2016 that the underlying scripts (`generate_report.py`, `bc_genrep_premis.py`) "have not been updated in a very long time" and "could definitely use a rewrite" ([bitcurator-users: Generating PREMIS xml](https://groups.google.com/d/topic/bitcurator-users/Ku7e4WsdCys)). The repository that held them, `bitcurator-distro-tools`, returns 404; the surviving `bitcurator-python-tools` package (MIT, last commit 2024-11-20) contains only `identify_filenames.py` and bulk_extractor helpers, and `identify_filenames.py` maps feature offsets to filenames plus MD5 rather than finding duplicates ([BitCurator/bitcurator-python-tools](https://github.com/BitCurator/bitcurator-python-tools); [identify_filenames.py](https://github.com/BitCurator/bitcurator-python-tools/blob/main/bitcurator_python_tools/identify_filenames.py)). The 2014 iPRES demonstration that advertised "identification of duplicate files" among BitCurator features described no mechanism; the most plausible reading is the xlsx hash columns plus FSlint, both now gone ([Phaidra iPRES 2014 record](https://phaidra.univie.ac.at/o:378717)). No official retirement statement for the Reporting Tool was found; status is inferred from the absence of a Salt state, launcher, and repository.

### DFXML is the cross-media path, but you will write the join yourself

fiwalk emits DFXML with `<hashdigest type='md5'>` and `<hashdigest type='sha1'>` per fileobject directly from a disk image, both on by default, with `-z` to disable and `-O` to restrict to allocated files; SHA-256 is not listed on the man page or the forensics wiki ([fiwalk(1) Debian man page](https://manpages.debian.org/unstable/sleuthkit/fiwalk.1.en.html); [forensics.wiki fiwalk](https://forensics.wiki/fiwalk/)). The `dfxml_python` library (a NIST/NPS work, CC0 for US-government portions and LGPL for other contributions, commits as recent as May 2026) parses this, and its `dfxml/bin/` directory includes `walk_to_dfxml.py` for loose directories, `make_differential_dfxml.py` and `idifference.py` for image-to-image differencing, `dedup.py`, and `dfxinfo.py` ([dfxml_python](https://github.com/dfxml-working-group/dfxml_python); [dfxml/bin](https://github.com/dfxml-working-group/dfxml_python/tree/main/dfxml/bin)). The dedup scripts are the weak point: `dedup.py` reads a single DFXML file, groups by MD5 only, prints counts and `--dups` lists, and despite its header never removes anything; `dfxinfo.py --files` as written raises a `TypeError` and a `NameError` and will not run without fixes ([dedup.py source](https://raw.githubusercontent.com/dfxml-working-group/dfxml_python/main/dfxml/bin/dedup.py); [dfxinfo.py source](https://raw.githubusercontent.com/dfxml-working-group/dfxml_python/main/dfxml/bin/dfxinfo.py)). The Smithsonian's time-based media workflow uses an idifference-style script to sort differences between two fiwalk reports into new and deleted files, which is differencing rather than dedup ([Smithsonian TBMA](https://www.si.edu/tbma/resource/comparing-fiwalk-reports), snippet only; page returned 403). **No shipped script deduplicates across multiple DFXML files.** The sound approach is to import the actively maintained library, iterate fileobjects across all DFXML inputs, and group on SHA-1 or MD5 yourself; hashdeep's `-d` flag emits compatible DFXML for directories, which gives one interchange format for images and loose files ([hashdeep.1 man page](https://raw.githubusercontent.com/jessek/hashdeep/master/man/hashdeep.1)). BitCurator also ships the DFXML tag library and schema under its Documentation menu, and `nsrllookup` provides an MD5-keyed known-file filter that works directly from DFXML hashes without extraction ([bitcurator-salt theme/documentation](https://github.com/BitCurator/bitcurator-salt/tree/main/bitcurator/theme/documentation)).

### The Consortium's own analysis software is retired; dedup rests on third parties

Of the software the BitCurator Consortium wrote, only the environment/installer, the mounter, and `bitcurator-python-tools` are live. BitCurator Access Webtools and Redaction were archived on 2 June 2023 with the statement that they "have reached end-of-life and are no longer maintained"; the NLP repositories were archived 2022–2023; `bc_to_aspace_toolkit` was archived in 2023; the Reporting Tool and Disk Image Access have no 5.x installer state ([BitCurator/bitcurator-access](https://github.com/BitCurator/bitcurator-access); [BitCurator org](https://github.com/BitCurator)). Everything dedup-relevant that remains is third-party, and its health is uneven: Siegfried (September 2026), The Sleuth Kit (April 2026), bulk_extractor (August 2026) and the dfxml library (May 2026) are active; Brunnhilde (2023), Bulk Reviewer (2022), hashdeep (2014) and ssdeep (2017) are installable but stalled; FSlint and sdhash are gone. The Consortium's own documentation on deduplication consists of a legacy, delete-oriented FSlint guide, Reporting Tool guides that do not discuss duplicates, and Brunnhilde guides that stop at the report ([FSlint guide](https://bitcurator.github.io/documentation/All%20Step-by-Step%20Guides/Forensics%20and%20Reporting%20Guides/FSlint); [Analyzing a Disk Image with Brunnhilde](https://github.com/BitCurator/documentation/blob/main/docs/All%20Step-by-Step%20Guides/Forensics%20and%20Reporting%20Guides/Analyzing%20a%20Disk%20Image%20with%20Brunnhilde.md)). A search of the bitcurator-users list for duplicate-file threads returned nothing, and no Consortium webinar on deduplication was located; the closest is Creighton Barrett's 2017 BitCurator Users Forum lightning talk on FSlint, FTK and the NSRL RDS (abstract only) ([Dalhousie record](https://dal.scholaris.ca/items/b1daa03c-3fa5-4739-bc68-00b95c0e669c/full)).

The clearest community workflow comes from outside the Consortium's docs. NC State Special Collections, processing the 8 TB, seven-drive John Mark Hall photographs, imaged each drive, transferred and arranged files, then "used the tool Jdupes to create symbolic links for each duplicate and generate a report of where link pointed," packaged that report with the processing documentation, and added `du -sh` to size packages correctly once symlinks were present ([Phillips, NC State poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)). Bentley's BitCurator teaching material presents Brunnhilde's unique-versus-duplicate counts as an aid to appraisal and gives no instruction to remove anything ([Bentley bitcurator-intro, Reporting](https://bentley-historical-library.github.io/bitcurator-intro/04-reporting.html)). The de facto BitCurator practice is therefore: hash at ingest, report duplicates, make the appraisal decision explicitly, and if copies are removed, replace them with links or a link-target report so order and provenance remain reconstructible. BitCurator's tools cover the detection step; nothing in the environment covers the decision or record-keeping step, which is where a BDPL tool adds value.

## Exact-match finders are fast and safe by default, but each sees one tree at a time

Every mainstream command-line duplicate finder uses the same funnel: group by size, hash a small head (and sometimes tail) block, hash the full file, and optionally confirm byte-by-byte. They differ in three things that matter to an archivist: whether the binary contains a deletion path at all, which hash it uses, and whether it emits machine-readable output. The most actively maintained in late 2026 are **jdupes 1.31.3 (20 October 2026)**, **rmlint 2.11.0 (1 November 2026)**, **czkawka 12.0.2 (9 September 2026)**, **yadf 1.5.2 (16 October 2026)** and **rdfind 1.8.0 (22 February 2026)**; fclones has had no commits since its 0.35.0 release on 3 March 2025; dupeGuru's last release was July 2022; duff (2012) and FSlint (Python 2) are dead ([Codeberg jdupes releases](https://codeberg.org/api/v1/repos/jbruchon/jdupes/releases); [rmlint releases](https://github.com/sahib/rmlint/releases); [qarmin/czkawka](https://github.com/qarmin/czkawka); [jRimbault/yadf](https://github.com/jRimbault/yadf); [pauldreik/rdfind](https://github.com/pauldreik/rdfind); [pkolaczk/fclones](https://github.com/pkolaczk/fclones); [arsenetar/dupeguru](https://github.com/arsenetar/dupeguru); [elmindreda/duff](https://github.com/elmindreda/duff)).

Two lessons stand out. First, "read-only" is not "writes nothing": rmlint writes a script and JSON to the working directory by default and its `--xattr` mode stores checksums in the extended attributes of scanned files; fdupes `-c` and jdupes `-y` write hash databases; fclones and czkawka cache to the user's cache directory ([rmlint tutorial](https://rmlint.readthedocs.io/en/latest/tutorial.html); [fdupes man page](https://raw.githubusercontent.com/adrianlopezroche/fdupes/master/fdupes.1); [Codeberg jdupes](https://codeberg.org/jbruchon/jdupes)). A wrapper should run from a directory outside the accession, hard-code the argument list, and prefer tools whose binary has no in-process delete path (rmlint, yadf, fclones `group`, czkawka with `-D NONE`). Second, the fast tools use non-cryptographic hashes: jdupes xxHash64, fclones metro-128, yadf highway. These are fine for *finding candidates* when a byte compare or a 128-bit space backs them up, but rmlint's own manual warns that "the use of 64-bit hash length for detecting duplicate files is not recommended, due to the probability of a random hash collision," and none of these values belongs in archival metadata ([rmlint man page](https://rmlint.readthedocs.io/en/latest/rmlint.1.html)). Published speed comparisons are all author-run on Linux SSDs; in the fclones author's 316 GB test, fclones finished in 0:34.59, yadf 0:59.32, czkawka 2:09.00, rmlint 2:28.43 and jdupes 5:01.91, and the yadf author's warm-cache test put yadf at 0.332 s against jdupes 1.31.2 at 3.205 s ([fclones README](https://github.com/pkolaczk/fclones); [yadf README](https://github.com/jRimbault/yadf)). The ordering (Rust tools fastest, byte-comparing single-threaded C tools slowest) is consistent, but absolute times do not transfer to macOS or network storage, and no independent 2026 benchmark on macOS was found.

### Manifests, not finders, are the cross-accession interchange format

None of the finders above compares a tree against a stored manifest from an earlier accession. hashdeep does: `-k` loads a known-hash file, `-m` lists input files that match it (`-w` names the known file matched), `-x` lists files that do not, and `-a` runs an audit that passes only "if each input file is matched against exactly one file in set of knowns"; it computes several algorithms in one pass (`-c md5,sha256`), emits DFXML with `-d`, and never writes to the scanned tree ([hashdeep.1 man page](https://raw.githubusercontent.com/jessek/hashdeep/master/man/hashdeep.1); [jessek/hashdeep](https://github.com/jessek/hashdeep)). Its cost is age: v4.4 dates from 29 January 2014, the last commit from 2017, and whether it builds on current Apple Silicon was not verified (Homebrew still ships it, which suggests yes). Faster hashers exist but leave the join to you: b3sum 1.8.7 (20 August 2026) is multithreaded and "an order of magnitude faster than e.g. sha256sum"; RHash 1.4.6 (13 May 2025) computes many digests in one pass under a 0BSD license but lists no BLAKE2/BLAKE3; bagit-python 1.9.0 (13 June 2025) writes md5/sha1/sha256/sha512 manifests with `--processes` for parallelism ([BLAKE3 GitHub](https://github.com/BLAKE3-team/BLAKE3); [RHash GitHub](https://github.com/rhash/RHash); [PyPI bagit](https://pypi.org/project/bagit/)). AVP's open-source Fixity was archived on 11 May 2022; Fixity Pro is reported to have been transferred to the Open Preservation Foundation, but its current license was not confirmed from an OPF page ([avpreserve/fixity](https://github.com/avpreserve/fixity); [digipres Fixity Pro demo](https://www.digipres.org/practices/tool-demos/fixity-pro/tool-demo-fixity-pro.pdf), unverified). Because hashdeep, b3sum, RHash, Siegfried CSV/JSON, DROID CSV and BagIt manifests are all flat per-file hash lists, a Python tool can treat "manifest" as its interchange format and join on the hash column in SQLite regardless of which hasher produced it. hashdeep's own DFXML output header format was recalled but not verified from a fetched source.

### NSRL known-file filtering now means opening a SQLite file

Known-file filtering removes operating-system and application noise before duplicates are counted, and it is orthogonal to intra-accession dedup. NIST now publishes only the **RDSv3 SQLite format; the current release is 2026.09.1 (1 September 2026)**, on a quarterly cadence, in Modern, Legacy, Android and iOS sets plus a "minimal" Modern database containing distinct FILE rows, and RDSv3 added SHA-256 alongside SHA-1 and MD5 ([NIST Current RDS Hash Sets](https://www.nist.gov/itl/ssd/software-quality-group/national-software-reference-library-nsrl/nsrl-download/current-rds); [RDSv3.pdf](https://s3.amazonaws.com/rds.nsrl.nist.gov/RDS/RDSv3_Docs/RDSv3.pdf), summarized from search; the PDF could not be text-extracted). Legacy consumers still key on MD5: TSK `hfind` indexes `nsrl-md5`/`nsrl-sha1`, Autopsy computes SHA-256 but states "these will not be used in hash set lookups," and bulk_extractor removed its hashdb scanner in 2.0 ([hfind man page](https://sleuthkit.org/sleuthkit/man/hfind.html); [Autopsy Hash Lookup 4.23.0](http://sleuthkit.org/autopsy/docs/user-docs/4.23.0/hash_db_page.html); [Garfinkel & Stewart, arXiv 2208.01639](https://arxiv.org/pdf/2208.01639)). For a Python tool, the simplest route is to open the minimal Modern database with the standard `sqlite3` module and query by SHA-256, sidestepping conversion to hfind or Autopsy formats; the FILE view's exact column names were not verified and should be confirmed against the `.schema.sql` shipped in each release. The NSRL also publishes MD5 hashes of the first 4,096 and 8,192 bytes of files and a 16,801,737-row SHA-1 to SHA-256 mapping; CAID is a separate child-abuse-imagery metadata product and irrelevant here ([NIST Non-RDS Hash Sets](https://www.nist.gov/itl/csd/secure-systems-and-applications/national-software-reference-library-nsrl/nsrl-download/non)). NSRL hits should be reported as a separate category ("known software file"), not as duplicates.

### The Python standard library is enough for the hashing core

`hashlib.file_digest()` (added in Python 3.11) hashes a file object directly, and the GIL is released for updates over 2,047 bytes, so a thread pool gets real parallelism for SHA-256; the `blake3` wheel (1.0.11, 8 October 2026; CC0 or Apache-2.0; Python ≥3.11) adds `max_threads=blake3.AUTO` and `update_mmap()` for multi-gigabyte files, with the caveat that threading "can be slower for inputs shorter than ~1 MB" ([Python hashlib docs](https://docs.python.org/3/library/hashlib.html); [PyPI blake3](https://pypi.org/project/blake3/)). The size-prefilter plus head/tail partial hash plus full hash pipeline is cheap to reimplement with `os.scandir`, and most wall time is I/O, so a pure-Python tool is adequate at appraisal scale with fclones or jdupes JSON as optional backends. The closest archival precedents are Brunnhilde (Siegfried CSV → SQLite → report) and Aarhus Stadsarkiv's digiarch, which computes BLAKE2 checksums with multiprocessing and writes a collisions file to flag duplicates ([digiarch docs](https://digiarch.readthedocs.io/en/development/identify.html)). No US university library's appraisal dedup script was located in two searches; COPTR's De-Duplication category lists Czkawka, dupeGuru, FSlint, Matchbox, Sumfolder1, AllDup, Autopsy and WinMerge, but the page itself returned 503 and was read from search excerpts only ([COPTR De-Duplication](https://coptr.digipres.org/De-Duplication), snippet only).

### Hash choice: MD5 finds duplicates, SHA-256 keeps them findable

For appraisal dedup the threat is accidental collision, not forgery, so MD5 groups duplicates perfectly well; dupeGuru's documentation makes exactly that argument ([dupeGuru scan docs](https://dupeguru.voltaicideas.net/help/en/scan.html)). The reason to prefer SHA-256 is interoperability and longevity: NIST retired SHA-1 for security use with a phase-out deadline of 31 December 2030, Archivematica defaults to SHA-256, NSRL added SHA-256, and Moab stores at least two of MD5/SHA-1/SHA-256, so a SHA-256-keyed index avoids re-hashing later ([NIST Retires SHA-1](https://www.nist.gov/news-events/news/2022/12/nist-retires-sha-1-cryptographic-algorithm)). BLAKE3 is "secure, unlike MD5 and SHA-1" and much faster than SHA-2 with multithreading, which makes it the best internal hash for a new tool, but SHA-256 and MD5/SHA-1 should be computable in the same pass for crosswalks to fiwalk (MD5/SHA-1 only), DROID (MD5 default) and legacy manifests; hashing once in Python and feeding bytes to several digest objects costs one extra CPU pass and no extra I/O ([BLAKE3 GitHub](https://github.com/BLAKE3-team/BLAKE3); [xxHash GitHub](https://github.com/Cyan4973/xxHash)). No measurement of BLAKE3 versus SHA-256 file-hashing throughput on Apple Silicon was found.

## Near-duplicate tools work from Python but have no archival track record

Bytewise fuzzy hashing has three candidates and only one with a pulse. **ssdeep 2.14.1 (7 November 2017)** is the reference context-triggered piecewise hash, GPL-2.0, with a 0–100 match score; its PyPI C wrapper is version 3.4 from 2019 with classifiers only to Python 3.7, and the pure-Python `ppdeep` dates from 2020; it cannot compare files of very different sizes because block size derives from length ([ssdeep-project/ssdeep](https://github.com/ssdeep-project/ssdeep); [PyPI ssdeep](https://pypi.org/project/ssdeep/); [PyPI ppdeep](https://pypi.org/project/ppdeep/20200505/); [ssdeep man page](https://www.mankier.com/1/ssdeep)). **sdhash 4.0 (9 December 2013)**, Apache-2.0, has a SWIG Python binding and was last pushed in October 2020; Roussev's 2011 DFRWS evaluation found it "consistently outperforms ssdeep across all categories, with ssdeep struggling on some MS Office files" ([sdhash/sdhash](https://github.com/sdhash/sdhash); [Roussev 2011, DFRWS](https://dfrws.org/presentation/an-evaluation-of-forensic-similarity-hashes/), quote via search summary; PDF not fetched). **TLSH 5.0.2 (July 2026)**, with `py-tlsh` 5.0.0 on PyPI (8 May 2026), is the only one with active releases; it needs at least 50 bytes of input, scores 0 as near-identical with higher meaning more different, and its `diffxlen` variant ignores length differences, directly addressing ssdeep's weakness on grown drafts ([trendmicro/tlsh README](https://github.com/trendmicro/tlsh); [PyPI py-tlsh](https://pypi.org/project/py-tlsh/)). Independent comparisons favor TLSH and sdhash over ssdeep: Pagani et al. (CODASPY 2018) conclude "tlsh and sdhash consistently outperform ssdeep and should be recommended in its place," and Nilsimsa "has a significantly higher false positive rate" than the other three ([Pagani et al. 2018](https://www.eurecom.fr/en/publication/5419/download/sec-publi-5419.pdf); [Wikipedia: Nilsimsa](https://en.wikipedia.com/wiki/Nilsimsa_Hash)). NIST SP 800-168 (May 2014) supplies the standard vocabulary (bytewise, syntactic, semantic approximate matching) for documenting whatever method a tool adopts ([NIST SP 800-168](https://csrc.nist.gov/publications/detail/sp/800-168/final)). Every one of these evaluations used malware or the t5 corpus; thresholds will need recalibration on archival test data.

For images, `imagehash` (BSD-2, 4.3.2 on 1 February 2025, repo pushed 12 October 2026) is the lowest-dependency option, returning a Hamming distance when two hashes are subtracted; `imagededup` adds CNN embeddings, a `find_duplicates` API and an evaluation framework against ground truth; Meta's PDQ is the most "documented" choice for defensible reporting because it publishes both a quality score (discard ≤49) and a match threshold (Hamming distance ≤31 of 256 bits) ([JohannesBuchner/imagehash](https://github.com/JohannesBuchner/imagehash); [idealo/imagededup](https://github.com/idealo/imagededup); [ThreatExchange/pdq](https://github.com/facebook/ThreatExchange/tree/main/pdq)). The archival need was framed in 2013 by Trevor Owens as "16 nearly identical catfish photos" and "15 PDFs that differ only in cover pages," and a 2015 NAU Special Collections post proposed ssdeep for hundreds of near-identical commercial photographs, but neither reports a tested result ([Owens, The Signal 2013](https://blogs.loc.gov/thesignal/2013/09/the-future-of-digital-equivalence-and-significance/); [NAU Special Collections blog 2015](https://library.nau.edu/speccoll/blog/2015/07/appraisal-of-digital-photographs/)).

For documents, the defensible pipeline is text extraction, normalization, k-shingles, MinHash and an LSH index with a Jaccard threshold, which is the architecture e-discovery vendors describe. `datasketch` 2.0.0 (5 July 2026, MIT) provides MinHash, MinHash LSH, LSH Forest and LSH Ensemble with Redis and Cassandra backends; note that 2.0.0 changed the default permutation scheme, so persisted sketches must be rebuilt or created with `scheme="legacy"` ([ekzhu/datasketch](https://github.com/ekzhu/datasketch)). Williams and Giles found shingling (F = 0.99) outperformed simhash (F = 0.91) on CiteSeerX in 2013 ([Microsoft Research record](https://www.microsoft.com/en-us/research/?p=415481)). Microsoft Purview's near-duplicate detection compares every text-bearing document pairwise against a configurable threshold, groups those above it and marks one "pivot" per group so reviewers read the pivot and then only the differences; that group-representative-differences pattern is a ready model for appraisal output ([Microsoft Learn: Near duplicate detection](https://learn.microsoft.com/en-us/purview/ediscovery-near-duplicate-detection)). Bytewise fuzzy hashing of OOXML and ODF containers is unreliable because compression scrambles byte similarity, which is consistent with ssdeep's observed trouble on Office files; extract text first.

Email is the one domain where Stanford already owns a dedup mechanism. ePADD (Apache-2.0, 11.1.3 on 3 June 2026, maintained by the Open Preservation Foundation) deduplicates at ingest on an exact composite signature: `EmailDocument.getSignature()` concatenates Date to the minute, From, To, Cc, Bcc and Message-ID when present, hashes it into `uniqueID`, and falls back to a body snippet (first and last 500 characters plus length) only when both date and Message-ID are missing; on a hit the fetcher skips the message, increments `nMessagesAlreadyPresent`, records the duplicate's folder and Message-ID against the retained document, and PREMIS events record "Duplicate messages: N" per source ([ePADD/epadd README](https://github.com/ePADD/epadd); [EmailDocument.java](https://github.com/ePADD/epadd/blob/master/src/java/edu/stanford/muse/index/EmailDocument.java); [EmailFetcherThread.java](https://github.com/ePADD/epadd/blob/master/src/java/edu/stanford/muse/email/EmailFetcherThread.java)). It performs no fuzzy matching, so sent-versus-received copies with different Message-IDs or dates a minute apart are not duplicates; its practice of retaining provenance for every suppressed copy is the useful model. DArcMail, TOMES and Mailbag convert formats and show no dedup feature; a code search of `mailbagit` for "duplicate" matched only a persona document and the WARC derivative ([Mailbag project](https://archives.albany.edu/mailbag/); [SIA DArcMail](https://siarchives.si.edu/what-we-do/digital-curation/email-preservation-darcmail)). A Rylands (Manchester) blog from November 2021 reported that ePADD's summary and per-MBOX reports gave different duplicate counts because "the figures were being calculated differently for different reports," and that a parser treating body text "From " as a new message inflated counts; both are cautionary for any tool that reports counts in several views ([Rylands Blog, Palladium project](https://rylandscollections.com/2021/11/17/palladium-project-development-work-on-epadd/)).

For audio, Chromaprint 1.6.2 (15 October 2026) with pyacoustid 1.3.1 (9 April 2026), whose `compare_fingerprints` is pure Python and local, identifies near-identical audio without calling the AcoustID web service; video hashing in Python is thin (videohash 3.0.1, May 2022, 64-bit frame-collage hash), and no archival deployment of either was found ([acoustid/chromaprint](https://github.com/acoustid/chromaprint); [PyPI pyacoustid](https://pypi.org/project/pyacoustid/); [PyPI videohash](https://pypi.org/project/videohash/)). The one archival precedent for content-level audio dedup is Six et al.'s finding of "around 38%" duplicate material in a Belgian shellac-disc collection, with a recommendation to link duplicates so listeners reach the better-preserved copy ([Six et al. 2022](https://0110.be/files/publications/2022/2022.duplicates-author_version.pdf)).

The single archival near-duplicate prototype is instructive mainly for how it failed. Eltrovo (St John Karp, Pratt Institute, GPL-3.0, presented at the BitCurator Forum in March 2024) runs ssdeep and sdhash over a collection and emits an RDF graph of duplicates, related drafts and embedded files; on a 229-file trial set it produced 1,168 RDF triples, "a graph so large that the conversion to a PDF could not be completed," and it has not been updated since 7 April 2024 ([dazzlepansy/eltrovo](https://github.com/dazzlepansy/eltrovo); [Karp, PDT&C 2024](https://www.degruyterbrill.com/document/doi/10.1515/pdtc-2024-0042/html), snippet only). Pairwise similarity output grows combinatorially; any BDPL tool that adds a similarity pass needs union-find clustering over threshold edges and a representative-per-cluster report, not a pair list.

## Preservation systems, including SDR, verify fixity but never compare deposits

No preservation platform surveyed exposes an appraisal view of duplicate content, and only two vendors claim duplicate detection at all, without saying how it works. The pattern across the field is that each file is compared against its own stored checksum, at ingest and on a schedule, and that cross-object comparison is left to whoever prepares the SIP.

### SDR's Moab design deduplicates inside an object and refuses to across objects

Stanford's situation is well documented and unambiguous. Richard Anderson's Moab design (Code4Lib Journal, 15 July 2013) generates "at least two of MD5, SHA1, or SHA256 hash values" per ingested file, treats "the fixity information of a file manifestation" as its primary identifier with the filename as metadata, and builds a `signatureCatalog.xml` holding "a file signature entry for every file manifestation ever ingested for the object," so that later version folders "contain only those new files that were added in that version" plus modified ones ([Anderson, Code4Lib Journal 21](https://journal.code4lib.org/articles/8482)). That is deduplication, but strictly within one druid's version history. Across objects the design is deliberately the opposite: "Because each digital object has its own separate file storage structure (rather than a common file pool), the risk of checksum collisions is very low" ([Anderson, Code4Lib Journal 21](https://journal.code4lib.org/articles/8482)). The `moab-versioning` gem's default checksum set is MD5, SHA-1 and SHA-256 ([rubydoc moab-versioning](https://rubydoc.info/gems/moab-versioning/Moab)). `preservation_catalog` tracks, audits and replicates Moabs to Amazon S3, Google Cloud Storage and an on-premises Ceph cluster; its audits are Moab-to-Catalog, Catalog-to-Moab, Checksum Validation (recomputing against `manifestInventory.xml` and the latest `signatureCatalog.xml`) and a replication audit, with failures raising Honeybadger alerts and a JWT-protected REST API; nothing in the README or audit wiki mentions duplicate content across druids ([sul-dlss/preservation_catalog](https://github.com/sul-dlss/preservation_catalog); [preservation_catalog wiki: Audits](https://github.com/sul-dlss/preservation_catalog/wiki/Audits-(basic-info))). A December 2022 wiki mirror mentions a 90-day fixity TTL; the current interval and the repository's license type were not confirmed from live pages ([preservation_catalog wiki mirror](https://github.imc.re/sul-dlss/preservation_catalog/wiki/Audits-(how-to-run-as-needed)/82ee6c230227188d87f3577262c59b2fb781f384), unverified).

Two consequences follow for BDPL. SDR will not warn that a file in a new accession is byte-identical to one already preserved under another druid, so any cross-accession duplicate review has to happen before accessioning or through an external index built from exported Moab inventories. And because Moab inventories already carry MD5, SHA-1 and SHA-256 per file, a BDPL tool that computes the same three algorithms produces hashes directly comparable with SDR preservation metadata, which makes a "has this already been deposited?" check against exported `signatureCatalog.xml` or `versionInventory.xml` files a matter of a join.

### Storage-level dedup is invisible to curators and intentionally avoided by preservation designs

Backup and filesystem dedup operate below the file. restic references all content by SHA-256 and splits files into content-defined chunks of 512 KiB to 8 MiB using Rabin fingerprints with a per-repository random polynomial; Borg cuts chunks with a buzhash and identifies them with an HMAC over plaintext; Kopia hashes blocks with SHA2 or BLAKE2S; OpenZFS `dedup` keys on sha256 by default with an optional byte-to-byte `verify`, and its own manual states that "unless necessary, deduplication should not be enabled on a system" ([restic design](https://restic.readthedocs.io/en/stable/100_references.html); [Borg internals](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html); [Kopia architecture](https://kopia.io/docs/advanced/architecture/); [OpenZFS zfsprops(7)](https://openzfs.github.io/openzfs-docs/man/master/7/zfsprops.7.html)). S3-style object stores such as Wasabi perform no dedup at all ([Wasabi: deduplication or compression](https://docs.wasabi.com/docs/does-wasabi-perform-data-deduplication-or-compression)). None of this tells an archivist that two *files* are duplicates, which copy sits in original order, or whether removing one changes evidential context, and it changes nothing about what is described, delivered, or counted in extent statements. The preservation community's preference for multiple independent copies runs against pool-wide dedup: a corrupted shared chunk would affect every object referencing it, and Moab's separate per-object storage is an explicit design choice against a common pool. The SAA Dictionary captures the two senses side by side, Richardson's 2012 storage definition ("comparing chunks of data") and Wong's 2006 file-level one ("identifying two files as being the same file"); the BDPL tool is squarely about the second ([SAA Dictionary: deduplication](https://dictionary.archivists.org/entry/deduplication.html)). Web archiving is the one domain that records dedup explicitly in the preservation format, through WARC `revisit` records that point to the retained payload, a model revisited below ([IIPC WARC deduplication proposal 1.0](https://iipc.github.io/warc-specifications/specifications/warc-deduplication/recording-arbitrary-duplicates-1.0)).

## Archival practice says detect early, decide at the Moderate tier, link rather than delete, and write it down

The most widely cited community framework places every duplicate-handling task above the baseline. The *Digital Processing Framework* (Faulder et al., August 2018, drafted after a 2016 Born Digital Archiving eXchange unconference at Stanford) defines Baseline as the minimum for any born-digital material, Moderate as work that "may utilize forensic tools and require specialized skill sets," and Intensive as the most resource-heavy; its activity "Address presence of duplicate content" has two tasks, both at **Moderate**: "Assess contextual and information value of duplicate content to determine if duplicates should be weeded" and "Document decision in collection documentation and in finding aid/catalog record" ([Digital Processing Framework, Cornell eCommons](https://ecommons.cornell.edu/handle/1813/57659), tier columns verified by parsing the XLSX). Running tools to identify duplicate, temporary, system and hidden files is likewise Moderate, while the Baseline obligation is documentary: "If files are deleted, restricted, or redacted note this in the Processing Information note and/or the Conditions Governing Access note in the finding aid, as well as in your collection management system and the collection file" ([Digital Processing Framework](https://ecommons.cornell.edu/handle/1813/57659)).

Institutional manuals agree on granularity and restraint. The University of California's *Guidelines for Efficient Archival Processing* (v4, May 2020) instruct that "appraising digital content at a high level means surveying carriers, disk-images, and directories, not individual files," that archivists should "not rename or re-arrange digital files during appraisal," that duplicate files "can be identified by comparing hash values or using tools that automate the recognition and deletion of duplicate files, such as TreeSize Professional or FTK," and, for photographs, "Retain duplicates, unless voluminous. Duplicates may have unseen value," because "numerous copies indicates a preferred, heavily used image" ([UC Guidelines v4](https://escholarship.org/uc/item/4b81g01z)). The Library of Congress Manuscript Division's 2023 processing-history note lists "Identify Duplicates and Empty Directories" as a stage, says duplicates "may be appraised for potential removal," and removes at media or folder rather than file level (snippet only; the PDF returned 403) ([LoC MSS Processing History Note](https://findingaids.loc.gov/exist_collections/ead3pdf/mss/2023/MSS-Processing-History-Note.pdf)). GWU's born-digital best practices (draft 30 November 2023) record outcomes such as "Duplicate files were reviewed by the practitioner and removed from the SIP" and "Duplicate files were not retained once it was confirmed that they existed in another preferred file format (PDF/A)," and warn that save-everything approaches "accrue significant environmental, labor, and resource costs overtime" ([GWU Best Practices](https://gwu-libraries.github.io/DigitalServicesDocs/borndigital/bestpractice)). The University at Buffalo splits documentation: a general statement about deduplication in the Appraisal Information note with no technical detail, specifics in Processing Information, an Extent that counts preserved files, and a pre-processing DROID manifest kept "available on request" ([UB Libraries, Processing digital materials](https://research.lib.buffalo.edu/processing/digital-materials)). Scholars Portal tells institutions to "define policies or processes for determining when to keep or discard duplicates" and how to document them, naming Brunnhilde and DROID as the detection tools ([Scholars Portal, Review and Appraisal](https://learn.scholarsportal.info/?p=4795)). The UK National Archives requires a DROID CSV with checksums before transfer, explains that "if two records are exactly identical, the checksums will be the same," and asserts that "on average there is 40% duplication in the digital environment," a figure given without a source ([TNA: Appraisal and selection](https://www.nationalarchives.gov.uk/information-management/manage-information/digital-records-transfer/digital-transfer-steps/steps-1-and-2-appraisal-and-selection/)). Stanford's own earlier practice, per Glynn Edwards's RBMS 2011 slides, used FTK for "identifying duplicates" among other forensic tasks (snippet only) ([RBMS 2011 Edwards slides](https://www.slideshare.net/slideshow/rbms-2011-edwards-8463230/8463230)). No manual found mandates file-level deduplication, and no published PREMIS event type for it exists.

The quantitative record is thin but consistent with high duplication. NC State's John Mark Hall collection (seven drives, about 8 TB, roughly 20 years of photographs) showed "~10-50% of each drive is comprised of duplicates of the photos on other drives," and processing yielded "an estimated 41% reduction of total storage size" (2,518,996 MB, 41.89%) with a stated 15% error margin that puts the low end at 26%; the arrangement step "reduced our ability to maintain original order" and carried an 8% redo rate ([Phillips, NC State poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG)). The University of Kentucky's 2025 reappraisal of legacy servers found "terabytes of duplicate materials that were clearly remnants of earlier processing" with TreeSize, noting that "duplicate files with different names are still found thanks to the software's checksum comparisons" ([McDonnell, SAA ERS blog 2025](https://saaers.wordpress.com/2025/11/05/looking-for-trouble-born-digital-reappraisal)). A 2024 PDT&C article on optical media reported that cross-disc checksum comparison "was not in archivists' toolkits, so a large degree of manual labor was still required" (snippet only) ([PDT&C 2024](https://www.degruyterbrill.com/document/doi/10.1515/pdtc-2024-0042/html)). If the duplicate set is routinely as large as the unique set, reports that list file pairs are useless; aggregation by carrier and directory is a requirement, not a nicety.

The arguments for keeping duplicates are about context, and they shape the output more than the algorithm. Patricia Galloway's "Order As Received" (2010) argues that order on the medium, including discrepancies between filesystem dates and embedded metadata dates, is itself evidence, that archivists customarily "weed duplicates" yet "nor is any public statement usually made as to what exactly has been done," and that the field should abandon "the too frequently silent emendation by archivists of 'order as received'" ([Galloway, Order As Received](https://pages.ischool.utexas.edu/galloway/spring2018/INF392K2018/OrderAsReceivedAERI-1.pdf)). The SAA Dictionary's entry for deduplication quotes Thompson (2022) that "deduplication of those files deemed to be unnecessary should be part of the appraisal process," Skinner and Hulbert (2022) that asking donors to dedupe before transfer proved impractical, and Kopin, Hutchinson and Truitt (2025) that tools like ePADD and DArcMail "can make it harder to read threads in context," with deduplication adding to that difficulty ([SAA Dictionary: deduplication](https://dictionary.archivists.org/entry/deduplication.html)). The practitioner compromise that reconciles storage, usability and evidence is "preserve the image, dedupe the DIP": NC State kept the drive images and the nested per-drive folder structure, replaced duplicates with symlinks and shipped a link-target report with the package; web archives write `revisit` records with `WARC-Refers-To` rather than dropping payloads; Six et al. recommend linking audio duplicates so users reach the better copy ([Phillips, NC State poster](https://cdn.fs.pathlms.com/HIBAakhRYOghl5Alu1vG); [IIPC WARC deduplication proposal 1.0](https://iipc.github.io/warc-specifications/specifications/warc-deduplication/recording-arbitrary-duplicates-1.0); [Six et al. 2022](https://0110.be/files/publications/2022/2022.duplicates-author_version.pdf)). Browsertrix's April 2026 dedup design adds a warning that translates directly: once content is deduplicated against a collection index, "deduplicated crawls depend on other archived items," so a DIP that omits copies depends on the package holding the retained copy, and the report must say so ([Webrecorder blog 2026-04-09](https://webrecorder.net/blog/2026-04-09-deduplication)).

## Design requirements for an appraisal-stage tool that reports and never modifies

The requirements below are synthesized from the tool inventories and the practice literature above; no published institutional requirements document for a dedup tool was found, so each row names the evidence it rests on. The organizing principle is the one every source converges on: the tool detects and documents, the archivist decides, and the source media are never touched.

| **A field for what cannot be automated.** Archivist-entered notes on analog duplication in hybrid collections and a free-text rationale per decision. | UC donor surveys and Scholars Portal both ask for analog duplication to be identified. | [UC Guidelines v4](https://escholarship.org/uc/item/4b81g01z); [Scholars Portal, Review and Appraisal](https://learn.scholarsportal.info/?p=4795) |

Two engineering notes round this out. The hashing core needs nothing beyond the standard library and, optionally, the `blake3` wheel; a size prefilter, a head/tail partial hash and a full hash reimplement the finders' funnel in a few dozen lines, and fclones or jdupes can be optional backends through their JSON output for very large trees ([Python hashlib docs](https://docs.python.org/3/library/hashlib.html); [PyPI blake3](https://pypi.org/project/blake3/); [Codeberg jdupes](https://codeberg.org/jbruchon/jdupes)). And the biggest unverified dependency in the BitCurator path is fiwalk's lack of SHA-256: a cross-walk between image-derived MD5/SHA-1 and a SHA-256-keyed index requires either extracting matched candidates to compute SHA-256 or keying the index on all three algorithms, which hashdeep's `-c md5,sha1,sha256` and a multi-digest Python pass both make cheap ([hashdeep.1 man page](https://raw.githubusercontent.com/jessek/hashdeep/master/man/hashdeep.1)). Whether TSK 4.15's fiwalk can emit SHA-256 should be checked with `fiwalk -h` before committing to that design.

## Conclusion

The research reframes the question. BDPL does not lack duplicate *detection*; BitCurator, Brunnhilde, Siegfried, fiwalk and a dozen fast finders already do that, and the hashing core of any new tool is a weekend of standard-library Python. What no existing tool does is the archival part: compare across carriers and accessions over time, aggregate at the level archivists actually appraise, propose a keep-rule and let a human overrule it, and produce the pointer records and finding-aid notes that the Digital Processing Framework, UC, Buffalo and GWU all require but currently assemble by hand in spreadsheets. The one archival attempt to go further, Eltrovo, failed on report design rather than algorithm, which is a warning that output structure deserves as much thought as hashing.

Three facts narrow the design more than any feature list. SDR will never tell BDPL that a new accession repeats an old one, so the appraisal stage is the only place that check can live, and keying on the same MD5/SHA-1/SHA-256 trio Moab uses makes it a join rather than a project. The BitCurator Consortium's own analysis software is retired and its remaining dedup-relevant pieces are third-party and unevenly maintained, so a BDPL tool should consume BitCurator's file formats (Siegfried CSV, DFXML, hashdeep sets) rather than depend on BitCurator's scripts. And the practice literature's consistent refusal to delete silently means the tool's most valuable output is not the duplicate list but the record of what was decided about it.
