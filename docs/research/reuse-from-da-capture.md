# Reusing BDPL LabKit components in the Dedupe tool

*Code analysis for the Stanford Libraries Born-Digital Preservation Lab (BDPL), 2026-11-01. Source read: `/Users/mgolson/projects/da-capture-macos` (BDPL LabKit, the `wblock_ingest` package, 24,011 lines across 46 modules, 310 `unittest` tests in 42 modules). Requirements read: `docs/research/deduplication-tools-landscape.md` in this repository, the thirteen-row design-requirements table and the BitCurator section. All file:line citations are into `da-capture-macos` unless another path is given; nothing in that repository was changed.*

## Executive summary

LabKit already produces, for every capture it packages, most of the raw material a deduplication tool needs: a per-file hash list from Siegfried (`-hash <algo>`, default MD5), a BagIt payload manifest in every selected algorithm (MD5 and SHA-256 by default), a DFXML `<fileobject>` inventory with one `<hashdigest>` per file, a per-accession `<media>_filelist.csv` export with a checksum column, and image-level digests in `fixity.log`, PREMIS and the bag manifests. None of these stores is indexed or compared across packages. The one cross-object comparison LabKit performs is `sweep._c5_twins`, which flags byte-identical images and identical filename+size sets *within one accession*; there is no SQLite anywhere in the codebase, no cross-accession structure, no match classification, no keep-rule and no fuzzy hashing. Brunnhilde is run without `-k`, so its SQLite is not kept, though its `csv_reports/` (including `duplicates.csv`) land inside the bag.

The reusable value is therefore in three places: (1) the **persisted hash stores and their exact formats**, which can seed a cross-accession index without re-reading media; (2) a set of **small, nearly dependency-free modules** that can be copied verbatim or with light adaptation: the capability registry (`capabilities.py`), the Siegfried CSV reader and container-member filter, the bag-manifest parser, the PREMIS 3.0 and DFXML serializers, the collection-manifest format (`syncstate.py`), the read-only sweep instruments (`sweep.py`), the CSV formula guard and offset-aware timestamp helpers, and the test harness and page-gate pattern; and (3) the **disk-image handling**, which is macOS-specific (`hdiutil`, `ewfexport` to a temp raw, hfsutils for classic HFS) and gives Dedupe a mount-and-walk path but not the in-image hashing that fiwalk provides.

The recommendation is a **standalone application in its own repository, with a copied (later shared) library and an integration seam to LabKit's package tree**, not a new lane inside LabKit. The grounds are structural: LabKit's `core` loads `~/.wblock/config.json` and the `wblock-mac` CLI at import time, holds a single global `session` describing exactly one medium, exits on any platform but macOS, and its job model is one worker thread per stage on that one object. Dedupe is cross-accession, read-only, must run on the BitCurator Linux workstation as well as the Mac, and has a different lifecycle (index, compare, decide, report). LabKit's own architecture strategy anticipates exactly this shape: a family of small apps over a shared core, split out when a concrete need forces it (`docs/architecture-strategy.md` §1, §4).

## 1. Hashing already in place

### What is computed, when, and how

**Algorithms and configuration.** The algorithm set is a per-station config in `~/.wblock/config.json`: `config.setdefault("hashes", {"md5": True, "sha256": True, "sha512": False})` (`macos/wblock_ingest/core.py:248`). `HASH_ALGOS = ("md5", "sha256", "sha512")` (`core.py:270`) and `selected_hashes()` returns the enabled subset in that order, falling back to `["sha256"]` when nothing is ticked (`core.py:273-276`). SHA-1 is never offered as a selectable algorithm, but it is accepted wherever LabKit reads someone else's hashes (sidecars, Siegfried columns). The UI exposes the three checkboxes in four places (`web.py:1518-1520` and repeats).

**Raw `.dd` acquisition** hashes inline in one pass while writing the image, then re-reads the image to verify: `_acquire_raw` reads 8 MiB chunks (`chunk = 8 * 1024 * 1024`, `acquire.py:729`), feeds every selected hasher (`acquire.py:733-746`), then a second pass with fresh hashers (`acquire.py:790-797`). The result is a `hashes` dict per algorithm of the form `{"source": hex, "image": hex, "match": bool}` on the image record, and `image.verified`.

**E01 acquisition** delegates hashing to libewf: `e01_argv` passes `-d sha256` to `ewfacquire` (`acquire.py:102-115`), and the MD5 and SHA-256 are scraped from the tool's "hash calculated over data" lines (`acquire.py:929-935`). No independent re-read is performed; the record says so in PREMIS (`provenance.py:118-120`: "read and verify are one … same instant").

**Logical capture** hashes every file as it is copied: `_copy_tree` opens the source with `O_NOFOLLOW`, copies in 8 MiB chunks and updates one hasher per algorithm (`acquire.py:490-505`). The per-file results are accumulated as `acc["cap"][bag-relative path] = {algo: hex}` (`acquire.py:505`) and stored as `session["capture_hashes"]` (`acquire.py:586`, `acquire.py:617`). Links and special files are recorded, never opened (`acquire.py:430-437`, `acquire.py:462-482`).

**Survey (Siegfried + Brunnhilde)** is where per-file hashes for *imaged* media come from. `_survey_worker` runs `sf -coe -z -hash <algo> -csv <mountpoint>` itself (`pipeline.py:1227-1229`) and then hands the CSV to Brunnhilde with `--noclam -w --csv <sfcsv> <mountpoint> <dest>` (`pipeline.py:1282-1283`). The algorithm is the first of the operator's selected hashes that Siegfried supports: `hashalgo = next((a for a in selected_hashes() if a in ("md5", "sha1", "sha256", "sha512")), "sha256")` (`pipeline.py:1213`). With the default config that is **MD5**, because `HASH_ALGOS` lists `md5` first. A comment marks `-hash` as load-bearing: it is what forces Siegfried to read every byte, and that read is what detected a 90 %-absent image (`pipeline.py:1203-1212`). The CSV lands at `<package>/brunnhilde/siegfried.csv` (`survey_dir()`, `pipeline.py:888-890`), later `data/brunnhilde/siegfried.csv` once bagged.

**Adopt** (an externally imaged file brought into the pipeline) reads `.md5`, `.sha`, `.sha1`, `.sha256` and `.filelist` sidecars beside the image (`adopt.py:200-215`), infers the algorithm from digest length (`{40: "sha1", 64: "sha256"}`, `adopt.py:214`), and verifies by re-hashing with the union of selected and expected algorithms in 1 MiB chunks (`adopt.py:323-329`, `adopt.py:433-445`).

**Bagging** reuses what was already computed rather than re-hashing: `known = dict(session.get("capture_hashes") or {})` plus the raw image's verified digest (`pipeline.py:1699-1706`); anything not covered is hashed by `_hash_file` (`core.py:827-836`, 8 MiB chunks, all algorithms in one read). Manifests are written per algorithm (`pipeline.py:1719-1722`), then `bagit.txt`, `bag-info.txt` and `tagmanifest-<algo>.txt` (`pipeline.py:1724-1738`).

Other hashing sites, for completeness: `syncstate._sha256` (1 MiB chunks, `syncstate.py:39-44`), `sweep._sha256` (`sweep.py:174-182`), `emulate.py:451-455` (a session's fixity audit, `md5(usedforsecurity=False)` alongside SHA-256), `packages._manifest_vouches` (`packages.py:202-223`), and `renderdisc.py:212` (MD5 of a composed derivative). There is no `blake3`, no partial/head-tail hashing, and no size prefilter anywhere; `_c5_twins` groups by size before hashing but only at image level (`sweep.py:409-414`).

Two facts in that table shape the Dedupe design. First, the institution's imaging-log CSV carries no hash at all (`intake.py:74-80`), so an index cannot be seeded from the one file every accession is guaranteed to have; it must come from bags and survey artifacts. Second, the per-file stores carry **one algorithm each** — the Siegfried column, the DFXML `<hashdigest>` and the filelist checksum are all the single `hashalgo`, which is MD5 under the default configuration. Only the bag manifests carry every selected algorithm, and they cover payload files as bagged (so a logical capture's files, but for an imaged carrier only the image, not the files inside it).

### Seeding a cross-accession index without re-reading media

For **logical captures**, `manifest-sha256.txt` and `manifest-md5.txt` give SHA-256 and MD5 for every captured file by bag-relative path, with sizes available from `Payload-Oxum` only in aggregate; the Siegfried CSV supplies size, mtime and PUID for the same files under a mount-root path that `fileobjects_from_siegfried` already relativizes (`provenance.py:816-820`). For **imaged captures**, the Siegfried CSV and DFXML are the only per-file sources and are MD5-only by default; SHA-256 for files inside images would require a re-mount and re-hash (or a fiwalk pass, which LabKit does not have). The sidecar and manifest readers that already exist (`pipeline.py:1800-1815`, `sweep.py:185-196`, `service.py:100-124`, `adopt.py:200-215`) are small and can be copied as the index's importers. The practical consequence for the requirements table's "SHA-256 as the persisted key": the index must be keyed on all three of MD5, SHA-1 and SHA-256 with nullable columns, as the research report's own engineering note anticipates, because LabKit's historical corpus is MD5-per-file.

One caveat found by reading: `parse_survey` counts duplicates from `row.get("md5")` only (`pipeline.py:1083-1086`). If a station deselects MD5 so that Siegfried runs with `-hash sha256`, LabKit's own "duplicates" figure silently becomes zero. It is a reminder that the hash column must be discovered by name (as `provenance.py:825` and `pipeline.py:1367` do) rather than assumed.

## 2. External tool wrappers

**Detection.** Two layers. `core.tool_path(name)` searches `PATH` then Homebrew and user bins (`_EXTRA_BIN`, `core.py:283-298`), and `core.deps()` returns a flat presence dict for twelve tools (`core.py:300-313`). Above it, `capabilities.py` holds `TOOLS` (detection probe, install command, license, tested version, `alt` names, or an `.app` `bundle`; `capabilities.py:24-152`) and `CAPABILITIES` (what the app can do, each naming its required tools; `capabilities.py:156-235`). `status()` is PATH-only and safe to poll (`capabilities.py:247-275`); `running_version()` probes the installed version at the moment a tool is used so the record names the version that ran (`capabilities.py:303-320`); `doctor_report()` drives `--doctor` (`capabilities.py:323-358`). The module imports only `IS_ROOT` and `tool_path` from `core` (`capabilities.py:21`), so it lifts out cleanly. Dedupe should copy it, keep the `sf`, `brunnhilde`, `ewfexport`, `hmount` entries, and add `fiwalk`, `hashdeep`, `jdupes`/`fclones` and `ssdeep`/`tlsh` as optional tools. Neither `fiwalk` nor any Sleuth Kit tool appears in `TOOLS` or anywhere in the code; the only references are backlog notes and the PREMIS plan's "tier 3" (`provenance.py:746`, `docs/premis-dfxml-plan.md:154-156`).

**Siegfried.** Invoked once, in `_survey_worker` (`pipeline.py:1227-1229`), with `-coe` (continue on errors, required or macOS metadata dirs abort the run, `CLAUDE.md` constraints) and `-z` (descend zip/tar/gzip/warc/arc only, verified scope at `pipeline.py:1215-1226`). Failure handling is exemplary for a report-only tool: exit code and zero-byte CSV are both treated as "survey did not run", distinct from "zero files" (`pipeline.py:1245-1275`), and the failure is written to the observations register as an unresolved finding (`pipeline.py:1259-1268`). Two helpers are worth copying: `_ContainerRows` (`pipeline.py:998-1021`), which recognizes `sf -z` member rows so they are counted separately from volume files, and `parse_survey` (`pipeline.py:1023-1115`), which aggregates formats, years and executables.

**Brunnhilde.** Run with `--noclam -w --csv <existing sf csv> <mountpoint> <dest>` (`pipeline.py:1282`), so Siegfried is not run twice and ClamAV is not delegated to it. The output directory becomes part of the payload; nothing in LabKit deletes `csv_reports/`, so `duplicates.csv` is present in every surveyed bag. Brunnhilde's SQLite is not retained because `-k` is not passed (see Unverified). Brunnhilde's version is captured with `running_version("brunnhilde")` (`pipeline.py:1337`) and emitted as a PREMIS agent (`provenance.py:185-189`).

**ClamAV.** `_scan_worker` (`pipeline.py:683-880`) writes the raw scanner output to `<media>-clamscan.log` (`pipeline.py:749-757`), parses the summary (`_parse_clam_summary`, `pipeline.py:609`), and computes coverage honestly, counting files over the 2 GiB cap as not examined (`_scan_coverage`, `pipeline.py:636`). Dedupe does not need ClamAV, but the pattern of keeping the tool's own log and reporting coverage as part of the verdict applies to any hashing pass.

**libewf.** `ewfacquire` for capture (`acquire.py:102-115`) and `ewfexport -u -f raw -S 0 -t <target> <e01>` for mounting (`pipeline.py:224-226`), both run as the invoking user via `as_user_argv` (`core.py:81-93`). The export is placed on the output volume rather than system temp, with a free-space guard against the uncompressed size (`pipeline.py:208-221`).

**hdiutil and the host seam.** `pipeline._hdiutil_attach` is a shim over `hostos.attach_image` (`pipeline.py:87-93`); the macOS backend runs `hdiutil attach -readonly -nobrowse -noverify [-imagekey diskimage-class=CRawDiskImage] -plist` (`hostos/darwin.py:17-38`) and the Linux backend uses `losetup`/`mount -o ro` (`hostos/linux.py:31`). The seam has no import back into the application (`hostos/_common.py:1-2`), so it can be vendored as-is.

**hfsutils.** `hfsext.extract(image, dest)` drives `hmount`/`hls`/`hcopy` with a private `HOME` per subprocess, restores catalog dates, and keeps every output path inside `dest` (`hfsext.py:1-20`, `hfsext.py:162`). Data forks only, resource forks stay in the image, and the PREMIS `replication` event says so (`provenance.py:422-437`).

**Process hygiene** that Dedupe should inherit: argument lists only, never shells; `as_user_argv` so analysis tools never run as root (`core.py:81-93`); `_tool_env` to put Homebrew bins on PATH (`pipeline.py:432-438`); `running_version` at the point of use.

## 3. Disk-image handling

**Mounting.** `mount_image` (`pipeline.py:95-198`) handles three shapes: raw `.dd` (forced `CRawDiskImage`), `.iso` (auto-detect), and E01 (export then attach, `pipeline.py:200-247`). When attach fails or yields no mountable volume it checks `fsdetect.detect` and `apple_hfs_partitions` and falls back to hfsutils extraction (`pipeline.py:118-135`), so a classic HFS floppy or a hybrid Mac/PC disc still reaches scan and survey. Attaches outlive the process, so there is an orphan sweep at startup (`sweep_stale_tmpdirs`, `pipeline.py:250`) and a release-on-exit hook (`pipeline.py:376`).

**The privilege split.** `rawreader.py` is a root-only process beside an unprivileged server, reached over an `AF_UNIX` socket in `~/.wblock/reader.sock`, with four jobs (`ping`, `open`, `run`, `cancel`) and a descriptor hand-back via `SCM_RIGHTS` (`rawreader.py:1-35`, `rawreader.py:52-54`); it refuses any disk that is not an attached external physical disk and any output path outside the person's roots (`rawreader.py:68-104`). Dedupe never reads devices, only images and directories, so it needs none of this; it is cited here because it is the reason the rest of LabKit can run as the person, which Dedupe should also do from the start.

**Logical walks.** `_copy_tree` (`acquire.py:439-511`) is a walk that never follows links, records FIFOs and devices instead of opening them, skips `JUNK_DIRS` (`core.py:265-267`), and places each volume in its own folder with a name that cannot collide with LabKit's reserved payload names (`_volume_dir`, `acquire.py:415-427`). `tests/test_logical_walk.py` pins each of these behaviours on scratch folders standing in for a mounted volume (`macos/wblock_ingest/tests/test_logical_walk.py:58-134`). Dedupe's hashing walk should copy exactly this discipline minus the copy: open with `O_NOFOLLOW|O_NONBLOCK`, `lstat` first, record what was not hashed and why.

**Filesystem identification without mounting.** `fsdetect.detect(path)` sniffs FAT12/16, Atari GEMDOS, HFS/MFS/HFS+, AmigaDOS, ProDOS, Apple DOS and D64 from on-disk bytes, stdlib only (`fsdetect.py:1-45`, `fsdetect.py:213`). `devices.iso_filesystems`, `apple_hfs_partitions` and `iso_profile` read ISO 9660 descriptors and Apple Partition Maps from an image file (`devices.py:464`, `523`, `594`); `sweep.declared_extents` and `iso_walk` do the same read-only (`sweep.py:55`, `sweep.py:100`). These are useful to Dedupe for tagging a carrier with its filesystem in the index and for refusing to claim a walk over a volume macOS cannot mount.

**What Dedupe needs that LabKit does not provide.** The requirements call for hashing files inside raw/E01 images without extraction, with allocated files by default and deleted-file matches reported separately. LabKit's only route into an image is mount-and-walk (or extract-and-walk for HFS), which sees the live filesystem only, carries no byte runs and no deleted content, and on macOS is limited to what `hdiutil` can mount. The PREMIS plan explicitly defers a TSK/fiwalk pass to a later tier (`docs/premis-dfxml-plan.md:154-156`, `provenance.py:746`). Dedupe should add `fiwalk` (or `tsk_recover`-style enumeration through `fls`/`icat`) as its image reader, consume its DFXML, and use LabKit's mount path only as a fallback or for carriers whose filesystems TSK does not read. The E01-to-temp-raw export and its free-space guard (`pipeline.py:208-221`) remain useful because fiwalk and `hdiutil` both prefer a raw.

## 4. Package and provenance model

**Layout.** `output_base/<collection slug>/<accession slug>/` is the accession ("group") directory (`intake.py:1144-1160`); each medium is `<group>/<media_full>/` (`intake.py:1175-1176`). Accession-level files: `imaging-log.csv`, `observations.csv` and `observations.md`, `<media>_filelist.csv`, `sessions.csv`, `exports/`, `<media>_pii-screening/`, `received-documentation/` (`sweep.py:203-235`, `packages.py:375-470`). A sealed package is a BagIt 1.0 bag: `bagit.txt`, `bag-info.txt`, `manifest-<algo>.txt`, `tagmanifest-<algo>.txt`, `data/` holding the image or volume folders, `data/brunnhilde/`, `data/metadata/`, `data/custody.log`, `data/fixity.log` (`pipeline.py:1669-1738`). Package discovery for a browser is `packages.scan_packages`, which joins imaging-log rows to on-disk folders (`packages.py:375-492`) and finds the survey directory by locating `siegfried.csv` (`packages.py:114-121`). Dedupe's "enumerate every carrier in a collection" step can reuse these three functions almost unchanged.

**bag-info.** `_bag_info_pairs` (`pipeline.py:1540-1586`) emits `Source-Organization, Contact-Name, External-Identifier, Source-ID, External-Description, Bagging-Date, Bag-Software-Agent, Bag-Size, Payload-Oxum, Accession-Number, Collection-Number, Physical-Format, Capture-Device, Capture-Device-Serial, Source-Media-Label, Capture-Timezone, Capture-Clock-Sync, JIRA-Ticket, Imaging-Success, Imaging-Unreadable-Bytes`. The requirements ask for dedup bag-info key/values; the natural place is this list, with new keys such as `Dedupe-Run`, `Dedupe-Index`, `Dedupe-Groups-Affected`, but only for bags not yet sealed, since appending to `bag-info.txt` after sealing invalidates the tag manifest.

**PREMIS.** `_gather` builds a neutral record (`provenance.py:73-616`) and `_premis_xml` serializes it (`provenance.py:649-706`). Events emitted, with their LoC `eventType` terms: `capture`, `fixity-init` ("message digest calculation"), `fixity-verify` ("fixity check"), `ingest` ("ingestion"), `hfs-extract` ("replication"), `virus-check` ("virus check"), `format-id` ("format identification"), `packaging` ("information package creation") (`provenance.py:264-538`). Agents carry versions in their identifiers (`siegfried@1.11.6`), roles nest inside `linkingAgentIdentifier` per PREMIS 3.0 (`provenance.py:675-699`), every vocabulary term is marked with its authority URI via `_authored` (`provenance.py:625-642`, `core.py:404-435`), and three human roles (authorizer, implementer, executing program) are distinguished (`provenance.py:191-233`). This is directly the shape the requirements' "per-run event log mappable to PREMIS" needs. A Dedupe run would add an event of type `message digest calculation` for any hashing it performed, and a local-vocabulary event ("deduplication decision" or the PREMIS `deaccession` term when a copy is excluded) with `eventDetail` naming the rule, the index, the groups and the archivist, exactly as the requirements table describes. The serializer's `_sub`, `_id_block` and `_authored` helpers (`provenance.py:618-647`) are stdlib `xml.etree` and can be copied; the profile registry (`PROFILES`, `provenance.py:895-898`) is the right extension point if Dedupe's record is emitted as a second profile.

**DFXML.** `_dfxml_xml` (`provenance.py:709-771`) and `fileobjects_from_siegfried` (`provenance.py:788-838`) together show how to turn a Siegfried CSV into fileobjects, including the honest markers `fileobject_source`, `fileobjects_truncated` and `container_members_excluded`. Dedupe should read these DFXML files as an index source and may emit its own DFXML for carriers it hashes itself.

**Observations register.** The append-only, accession-level register (`observations.py:1-60`) with columns `recorded, media, stage, class, finding, instrument, disposition, rationale, recorded_by, capture_time` (`observations.py:56-57`), classes `observation | testimony | interpretation | removal` and dispositions `explained | overridden | unresolved` (`observations.py:59-60`), is the closest existing structure to a dedup decision record. It is designed to accrete after bags are sealed (its docstring says so, `observations.py:48-54`), which is precisely when a reappraisal dedup run happens. A frozen snapshot is carried into each bag at sealing (`write_snapshot`, `observations.py:656-690`). Dedupe can write `interpretation` rows ("group 3f2a…: six copies across CM003/CM007/CM011; keep CM003 by earliest-carrier rule; archivist confirmed") with `disposition` and `rationale` filled, and the setaside module already shows the precedent of a `removal` row that outlives the bytes (`setaside.py:246-258`).

**Imaging log.** The 17 columns (`intake.py:74-80`) are the institution's template verbatim; `build_log_row` can be driven with explicit dicts rather than the session (`intake.py:1197-1207`). Dedupe should not add columns; the requirements' DACS prose (Appraisal Information, Processing Information, Extent) belongs in `data/metadata/description.csv` for unsealed bags (`provenance.py:853-863`), in the observations register at accession level, or in Dedupe's own report directory.

## 5. Application scaffolding worth reusing

**Server and token.** `web.main` binds `127.0.0.1` on a random port (`web.py:3207-3213`), mints a per-process `TOKEN = secrets.token_urlsafe(18)` (`web.py:58`), hands the browser a one-time launch key that is traded for an `HttpOnly; SameSite=Strict` cookie (`web.py:73-88`, `web.py:2001-2008`), accepts the API only with an `X-WB-Token` header present (`web.py:2030-2039`), refuses unknown `Host` values (`web.py:197`), and writes `~/.wblock/server.json` (0600) for scripts and `--open` (`web.py:121-145`). It sends `Referrer-Policy: no-referrer` and `nosniff` on every response (`web.py:2015-2018`). This is roughly 300 lines of `web.py`'s 3,898; the rest is embedded HTML pages and 60 `/api/*` routes. The security pattern should be copied; the page machinery should not, because it is bound to LabKit's state snapshot. Note `main()` exits unless `sys.platform == "darwin"` (`web.py:3203-3205`).

**Job model.** There is no queue. Each stage is one daemon thread started under `power.guard` (`pipeline.py:1181-1183`, `pipeline.py:1650-1651`), writing into a single global `session` dict guarded by `_state_lock` (`core.py:372-380`), with `busy()` refusing a second stage (`core.py:458`). The "lane" is not a job model either: `lane.py` is an HTML page that calls the same API (`lane.py:1-37`) and `service.py` is a profile store and staging step (`service.py:1-30`). Dedupe needs a different model, a run over N carriers producing an index and a report, possibly resumable, so this is a rewrite, not a reuse.

**Config.** `~/.wblock/config.json`, loaded once at import (`core.py:206-216`, `core.py:246`) and written without following links (`core.py:218-241`). `core` also loads the `wblock-mac` CLI as a module at import (`core.py:41`, `core.py:17-29`), which means `import wblock_ingest.core` requires that file to exist. Dedupe should keep the `~/.wblock/` directory convention (and read LabKit's `output_base`/`collections_root` from it to find collections) but keep its own config file.

**Stdlib-only constraint.** Stated in `CLAUDE.md` rule 4 and `docs/architecture-strategy.md` §2 and enforced by review. Dedupe's `CLAUDE.md` relaxes this to "no new runtime dependencies without a reason in the PR", which is right: `sqlite3` is stdlib, but TLSH, `imagehash` and `datasketch` are not, and the research report's engineering note allows `blake3` as optional.

**Test harness and gates.** `tests/_harness.py` redirects `HOME` to a scratch tree before `core` is imported, refuses to run against the operator's real config, and starts the real `Handler` in-process on an ephemeral port (`_harness.py:7-20`, `_harness.py:47-63`, `_harness.py:73-99`). `tools/page-gate.py` loads every page in headless Chrome on a throwaway server and fails on any script error or failed resource (`tools/page-gate.py:1-24`). The "four-line checklist" (`CLAUDE.md`, "Done means") is already copied into Dedupe's `CLAUDE.md`. All three should be adopted; the harness needs only its config path and module names changed.

**Release and distribution.** `tools/release.sh` gates a tag on well-formed dated version, `main`, clean tree, `HEAD == origin/main`, green CI, unused tag (`tools/release.sh:1-50`); `release.py` carries a status mark and five release criteria (`release.py:14-22`); CI runs lint, security and tests on every PR (`.github/workflows/ci.yml`). The LabKit kit (`tools/labkit/build.py`, `setup-workstation.py`) assembles a 47 GB portable instance with emulation goldens and collections (`build.py:1-30`), verified by a kit manifest (`setup-workstation.py:1-25`); that mechanism exists because LabKit ships licensed emulation assets and is far heavier than Dedupe needs. Dedupe's distribution should be a git tag plus `brew bundle`, as `docs/install-for-contributors.md` describes for contributors (`docs/install-for-contributors.md:27-37`).

### Recommendation: a standalone app with a copied library and a LabKit seam

Three options were weighed.

*A new lane inside LabKit.* Lowest initial cost: the server, token, capabilities panel and package browser exist. But LabKit's `session` describes one medium (`core.py:372-380`), every stage refuses while another runs (`core.py:458`), `main()` is macOS-only (`web.py:3203`), and the production checkout runs only release tags cut monthly from a 24k-line codebase whose security review is mid-remediation (`README.md`, "Where it stands"). A cross-accession, long-running, Linux-capable analysis does not fit that lifecycle, and every Dedupe change would ride LabKit's release train.

*A separate app sharing a library.* The architecture strategy's own target (`docs/architecture-strategy.md` §1, §4: "modular monolith first, separate apps on demand"; `intake` as the shared component). The shared library does not yet exist as a package; `core` is not importable without `wblock-mac` and a config file. Creating it means refactoring LabKit, which is Michael's call and LabKit's work, not Dedupe's.

*A standalone CLI with LabKit integration (recommended).* Dedupe is a CLI first (index, compare, report, confirm), with an optional localhost page using the copied token pattern. It copies the stdlib-only modules and the small helpers it needs into its own `labtools_common` (later promoted to a shared package when LabKit is ready to consume it too), and integrates with LabKit through files, not imports: it reads LabKit's `~/.wblock/config.json` for `output_base` and `collections_root`, walks accessions with the `scan_packages`/`_find_report_dir` logic, imports bag manifests, Siegfried CSVs and DFXML as index sources, and writes back only to places designed for post-seal accretion: the accession's observations register, a `<accession>/dedupe/` report directory, and (for unsealed bags) `data/metadata/`. A LabKit front-door errand pointing at the Dedupe page (`frontdoor.py`) is a one-line integration later. Trade-off: some duplication of helper code until the shared package exists, and two repositories to keep in step on the observations schema and PREMIS vocabulary; both are small and already documented in LabKit.

## 6. Gaps

What the requirements need and LabKit has no analogue for:

- **A persistent cross-accession hash index.** Nothing in LabKit compares two packages except `sweep._c5_twins`, which works within one accession directory and compares whole images or filename+size sets (`sweep.py:409-441`). No SQLite, no index file, no join against SDR Moab inventories.
- **Match classification.** LabKit's only duplicate notion is Brunnhilde's grouping and `parse_survey`'s count of repeated MD5s on one volume (`pipeline.py:1083-1090`). Exact-in-different-container, candidate-equivalent (same name/size/date, different hash), version/draft exclusion and NSRL "known software file" are all absent.
- **Keep-rule and confirmation workflow.** No concept of a preferred copy, carrier precedence, "keep all" or "never dedup" flags. The closest UI precedents are the scan override with recorded rationale (`pipeline.py:1117`, `observations.record_override`, `observations.py:571`) and the park/set-aside acts with operator reasons (`setaside.py`, `park.py`).
- **Fuzzy or perceptual hashing.** None; no ssdeep, TLSH, MinHash or image hashing anywhere.
- **SHA-256 per file inside images.** Per-file stores are single-algorithm and MD5 by default (`pipeline.py:1213`, `core.py:270`); SHA-256 per file exists only for logical captures (bag manifests). SHA-1 is never computed by LabKit itself.
- **fiwalk/TSK image reading.** Deferred in LabKit (`docs/premis-dfxml-plan.md:154-156`); no allocated/deleted distinction, no byte runs.
- **Containment matrix and aggregation by carrier/directory.** `parse_survey` aggregates by format, not by directory; nothing computes "share of carrier B present on A".
- **Container-member and email-message granularity.** `sf -z` members are identified but deliberately excluded from DFXML and duplicate counting (`provenance.py:806-812`, `pipeline.py:1079-1082`); email stores are detected (`_EmailScan`, `pipeline.py:926`) and staged (`emailext.py`) but not parsed to message or attachment level.
- **Report formats.** LabKit emits HTML pages, CSV logs and XML; it has no HTML report generator independent of the server and no JSON report, though the structure SVG writer (`sweep.structure_svg`, `sweep.py:692`) shows self-contained artifact generation.
- **DACS note generation and ArchivesSpace push.** The ArchivesSpace integration is a plan (`docs/aspace-integration-plan.md`) with the posture that the app opens the archivist's browser rather than writing records (`DESIGN-PHILOSOPHY.md` §3).
- **A dedup PREMIS event.** The vocabulary emitted is capture-centric (`provenance.py:264-538`); a local "deduplication decision" term and a `deaccession` mapping must be added.
- **Linux execution.** `web.main` refuses non-macOS (`web.py:3203`); the `hostos` seam exists but device enumeration is not behind it yet (`hostos/__init__.py:26-29`).

## Unverified

- **Brunnhilde's output set and `-k`.** That Brunnhilde writes `csv_reports/duplicates.csv` by default and deletes its SQLite unless `-k/--keepsqlite` is given is taken from the research report's description of `brunnhilde.py` and from Brunnhilde's documented options, not from code in `da-capture-macos`; LabKit only passes `--noclam -w --csv` (`pipeline.py:1282`). The meaning of `-w` (show Siegfried warnings in the HTML report) is likewise from Brunnhilde's documentation.
- **Siegfried CSV column names.** The column list in the table (`filename, filesize, modified, errors, <algo>, namespace, id, format, version, mime, basis, warning`) is Siegfried's documented `-csv` output; LabKit reads `filename, filesize, modified, errors, id, format, mime` and the algorithm-named column (`pipeline.py:1036-1050`, `provenance.py:802-828`), which is consistent with it, but no sample CSV was read.
- **The default-config duplicate-count caveat** (`pipeline.py:1083`) is inferred from reading the code path with `md5` deselected; it was not driven.
- **fiwalk and SHA-256.** Whether TSK 4.15's fiwalk can emit SHA-256 was not checked here; the research report flags the same question.
- **Line counts in the extraction table** are approximate spans read from the files, not measured by extraction.
- **`hostos.linux.attach_image`** was identified by its definition line (`hostos/linux.py:31`) and the package docstring; its body was not read.
- **The number of `/api/*` routes (60)** is a count of distinct quoted route strings in `web.py`, which may include routes referenced from pages as well as served.
